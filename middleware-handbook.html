1.3 面试官问你「为什么用中间件」的标准答法

🗣 人话：别只答「解耦、异步、削峰」这三个词，要带代价。6 年经验的人如果说不出「引入了 MQ 会带来什么问题」，面试官立刻知道你没真用过。

推荐回答结构（60 秒）：

「我们用 RocketMQ 主要解决三件事：
 第一是解耦——订单履约要通知仓储、积分、营销，原来下游挂了整个下单就失败，现在消息发出去就行；
 第二是削峰——大促时支付回调峰值是平时 20 倍，MQ 兜住之后按自己节奏消费；
 第三是异步提速——下单接口从 800ms 降到 120ms。

 但代价我们也是清楚的：引入了重复消费、消息丢失、顺序错乱、堆积这四类问题。
 所以我们做了三件事保证：
 ① 消费端幂等，用订单号 + 状态机，重复消息直接被状态拦掉；
 ② 生产端同步发送 + Broker 同步刷盘 + 主从，消费端手动 ACK；
 ③ 堆积有监控告警，lag 超过阈值自动扩容消费者。

 所以我的观点是：MQ 不是银弹，只把非核心、可补偿的链路异步化，核心的扣库存还是同步调用。」

最后那句话是加分点——它证明你有判断力，不是为了用而用。

🗣 人话版：MQ 就是传菜口。厨师（生产者）做好放上去，服务员（消费者）自己来取，两边不用互相等。它的毛病也都是传菜口的通病：菜会不会掉（丢消息）、会不会上两遍（重复消费）、会不会排错队（顺序）、堆太多怎么办（堆积）。这一章把四个毛病一个个解决掉。

几个必须记住的点：

  1. NameServer 无状态，挂了不影响已建立的连接，只影响新连接发现（这就是为什么 RocketMQ 比 ZooKeeper 方案运维简单）。
  2. Broker 有 Master / Slave。默认 ASYNC_MASTER 刷盘 + 异步复制，会丢消息；生产环境要 SYNC_MASTER（同步复制到从节点）。
  3. Pull 模式：消费者主动来拉（DefaultMQPushConsumer 封装了拉取逻辑，内部看起来像推）。
  4. 消费进度存在 Broker 端（ConsumerQueue 的 offset），所以消费位点是集群共享的。

2.2 消息不丢：三段式防线 + 代码

🗣 人话：一封信要送到，三关都得守住：发的人确认寄出去了、邮局确认入箱了、收的人确认拆开看了。少一关都可能丢。我们项目里三关全上了，还留了第四关——对账兜底。

三关分别是什么

【第一关】生产者 → Broker
   同步发送 + 失败重试 + 检查 SendStatus
   ↓
【第二关】Broker 落盘
   同步刷盘(SYNC_FLUSH) + 同步复制(SYNC_MASTER)
   ↓
【第三关】Broker → 消费者
   手动 ACK（业务处理成功才提交 offset）
   ↓
【兜底】本地消息表 + 定时对账

生产端代码：同步发送 + 状态校验

@Service
@RequiredArgsConstructor
public class OrderMessageProducer {

    private final RocketMQTemplate rocketMQTemplate;
    private final MqSendLogMapper mqSendLogMapper;

    /**
     * 发送订单事件。
     * 关键点1：syncSend 是同步等待 Broker 的 ack，失败会抛异常
     * 关键点2：必须检查 sendStatus，SendStatus != SEND_OK 视为失败
     * 关键点3：先落本地消息表再发消息（或用事务消息），保证本地事务与消息最终一致
     */
    public void sendOrderPaid(OrderPaidEvent event) {
        // 兜底：先写本地消息表，状态 INIT
        MqSendLog log = new MqSendLog();
        log.setBizId(event.getOrderNo());
        log.setTopic("ORDER_TOPIC");
        log.setTag("ORDER_PAID");
        log.setMsgId(IdWorker.getIdStr());
        log.setStatus(SendStatusEnum.INIT.getCode());
        log.setCreateTime(LocalDateTime.now());
        mqSendLogMapper.insert(log);   // 唯一索引：biz_id + topic + tag

        try {
            Message<String> message = MessageBuilder.withPayload(JSON.toJSONString(event))
                    .setHeader(RocketMQHeaders.KEYS, event.getOrderNo())
                    .setHeader(RocketMQHeaders.TAGS, "ORDER_PAID")
                    .build();

            // 同步发送，超时 3 秒；sendTimeout 单位毫秒
            SendResult sendResult = rocketMQTemplate.syncSend(
                    "ORDER_TOPIC:ORDER_PAID", message, 3000);

            if (sendResult.getSendStatus() != SendStatus.SEND_OK) {
                // 关键点：状态不是 SEND_OK，不能当成功，要落 FAIL 等补偿任务捞
                log.setStatus(SendStatusEnum.FAIL.getCode());
                log.setErrMsg(sendResult.getMsgId() + ":" + sendResult.getSendStatus());
                mqSendLogMapper.updateById(log);
                log.warn("MQ 发送状态异常 orderNo={} status={}",
                        event.getOrderNo(), sendResult.getSendStatus());
                return;
            }

            log.setStatus(SendStatusEnum.SUCCESS.getCode());
            log.setMsgId(sendResult.getMsgId());
            mqSendLogMapper.updateById(log);
        } catch (Exception e) {
            log.setStatus(SendStatusEnum.FAIL.getCode());
            log.setErrMsg(e.getMessage());
            mqSendLogMapper.updateById(log);
            log.error("MQ 发送异常 orderNo={}", event.getOrderNo(), e);
            // 关键点：不要吞异常，让上游感知；失败记录由定时任务兜底重发
            throw new BizException("订单事件发送失败", e);
        }
    }
}

@Service
public class ManualAckService {

    @Autowired
    private RocketMQTemplate rocketMQTemplate;

    /**
     * 拉模式：完全自己控制 ACK 时机。
     * 关键点1：pullSyncAndDecode 拿到的是 MessageExt，可以拿到 msgId 做幂等
     * 关键点2：processConsumeResult 返回 CommitState 才能提交 offset
     */
    public void consume() {
        PullRequest request = new PullRequest();
        request.setConsumerGroup("ORDER_FULFILL_GROUP");
        request.setQueueNames(new String[]{"ORDER_TOPIC"});

        PullResult pullResult = rocketMQTemplate.pullSyncAndDecode(request);
        for (MessageExt messageExt : pullResult.getFoundList()) {
            boolean ok = false;
            try {
                OrderPaidEvent event = JSON.parseObject(
                        new String(messageExt.getBody(), StandardCharsets.UTF_8),
                        OrderPaidEvent.class);
                orderService.handleOrderPaid(event);
                ok = true;
            } catch (BizException e) {
                // 可重试异常：返回失败，会重试
                log.error("业务处理失败，将重试 msgId={}", messageExt.getMsgId(), e);
            } catch (Exception e) {
                // 不可重试异常：直接标记成功，避免无限重试（脏数据）
                log.error("数据异常，跳过 msgId={} body={}", messageExt.getMsgId(), e.getMessage());
                ok = true;
            }
            // 关键点3：只有业务明确成功才提交位点
            rocketMQTemplate.ackMessageSync(messageExt, ok
                    ? ConsumeConcurrentlyStatus.CONSUME_SUCCESS
                    : ConsumeConcurrentlyStatus.RECONSUME_LATER);
        }
    }
}

2.3 幂等消费：MQ 只能保证「至少一次」

🗣 人话：MQ 的投递语义是 at least once（至少一次），也就是「宁可多送一次，绝不漏送」。所以重复消费是必然发生的，不是意外。你必须在消费端做幂等——这才是 MQ 使用的核心工作量所在。

为什么一定会重复

场景 原因
网络抖动 Broker 已投递，消费者已收到但 ACK 丢了 → 重投
消费端宕机 业务处理完了但还没提交 offset 就挂了 → 重投
Rebalance 消费组重新分配时，未 ACK 的消息被分给新消费者 → 重投
重试机制 消费失败自动重投
生产端重试 同步发送超时但 Broker 实际已收到 → 重复投递

幂等的四种方案（按可靠性排序）

方案一：数据库唯一索引（最可靠，首选）

/**

 * 方案一：唯一索引 + 状态机。
 * 关键点1：唯一索引是最后一道防线，靠数据库保证，不会因为并发失效
 * 关键点2：先查再插在并发下不可靠，必须靠唯一索引兜底
 */
@Service
public class IdempotentService {

    @Autowired
    private IdempotentRecordMapper idempotentMapper;

    @Autowired
    private OrderService orderService;

    public void handle(OrderPaidEvent event) {
        // 尝试插入幂等记录，唯一索引冲突就说明处理过了
        IdempotentRecord record = new IdempotentRecord();
        record.setBizId(event.getOrderNo());
        record.setBizType("ORDER_PAID");
        record.setStatus(ProcessStatusEnum.INIT.getCode());
        record.setCreateTime(LocalDateTime.now());

        int inserted;
        try {
            inserted = idempotentMapper.insertIgnore(record);
        } catch (DuplicateKeyException e) {
            // 关键点3：重复消息直接跳过，但要判断上次的处理状态
            IdempotentRecord exist = idempotentMapper.selectByBizId(
                    event.getOrderNo(), "ORDER_PAID");
            if (exist != null && ProcessStatusEnum.SUCCESS.getCode() == exist.getStatus()) {
                log.info("重复消息，跳过 orderNo={}", event.getOrderNo());
                return;
            }
            // 存在但状态不是 SUCCESS，可能是上次处理中失败，允许重试
            inserted = 1;
        }

        if (inserted > 0) {
            try {
                orderService.handleOrderPaid(event);
                idempotentMapper.updateStatus(event.getOrderNo(), "ORDER_PAID",
                        ProcessStatusEnum.SUCCESS.getCode());
            } catch (Exception e) {
                idempotentMapper.updateStatus(event.getOrderNo(), "ORDER_PAID",
                        ProcessStatusEnum.FAIL.getCode());
                throw e;   // 抛出让 MQ 重试
            }
        }
    }
}

2.4 顺序消息：只要「局部有序」，不要全局有序

🗣 人话：全局有序 = 所有消息走一个队列一个线程消费，吞吐直接废掉。实际业务只要同一个订单的消息按顺序处理就行——那就是「同 key 同队列同线程」。

RocketMQ 顺序消息实现

@Component
@RequiredArgsConstructor
public class OrderMessageSelector implements MessageQueueSelector {

    private final OrderMapper orderMapper;

    /**
     * 关键点：用订单号做 hash，保证同一个订单的消息永远进同一个队列。
     * 队列数固定（broker 配置的 queueNums），扩队列会破坏已有映射，慎改。
     */
    @Override
    public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
        String orderNo = (String) arg;
        // 二次 hash 再取模，避免连续订单号落到同一队列（数据倾斜）
        long hash = Math.abs(orderNo.hashCode());
        int index = (int) (hash % mqs.size());
        return mqs.get(index);
    }

    public void sendOrdered(OrderEvent event) {
        Message<String> message = MessageBuilder.withPayload(JSON.toJSONString(event))
                .setHeader(RocketMQHeaders.TAGS, "ORDER_STATUS")
                .build();
        // 关键点2：syncSend 第四个参数传 MessageQueueSelector，第五个参数传 hashKey
        rocketMQTemplate.syncSend("ORDER_TOPIC:ORDER_STATUS", message, 3000,
                new OrderMessageSelector(), event.getOrderNo());
    }
}

方案 C：Redis ZSet 延时队列（自己实现，灵活）

/**

 * Redis ZSet 延时队列。
 * 关键点1：用 ZSet 的 score 存到期时间戳，ZPOPMIN 拿到期任务
 * 关键点2：需要轮询调度器（多实例要用分布式锁，或者用 Redisson 看门狗）
 * 关键点3：数据在内存，宕机可能丢（Redis 有持久化但不保证），对可靠性要求高的场景不要用
 */
@Component
public class DelayQueueService {

    private static final String ZSET_KEY = "delay:queue:order:close";
    private static final String LOCK_KEY = "delay:queue:lock";

    @Autowired
    private StringRedisTemplate redisTemplate;

    @Autowired
    private RedissonClient redissonClient;

    public void push(String bizId, long executeAtMillis) {
        redisTemplate.opsForZSet().add(ZSET_KEY, bizId, executeAtMillis);
    }

    /**
     * 调度任务：每 1 秒扫一次到期任务。
     * 关键点：用 Redisson 分布式锁保证多实例只有一个在扫（否则重复消费）
     */
    @Scheduled(fixedDelay = 1000)
    public void schedule() {
        RLock lock = redissonClient.getLock(LOCK_KEY);
        // 关键：tryLock 拿不到就跳过，不要阻塞
        if (!lock.tryLock()) {
            return;
        }
        try {
            long now = System.currentTimeMillis();
            // 关键：一次只取一批，避免单次拉太多把 Redis 拖死
            Set<String> due = redisTemplate.opsForZSet()
                    .rangeByScore(ZSET_KEY, 0, now, 0, 100);
            if (due == null || due.isEmpty()) {
                return;
            }
            for (String bizId : due) {
                // 关键：ZREM 返回 1 表示删除成功 = 抢到了这个任务
                Boolean removed = redisTemplate.opsForZSet().remove(ZSET_KEY, bizId);
                if (Boolean.TRUE.equals(removed)) {
                    orderService.closeIfUnpaid(bizId);
                }
            }
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}

2.6 事务消息：本地事务与消息的原子性

🗣 人话：你改了数据库，然后要发消息通知下游。这俩是「改库」和「发消息」两个动作，中间可能断电。事务消息的办法是：先发一条「半消息」（消费者看不见），你把库改成功后回复「提交」，它才变成真消息；如果中途挂了，Broker 会回来问「你那事到底成没成」，你查库告诉它。

RocketMQ 事务消息实现

@Service
@RequiredArgsConstructor
public class OrderTransactionProducer {

    private final TransactionMqProducer producer;   // 或用 rocketMQTemplate 的事务方法
    private final OrderMapper orderMapper;

    /**
     * 关键点1：先发半消息，Broker 只存储不投递
     * 关键点2：拿到 sendResult 后执行本地事务
     * 关键点3：本地事务执行完，明确回复 COMMIT / ROLLBACK
     * 关键点4：如果没回复（进程挂了），Broker 会回查 checkLocalTransaction
     */
    public void createOrderWithTx(OrderDO order) {
        Message<String> message = MessageBuilder
                .withPayload(JSON.toJSONString(order))
                .setHeader(RocketMQHeaders.KEYS, order.getOrderNo())
                .setHeader(RocketMQHeaders.TAGS, "ORDER_CREATED")
                .setHeader("TX_XID", order.getOrderNo())   // 关键：回查时用来定位业务
                .build();

        TransactionSendResult result = producer.sendMessageInTransaction(
                new Message("ORDER_TOPIC:ORDER_CREATED", message),
                order,   // 关键：本地事务参数，回查时原样带回
                this::executeLocalTransaction,
                this::checkLocalTransaction);
    }

    /** 本地事务执行 */
    private LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        OrderDO order = (OrderDO) arg;
        try {
            orderMapper.insert(order);
            return LocalTransactionState.COMMIT_MESSAGE;   // 成功 → 提交消息
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE; // 失败 → 回滚消息
        }
    }

    /** Broker 回查：进程重启/网络异常时，Broker 不知道结果，会来问 */
    private LocalTransactionState checkLocalTransaction(MessageExt msg) {
        String orderNo = msg.getUserProperty("TX_XID");
        // 关键：回查时必须查真实数据，不能凭内存状态判断
        OrderDO order = orderMapper.selectByOrderNo(orderNo);
        if (order == null) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
        return LocalTransactionState.COMMIT_MESSAGE;
    }
}

            return orderMapper.selectByOrderNo(orderNo) != null
                    ? LocalTransactionState.COMMIT_MESSAGE
                    : LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    public void create(OrderDO order) {
        // 关键：第二个参数是本地事务执行器要用的业务参数
        TransactionSendResult result = rocketMQTemplate.sendMessageInTransaction(
                "ORDER_TOPIC:ORDER_CREATED",
                MessageBuilder.withPayload(JSON.toJSONString(order)).build(),
                order);
    }
}

事务消息的局限（面试必答）

🗣 人话：事务消息不是万能的。Broker 回查最多 15 次，回查期间消息是「悬着的」；如果你的业务在回查时仍然判断不了（比如依赖了已经回滚的外部系统），还是会有不一致。所以任何方案都要有对账兜底。

局限 说明 兜底
回查次数有限 默认 15 次 超时后进死信，人工/定时处理
回查有延迟 Broker 默认 6s 后开始回查 下游能接受秒级延迟
依赖本地库可查 回查要查 DB 业务数据要有唯一键可查
不解决跨异构系统 支付网关的事务不受你控制 用「查询 + 补偿」代替事务

三种方案的取舍

方案 一致性 复杂度 场景
本地消息表 最终一致 中 通用，推荐
RocketMQ 事务消息 最终一致 中高 已经在用 MQ 的项目
Seata AT 强一致（准） 高 同步链路、跨自家服务

本地消息表（最推荐的通用方案）：

/**

 * 本地消息表：在同一个事务里写业务数据和消息表，
 * 再由定时任务扫描消息表发消息，发成功后标记完成。
 * 关键点1：业务数据 + 消息表在同一个本地事务里，天然一致
 * 关键点2：定时任务扫描未发送的消息重发（这就是"至少一次"）
 * 关键点3：消费端做幂等，配合唯一索引
 */
@Transactional(rollbackFor = Exception.class)
public void createOrder(OrderDO order) {
    orderMapper.insert(order);

    MessageLog msgLog = new MessageLog();
    msgLog.setBizId(order.getOrderNo());
    msgLog.setTopic("ORDER_TOPIC");
    msgLog.setTag("ORDER_CREATED");
    msgLog.setPayload(JSON.toJSONString(order));
    msgLog.setStatus(SendStatusEnum.INIT.getCode());
    msgLog.setRetryCount(0);
    msgLog.setCreateTime(LocalDateTime.now());
    messageLogMapper.insert(msgLog);   // 和业务数据同一个事务
}

/** 定时扫描发送（每 5 秒） */
@Scheduled(fixedDelay = 5000)
public void scanAndSend() {
    List<MessageLog> logs = messageLogMapper.selectPending(100);
    for (MessageLog msgLog : logs) {
        try {
            SendResult result = rocketMQTemplate.syncSend(
                    msgLog.getTopic() + ":" + msgLog.getTag(), msgLog.getPayload(), 3000);
            if (result.getSendStatus() == SendStatus.SEND_OK) {
                messageLogMapper.markSuccess(msgLog.getId());
            } else {
                messageLogMapper.markRetry(msgLog.getId());
            }
        } catch (Exception e) {
            messageLogMapper.markRetry(msgLog.getId());
        }
    }
}

2.7 消息堆积：先定位，再止血

🗣 人话：队列里消息越堆越多，常见原因就四个：消费者挂了、消费者变慢了、上游流量突增、有消息一直重试（毒消息卡住）。先看监控知道是哪个，再对症下药。

第一步：定位（必须有监控）

/**

 * 消费端埋点：每条消息的处理耗时 + 成功率。
 * 关键点1：耗时打点能看出是「整体变慢」还是「个别消息超时」
 * 关键点2：成功率能看出是异常还是单纯慢
 */
@Aspect
@Component
public class MqConsumeMetricsAspect {

    @Around("@annotation(org.apache.rocketmq.spring.annotation.RocketMQMessageListener)")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        String topic = pjp.getSignature().getName();
        try {
            Object result = pjp.proceed();
            Metrics.counter("mq.consume.success", "topic", topic).increment();
            return result;
        } catch (Throwable t) {
            Metrics.counter("mq.consume.fail", "topic", topic).increment();
            throw t;
        } finally {
            Metrics.timer("mq.consume.latency", "topic", topic)
                    .record(System.currentTimeMillis() - start);
        }
    }
}

第二步：止血（按优先级）

优先级 1 —— 临时扩容消费者
  RocketMQ：直接加机器/加线程，队列数决定并行度上限
  Kafka：消费者数 ≤ 分区数（超了多出来的空转），只能加分区
  ⚠ 消费能力受限于「分区数 / 队列数」，不是线程数

优先级 2 —— 提升单条处理效率
  · 把同步调用改异步
  · 批量写 DB（一条条 insert 改 batch insert）
  · 把非关键逻辑挪到消费后置（比如日志上报、埋点）

优先级 3 —— 降级
  · 把堆积消息转存到临时 Topic / DB，恢复主链路
  · 丢弃非核心消息（日志、埋点类）

优先级 4 —— 跳过积压
  · resetOffsetByTime 跳到某个时间点（应急，会丢消息）
  · 只在「消息本身价值不大」时用

优先级 5 —— 事后补偿
  · 消费完后再跑一次对账/补偿任务，把漏掉的补齐

/**

 * 消费端熔断：下游依赖挂了，快速失败让 MQ 重试，别把自己也拖死。
 */
@Service
public class ResilientOrderHandler {

    private final SentinelSentinel sentinel;  // 或用 Resilience4j

    public void handle(OrderPaidEvent event) {
        // 关键：熔断降级，避免一个慢下游拖垮整个消费线程
        if (!sentinel.tryEntry()) {
            throw new DegradeException("下游系统繁忙，稍后重试");
        }
        try {
            orderService.handleOrderPaid(event);
        } finally {
            sentinel.exit();
        }
    }
}

2.8 MQ 常见坑清单（每一条都真实踩过）

# 坑 症状 解决
1 消费者数 > 分区数 多出来的消费者空转，CPU 高但没产出 Kafka 扩分区或减少消费者
2 消息体太大 发送超时、Broker 拒绝（默认 4MB） 压缩、分片、或走文件传输
3 Tag 表达式写错 消费者收不到消息，没有任何报错 Tag 用 || 不是 &&；用 * 匹配全部前测试
4 消费组名不一致 消息被另一个组消费了 组名当常量管理，别硬编码
5 循环依赖消费 A 消费发消息给 B，B 又发回 A 加消息链路 ID + 深度限制
6 大事务里发消息 长事务持锁 + 消息发不出去 消息发送放事务外，状态表兜底
7 忽略 SendStatus 发送失败但业务当成功 严格检查 SEND_OK
8 消费端吞异常 消息丢失（当成消费成功提交 offset） 异常必须抛出
9 毒消息无限重试 一个坏消息卡住整个队列 maxReconsumeTimes + DLQ + 死信告警
10 消息 key 没设 查轨迹困难、日志排查低效 用业务 ID 做 key，日志打 msgId
11 时钟不同步 延迟消息不准、过期判断错 生产环境配 NTP
12 Broker 重启丢消息 异步刷盘 + 断电 交易类必须同步刷盘

三、Elasticsearch 实战全解

🗣 人话版：ES 是一本倒着查的书。普通数据库是「翻到第几页看写了啥」，ES 是「先查关键词索引，直接告诉你哪几页有这个词」。所以它搜得快，但写得慢一点，而且默认不是实时的（差 1 秒）。

3.1 倒排索引：为什么搜得快

🗣 人话：正排是「这本书第 300 页写了什么」，倒排是「『支付』这个词出现在第 12、45、300 页」。查词不用从头翻，直接跳到那几页。

倒排索引长什么样

文档（正排视角）：
  文档1: "用户用微信支付了订单1001"
  文档2: "用户用支付宝支付了订单1002"
  文档3: "用户用微信退款了订单1003"

倒排索引（词 → 文档列表）：
  "用户"  → [文档1, 文档2, 文档3]
  "微信"  → [文档1, 文档3]
  "支付宝"→ [文档2]
  "支付"  → [文档1, 文档2]
  "退款"  → [文档3]

查「微信 AND 支付」= 倒排表求交集 = [文档1]。

两层结构（面试高分点）

┌─────────────────────────────────────────┐
│  Term Dictionary（词典）                │
│  内存里，压缩成 FST（有限状态转换器）      │
│  作用：词 → 定位到倒排表文件位置            │
│  特点：极小、可全内存、查找 O(1)          │
└───────────────┬─────────────────────────┘
                │ 指向
                ▼
┌─────────────────────────────────────────┐
│  Posting List（倒排表）                  │
│  磁盘上，.doc 存文档ID，.tim 存词频+位置  │
│  特点：用【跳表 SkipList】支持快速求交集  │
└─────────────────────────────────────────┘

为什么求交快：跳表让每个文档列表按"每 16 个取一个"建稀疏索引，跳跃查找可以跳过大量元素。

关键点：分词是罪魁祸首。搜不到 90% 的原因是分词器或字段类型配错：

字段类型 分词 用途 例子
text 会分词 全文搜索、模糊匹配 商品标题、描述
keyword 不分词 精确匹配、聚合、分组 商品编码、状态、用户 ID
text + keyword 双字段 两种都有 全文搜 + 精确匹配 最常用做法 
{
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "ik_max_word",          // 索引时细粒度切分
        "search_analyzer": "ik_smart",      // 搜索时粗粒度切分
        "fields": {
          "keyword": {                       // 冗余一个不分词字段，用于精确匹配/聚合
            "type": "keyword",
            "ignore_above": 256
          }
        }
      },
      "status": { "type": "keyword" },
      "createTime": { "type": "date", "format": "yyyy-MM-dd HH:mm:ss||epoch_millis" }
    }
  }
}

为什么用 ik_max_word 索引、ik_smart 搜索？ 索引时切得细（"北京大学" → 北京/大学/北京大学），召回全；搜索时切得粗（避免"中国"命中所有含"国"的文档），精度高。这是 IK 的标准用法。

3.2 写入流程：为什么 ES 是「近实时」

🗣 人话：写进去先放内存缓冲区并记日志，默认每秒刷一次生成一个新段，这时候才能被搜到——所以叫「近」实时。批量导入时把刷新关掉，导完再手动刷，能快好几倍。

写请求
  │
  ▼
① 写入 memory buffer（内存缓冲）
  │  同时写 translog（事务日志，防宕机丢数据）
  ▼
② refresh（默认 1s）——把 buffer 生成一个新的 segment
  │  ★ 此时数据才可被搜索 → 这就是 near real-time 的来源
  ▼
③ flush ——segment 落盘到磁盘，清空 translog
  ▼
④ merge（后台）——小 segment 合并成大 segment
     ★ merge 很吃 IO 和 CPU，要限流

/**

 * 批量导入的正确姿势：关 refresh + 关 merge + 导完手动 refresh。
 * 关键点1：refresh_interval 设为 -1，导入期间不生成新 segment
 * 关键点2：导入完成后手动 POST /_refresh 让数据可搜
 * 关键点3：merge 限流避免影响线上查询
 */
public void bulkImport(List<OrderDoc> list) {
    // 关键点1：临时关 refresh
    client.indices().putSettings(s -> s
            .index(INDEX)
            .settings(st -> st
                    .indexSettings(is -> is.refreshInterval(r -> r.time(" -1s")))
                    .numberOfReplicas(r -> r.value("0"))   // 导入期间不要副本
            ));

    try {
        BulkRequest bulk = new BulkRequest();
        for (OrderDoc doc : list) {
            bulk.operations(op -> op.index(idx -> idx
                    .index(INDEX)
                    .id(doc.getOrderNo())
                    .document(doc)));
        }
        client.bulk(bulk, BulkRequestOptions.DEFAULT);
    } finally {
        // 关键点2：手动刷新 + 恢复副本
        client.indices().refresh(r -> r.index(INDEX));
        client.indices().putSettings(s -> s
                .index(INDEX)
                .settings(st -> st
                        .indexSettings(is -> is.refreshInterval(r -> r.time("1s")))
                        .numberOfReplicas(r -> r.value("1"))
                ));
    }
}

3.3 深分页：from + size 为什么慢

🗣 人话：from+size 是「每个分片都把前 N 条搬出来，协调节点再统一排序」——翻到第 1000 页等于搬了几十万条。用 search_after 拿上一页最后一条当书签，实时又没深度限制。

/**

 * 深分页方案一：search_after（推荐）。
 * 关键点1：sort 字段必须唯一且有值（用 createTime + _id 组合）
 * 关键点2：只能往后翻，不能往前
 * 关键点3：实时数据，不占资源（不像 scroll 占快照）
 */
public SearchResult searchAfter(List<SortValue> lastSort, int size) {
    SearchRequest request = new SearchRequest.Builder()
            .index(INDEX)
            .query(q -> q.bool(b -> b
                    .must(m -> m.match(mm -> mm.field("status").query("PAID")))))
            .sort(s -> s.field(f -> f.field("createTime").order(SortOrder.Desc)))
            .sort(s -> s.field(f -> f.field("_id").order(SortOrder.Desc)))
            .searchAfter(lastSort)          // 关键：传上一页最后一条的 sort 值
            .size(size)
            .build();

    SearchResponse<OrderDoc> response = client.search(request, OrderDoc.class);

    List<SearchResult> results = new ArrayList<>();
    List<SortValue> nextCursor = null;
    for (Hit<OrderDoc> hit : response.hits().hits()) {
        results.add(new SearchResult(hit.source(), hit.sort()));
        nextCursor = hit.sort();          // 关键：保存作为下一页游标
    }
    return new SearchResult(results, nextCursor);
}

/**

 * 深分页方案二：scroll（适合导出，不适合分页 UI）。
 * 关键点1：基于时间点快照，数据是"冻结"的，导完要 clear scroll
 * 关键点2：大量导出会占用 ES 资源，要限流
 */
public void exportAll(Consumer<OrderDoc> consumer) {
    ScrollRequest scrollRequest = new ScrollRequest.Builder()
            .indices(INDEX)
            .scroll(Time.ofMinutes, 1L))
            .size(500)
            .query(q -> q.matchAll(m -> m))
            .build();

    ScrollResponse<OrderDoc> response = client.scroll(scrollRequest, OrderDoc.class);
    String scrollId = response.scrollId();

    try {
        while (response.hits().hits().size() > 0) {
            for (Hit<OrderDoc> hit : response.hits().hits()) {
                consumer.accept(hit.source());
            }
            response = client.scroll(scrollRequest.scrollId(scrollId)
                    .scroll(Time.ofMinutes, 1L)), OrderDoc.class);
            scrollId = response.scrollId();
        }
    } finally {
        // 关键点3：必须清理，否则 scroll 上下文一直占资源
        client.clearScroll(c -> c.scrollId(scrollId));
    }
}

3.4 MySQL 与 ES 数据同步（最容易追问的题）

🗣 人话：双写最简单但容易不一致；发 MQ 解耦但要处理顺序和重复；最省心的是 Canal 订阅 binlog，业务代码一行不用改，还天然有序。

/**

 * Canal 客户端：监听 binlog 变化，同步到 ES。
 * 关键点1：按数据库+表名订阅，避免全库监听
 * 关键点2：增量订阅要记录位点，重启能续上
 * 关键点3：ES 写入用 bulk，不要一条一条写
 */
@Component
public class CanalSyncService {

    private static final String CANAL_HOST = "192.168.31.6";
    private static final int CANAL_PORT = 11111;

    @Autowired
    private ElasticsearchClient esClient;

    @Autowired
    private CanalClient canalClient;

    @Autowired
    private CanalPositionMapper positionMapper;

    /**
     * 启动监听（放在一个独立线程里，不阻塞主流程）。
     */
    @PostConstruct
    public void start() {
        Thread thread = new Thread(this::run, "canal-sync");
        thread.setDaemon(true);
        thread.start();
    }

    private void run() {
        CanalConnector connector = CanalConnectors.newSingleConnector(
                new InetSocketAddress(CANAL_HOST, CANAL_PORT),
                "example", "", "");
        try {
            connector.connect();
            connector.subscribe(".*\\..*\\..*");
            logger.info("Canal 连接成功");

            while (running) {
                CanalEntry entry = connector.getWithoutAck(100);
                long batchId = entry.getHeader().getLogfileOffset();
                int size = entry.getEntryCount();

                for (int i = 0; i < size; i++) {
                    CanalEntry.Entry e = entry.getEntries().get(i);
                    if (e.getEntryType() == EntryType.ROWDATA) {
                        CanalEntry.RowChange rowChange = CanalEntry.RowChange.parse(e);
                        for (CanalEntry.RowData rowData : rowChange.getRowDatasList()) {
                            handleRowChange(rowChange.getEventType(), rowData);
                        }
                    }
                }
                connector.ack(batchId);   // 关键点2：处理完才 ack，否则会丢
            }
        } catch (Exception e) {
            logger.error("Canal 同步异常", e);
        } finally {
            connector.disconnect();
        }
    }

    private void handleRowChange(EntryType type, CanalEntry.RowData rowData) {
        String table = rowData.getTableName();
        // 关键点1：只处理关心的表
        if (!"t_order".equals(table)) {
            return;
        }

        List<Map<String, Object>> columns = rowData.getAfterColumnsList().stream()
                .map(c -> {
                    Map<String, Object> m = new HashMap<>();
                    m.put(c.getName(), c.getValue());
                    return m;
                }).collect(Collectors.toList());

        String orderNo = (String) columns.get(0).get("order_no");

        if (type == EntryType.DELETE) {
            esClient.delete(d -> d.index(INDEX).id(orderNo));
            return;
        }

        // 关键点3：走 bulk（这里简化为单条，实际应批量攒 500 条一次提交）
        esClient.index(i -> i.index(INDEX).id(orderNo).document(columns));
    }
}

/**

 * MQ 方案：业务写库后发消息，ES 消费端消费。
 * 关键点1：消息里带全量数据还是只带 ID？带 ID 要回查 DB，带全量省一次查询但数据可能旧
 * 关键点2：ES 写入要幂等（用业务 ID 做文档 ID，天然幂等——重复写覆盖同一份）
 * 关键点3：update 用 doc（部分更新）还是全量覆盖？partial update 更快但要注意字段删除
 */
@RocketMQMessageListener(topic = "ORDER_TOPIC", consumerGroup = "ORDER_ES_SYNC_GROUP")
public class OrderEsSyncListener implements RocketMQListener<OrderSyncMessage> {

    @Autowired
    private ElasticsearchClient esClient;

    private OrderMapper orderMapper;

    public void onMessage(OrderSyncMessage msg) {

                .index("order_index")
                .id(msg.getOrderNo())            // 关键点2

同步方案必须处理的 4 个问题

  1. 全量初始化：ES 空索引 → 写个 DataSyncJob 从 MySQL 分批导入（用 scroll 或分页，避免深分页）
  2. 增量追平：初始化期间的数据用 binlog 位点补齐
  3. 删除同步：binlog 方案能拿到 DELETE 事件，MQ 方案要在消息里带操作类型
  4. 一致性延迟：用户写完立刻搜索可能搜不到 → 前端做乐观更新，或搜索时先查主库
/**

 * 全量初始化 + 增量追平。
 * 关键点1：先记 binlog 起始位点，再导存量，最后追增量
 * 关键点2：存量导入用 scroll，避免深分页
 */
public void initFullSync() {
    // 1. 记录当前 binlog 位点
    CanalPosition position = canalClient.getCurrentPosition();
    positionMapper.save(position);

    // 2. 全量导入（scroll）
    BulkProcessor bulkProcessor = BulkProcessor.builder(esClient, b -> b)
            .setBulkActions(500)
            .setBulkSize(new ByteSizeValue(5, ByteSizeUnit.MB))
            .setFlushInterval(new TimeValue(5, TimeUnit.SECONDS))
            .build();

    try {
        scrollExport(order -> bulkProcessor.add(new IndexOperation<>(
                b -> b.index("order_index").id(order.getOrderNo()).document(order))));
    } finally {
        bulkProcessor.close();
    }

    // 3. 增量追平（从记录的位点开始）
    canalClient.startFrom(position);
}

3.5 ES 在业务里的典型用法

用法一：商品/门店搜索（多条件 + 排序 + 聚合）

/**

 * 多条件搜索：关键词 + 过滤条件 + 排序 + 分页。
 * 关键点1：关键词用 match（会分词），精确条件用 term（不分词）
 * 关键点2：filter 上下文不打分，性能比 must 好
 */
public SearchResult<StoreDoc> searchStore(StoreQuery query) {
    BoolQuery.Builder bool = new BoolQuery.Builder();

    if (StringUtils.hasText(query.getKeyword())) {
        bool.must(m -> m.multiMatch(mm -> mm
                .query(query.getKeyword())
                .fields("name^3", "address", "tags")));   // ^3 = name 权重 3 倍
    }
    if (query.getCityCode() != null) {
        bool.filter(f -> f.term(t -> t.field("cityCode").value(query.getCityCode())));
    }
    if (query.getStatus() != null) {
        bool.filter(f -> f.term(t -> t.field("status").value(query.getStatus())));
    }
    if (query.getMinScore() != null) {
        bool.filter(f -> f.range(r -> r.field("score").gte(JsonData.of(query.getMinScore()))));
    }

    SearchRequest request = new SearchRequest.Builder()
            .index("store_index")
            .query(q -> q.bool(bool.build()))
            .sort(s -> s.field(f -> f.field("_score").order(SortOrder.Desc)))
            .sort(s -> s.field(f -> f.field("distance").order(SortOrder.Asc)))  // 地理位置
            .from(query.getPage() * query.getSize())
            .size(query.getSize())
            .highlight(h -> h
                    .fields("name", f -> f.highlightType(HighlightType.Marked))
                    .preTags("<em>").postTags("</em>"))
            .build();

    return client.search(request, StoreDoc.class);
}

用法二：聚合分析（报表、看板）

/**

 * 聚合分析：按状态分组统计 + 求和 + 去重计数。
 * 关键点1：terms 聚合要设置 size，不然返回的桶不够
 * 关键点2：基数聚合（cardinality）有精度代价，基数不大时用 terms + 子聚合更准
 * 关键点3：聚合字段必须 doc_values 开启（默认开启，别设 "index": false）
 */
public Map<String, Object> orderStatistics(LocalDateTime start, LocalDateTime end) {
    SearchRequest request = new SearchRequest.Builder()
            .index("order_index")
            .size(0)   // 只要聚合结果，不要文档
            .query(q -> q.bool(b -> b
                    .filter(f -> f.range(r -> r.field("createTime")
                            .gte(JsonData.of(start.toString()))
                            .lte(JsonData.of(end.toString()))))))
            .aggregations("by_status", a -> a.terms(t -> t
                    .field("status")
                    .size(50)
                    .aggregations("amount_sum", s -> s.sum(x -> x.field("payAmount")))
                    .aggregations("store_count", c -> c.cardinality(x -> x.field("storeId")))
                    .aggregations("avg_time", av -> av.avg(x -> x.field("payDuration")))))
            .build();

    SearchResponse<Void> response = client.search(request, Void.class);
    // 解析聚合结果
    return parseAggregations(response);
}

用法三：日志检索（ELK 场景）

/**

 * 日志检索：时间范围 + 关键字 + 排除噪音 + 采样。
 * 关键点1：日志必须按天/按月分索引，否则单个索引文档数爆炸
 * 关键点2：traceId 精确匹配用 term，消息内容模糊用 match
 * 关键点3：大范围查询要加采样或限流
 */
public SearchResponse<LogDoc> searchLog(LogQuery query) {
    return client.search(s -> s
            .index("app-log-*")                      // 通配符匹配所有日志索引
            .query(q -> q.bool(b -> b
                    .filter(f -> f.range(r -> r.field("@timestamp")
                            .gte(JsonData.of(query.getFrom()))
                            .lte(JsonData.of(query.getTo()))))
                    .must(m -> m.queryString(qs -> qs
                            .query(query.getKeyword() + "*")
                            .defaultField("message")))
                    .mustNot(mn -> mn.term(t -> t.field("level").value("DEBUG")))))
            .sort(s -> s.field(f -> f.field("@timestamp").order(SortOrder.Desc)))
            .size(100)
            .trackTotalHits(t -> t.enabled(true)),
            LogDoc.class);
}

4.1 Redis 分布式锁（Redisson）

🗣 人话：分布式锁就是「多个机器抢一把钥匙，谁拿到谁干活」。手写 SETNX 有坑：① 没设过期时间会死锁；② 到期释放前业务没执行完锁就没了（删了别人的锁）；③ 释放锁时删错了别人的锁。Redisson 用 Lua + 看门狗把这些都解决了。

/**

 * Redisson 分布式锁。
 * 关键点1：tryLock(waitTime, leaseTime, unit) —— waitTime 是等待时间，leaseTime 是自动释放时间
 * 关键点2：不想传 leaseTime 就用 tryLock(waitTime, unit)，Redisson 会启动看门狗每 10s 续期
 * 关键点3：业务必须在 try 块里，finally 里解锁
 */
@Service
@RequiredArgsConstructor
public class StockService {

    private final RedissonClient redissonClient;
    private final StockMapper stockMapper;

    public boolean deduct(Long skuId, int quantity) {
        RLock lock = redissonClient.getLock("stock:lock:" + skuId);
        try {
            // 关键点2：等待 3 秒，拿到锁后自动续期
            if (!lock.tryLock(3, TimeUnit.SECONDS)) {
                return false;   // 抢不到锁，交给上层重试或降级
            }
            try {
                // 关键点3：真正的扣减要原子，用 SQL 条件更新而不是先查后改
                int rows = stockMapper.deductIfEnough(skuId, quantity);
                return rows > 0;
            } finally {
                // 只有当前线程持有才解锁，防止误解别人的锁
                if (lock.isHeldByCurrentThread()) {
                    lock.unlock();
                }
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return false;
        }
    }
}

-- 关键：原子扣减的正确写法，靠数据库保证，不靠 Redis
UPDATE t_stock
   SET stock = stock - #{quantity}
 WHERE sku_id = #{skuId} AND stock >= #{quantity};

Redisson 锁的坑：

坑 说明 解决
看门狗续期 默认 30s 过期，每 10s 续期到 30s 正常；但服务挂掉锁最多 30s 后释放
锁粒度 按 skuId 加锁，不同 sku 互不阻塞 粒度别太粗（别锁整张表）
Redisson 集群 用的是 Redis 集群的分布式锁，不是单机 主从切换时锁安全性依赖 Redis 自身的持久化配置
误用 lock() 无限等待，会把线程池耗尽 生产必须用 tryLock 带超时

/**

 * Sentinel 限流：QPS 模式。
 * 关键点1：@SentinelResource 的 value 是资源名，blockHandler 处理限流
 * 关键点2：fallback 处理业务异常，blockHandler 处理限流异常，两者都要配

@Service
public class OrderService {

    @SentinelResource(
            value = "createOrder",
            blockHandler = "createOrderBlocked",     // 限流/熔断时走这里

            blockHandlerClass = OrderService.class,
            fallbackClass = OrderService.class)

        return doCreateOrder(userId, skuId);
    }

    /** 限流处理：返回友好提示 + 埋点告警 */
    public OrderResult createOrderBlocked(Long userId, Long skuId, BlockException ex) {

4.4 Seata AT 模式：分布式事务

🗣 人话：Seata AT 帮你自动"撤销"操作。改数据前拍张照（before image），改完提交时如果失败了，用照片把数据改回去。它靠全局锁保证并发安全——改的行在事务结束前别人不能改。

/**

 * Seata AT 模式：全局事务入口。
 * 关键点1：@GlobalTransactional 标在「事务发起方」
 * 关键点2：每个参与方（写库的操作）都要有 undo_log 表
 * 关键点3：多个 @GlobalTransactional 不能嵌套（会冲突）
 */
@Service
@RequiredArgsConstructor
public class OrderTransactionService {

    private final OrderMapper orderMapper;
    private final AccountMapper accountMapper;
    private final InventoryMapper inventoryMapper;

    /**
     * 关键点2：这个方法里的所有 DB 操作都是全局事务的一部分，
     * 任一失败，全局回滚
     */
    @GlobalTransactional(name = "order-create-tx", rollbackFor = Exception.class)
    public void createOrder(OrderDO order) {
        // 1. 建单
        orderMapper.insert(order);
        // 2. 扣库存
        inventoryMapper.deduct(order.getSkuId(), order.getQuantity());
        // 3. 扣账户余额
        accountMapper.deductBalance(order.getUserId(), order.getAmount());
        // 4. 调用远程服务（如果远程服务也接了 Seata，同样加入全局事务）
        // remoteInventoryService.deductWithTx(...);
    }
}

-- 关键：每个参与全局事务的库都要建 undo_log 表
CREATE TABLE `undo_log` (
  `branch_id`     BIGINT       NOT NULL COMMENT '分支事务 ID',
  `xid`           VARCHAR(128) NOT NULL COMMENT '全局事务 ID',
  `context`       VARCHAR(128) NOT NULL COMMENT '上下文（序列化方式等）',
  `rollback_info` LONGBLOB     NOT NULL COMMENT '回滚信息',
  `log_status`    INT          NOT NULL COMMENT '状态 0=正常 1=防悬挂标记',
  `log_created`   DATETIME(6)  NOT NULL,
  `log_modified`  DATETIME(6)  NOT NULL,
  UNIQUE KEY `ux_undo_log` (`xid`, `branch_id`)
) ENGINE=InnoDB;

AT 模式的三个限制（必背）：

  1. 隔离性不是真正的隔离：靠全局锁（行级）在事务期间锁住被修改的行，所以是"读未提交"级别的隔离
  2. 只支持关系型数据库：不支持 MongoDB、Redis 等
  3. 不能有非 SQL 副作用：AT 靠解析 SQL 撤销，如果你在事务里发了 MQ、写了 Redis，回滚时不会撤销，必须用 TCC 或 Saga

TCC 模式（业务侵入但能力强）：

/**

 * TCC：Try 阶段预留资源，Confirm 确认，Cancel 取消。
 * 关键点1：每个服务都要实现三个接口
 * 关键点2：Confirm/Cancel 必须幂等（网络重试会导致重复调用）
 * 关键点3：空回滚（Cancel 先到）、幂等、悬挂（Try 后到）三个问题必须处理
 */
public interface InventoryTccService {
    void tryDeduct(String bizId, Long skuId, int qty);   // 冻结库存
    void confirmDeduct(String bizId);                     // 真正扣减
    void cancelDeduct(String bizId);                     // 解冻
}

AT vs TCC vs MQ 最终一致：

AT TCC MQ + 本地消息表
代码侵入 低（加注解） 高（写三个方法） 中
隔离性 低（全局锁） 高（业务自己控制） 无（最终一致）
性能 好（无额外 RPC） 差（多次 RPC） 好
适用 关系库、同构服务 异构、要强一致 大多数场景（推荐）

五、中间件高频面试题 30 道（带答案）

🗣 人话版：这 30 道是中间件板块最常被问的。答案按「结论 → 原理 → 项目里的做法 → 代价」四段写，背这个结构比背句子管用。每道都标了 ★（必问）和 ⚠（高频追问）。

MQ 类（15 题）

MQ-1 ★ 三种 MQ 怎么选？为什么你项目用 RocketMQ？

🗣 人话：选型看四件事——量多大、要不要延迟/事务消息、团队会不会运维、业务能不能容忍最终一致。别说什么都能干，选型是取舍。

要点：

  • RocketMQ：电商交易首选。原生支持事务消息、延迟/定时消息（18 档 + 5.x 任意时间）、分级重试 + 死信队列、消息轨迹（能查一条消息的收发链路，排查问题救命）、顺序消息（QueueSelector）。吞吐百万级。
  • Kafka：吞吐最高（千万级），顺序写 + 零拷贝 + 批量。但延迟消息、事务消息、重试死信、消息轨迹都弱，topic 多了性能下降。适合日志/埋点/流计算/CDC 数据管道。
  • RabbitMQ：路由能力最强（Exchange 四种类型：direct/fanout/topic/headers），延迟低，但堆积能力弱（百万级就吃力）。适合复杂路由、中小规模业务解耦。
  • 你的项目：订单履约、支付回调 → RocketMQ（要延迟关单、要事务消息、要消息轨迹）；门店操作日志 → Kafka 或 ELK；如果公司已有 MQ 基建，跟着公司走（这是加分点：懂成本）。

MQ-2 ★ 消息为什么会丢？三段式怎么保证不丢？

🗣 人话：一封信要送到，三关都得守住——发的确认寄出去了、邮局确认入箱了、收的人确认拆开了。少一关都可能丢。

要点：

  1. 生产端：syncSend 同步发送 + 检查 sendStatus == SEND_OK + 失败重试（retry-times-when-send-failed）。不能用 sendOneWay（完全不等确认）。
  2. Broker 端：同步刷盘 flushDiskType=SYNC_FLUSH + 同步复制 haMasterAddress（SYNC_MASTER）+ 主从。异步刷盘断电会丢。
  3. 消费端：手动 ACK，业务处理成功才提交 offset；异常必须抛出（吞异常 = 消息丢了）。
  4. 兜底：本地消息表 + 定时对账（业务数据和消息表同事务落库，定时任务扫描发送 + 对账补偿）。这是"不丢"的最后一道防线。

MQ-3 ★ 为什么一定会重复消费？幂等怎么做？

🗣 人话：MQ 的语义是 at least once（至少一次），宁可多送绝不漏送，所以重复是必然的不是意外。你要在消费端解决。

要点：

  • 重复原因：网络抖动（ACK 丢了）、消费端宕机（处理完没提交 offset）、Rebalance（未 ACK 的消息分给新消费者）、重试机制、生产端超时重试。
  • 方案（按可靠性）：
  • DB 唯一索引（首选，靠数据库兜底）：UNIQUE(biz_id, biz_type)，插入冲突即重复。
  • 状态机：UPDATE ... WHERE status='待支付' 受影响 0 行 = 已处理过，天然幂等。
  • Redis SETNX（快，但不能先占位后处理——业务失败消息会被吞；必须业务成功后再写 key）。
  • 乐观锁/version。
  • 反面案例（要能说）：只靠 Redis 去重 + 主从异步复制 → 主从切换丢 key → 幂等失效。

MQ-4 ★ 消息堆积了怎么办？

🗣 人话：先搞清楚为什么堆——消费者挂了、变慢了、流量突增、还是毒消息一直重试。然后临时加消费者，最后要能从根上防。

要点：

  • 定位：mqadmin consumerProgress -g GROUP 看 DIFF 列（堆积量）；消费端埋点看耗时和成功率。
  • 止血（优先级）： 1. 临时扩容消费者（注意上限：Kafka 消费者数 ≤ 分区数，RocketMQ ≤ 队列数） 2. 提升单条效率（异步化、批量写 DB、把非关键逻辑后置） 3. 降级（消息转存临时 topic/DB；丢弃日志类消息） 4. 跳过积压（resetOffsetByTime，应急，会丢消息） 5. 事后补偿（对账补齐）
  • 预防：lag 监控告警、消费超时、消费端熔断（下游挂了不能拖死整个 topic）、毒消息进 DLQ 后告警。

MQ-5 ★ 怎么保证消息顺序？

🗣 人话：全局有序等于单线程消费，吞吐直接废。实际只要同一个订单有序——同 key 同队列同线程。

要点：

  • 全局顺序 = 单队列单消费者，吞吐极低，一般不做。
  • 局部顺序（同订单/同用户）：RocketMQ 用 MessageQueueSelector 按业务 key 选队列 + ConsumeMode.ORDERLY；Kafka 用相同 key hash 到同一 partition + 单消费者单线程。
  • 坑：① 顺序消费时一条卡住会阻塞整个队列 → 必须配消费超时；② 扩队列数会破坏已有映射，生产环境队列数一次定好；③ 用订单号 hash 会有数据倾斜 → 二次 hash 打散。

MQ-6 ★ RocketMQ 事务消息的原理？为什么还需要对账？

🗣 人话：先发一条「半消息」（消费者看不见），执行本地事务，成功了才转成真消息；中途挂了 Broker 会回来问「你那事成没成」。就是为了让「改库」和「发消息」要么都成要么都不成。

要点：

  • 流程：发半消息（half message，不投递）→ 执行本地事务 → 返回 COMMIT/ROLLBACK → 没回复时 Broker 回查 checkLocalTransaction → 决定提交或回滚。
  • 解决什么：本地事务与发消息的原子性。
  • 局限（必答）：回查最多 15 次；回查有延迟（默认 6s 起）；回查依赖业务数据可查（要有唯一键）；不解决跨异构系统。
  • 所以：任何方案都要对账兜底。事务消息 + 本地消息表是同一个思路的两面。

MQ-7 ★ 延迟消息怎么做？订单 30 分钟未支付关单？

🗣 人话：发一条 30 分钟后才被消费的消息，消费时查一下订单状态——没付款就关掉。

要点：

  • RocketMQ 4.x：固定 18 个延迟级别（1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h），level=14 是 30 分钟。
  • RocketMQ 5.x：支持任意时间点的定时消息（精度毫秒）。
  • RabbitMQ：TTL + 死信队列（有队头阻塞问题）或延迟插件。
  • Kafka：原生不支持，要自建时间轮 / 多级 topic。
  • Redis ZSet：score 存到期时间戳，轮询 + 分布式锁抢任务。灵活但数据在内存。
  • XXL-Job 扫表：最土但最可靠，可查可补偿。
  • 生产推荐：MQ 延迟消息做主路径 + 定时扫表做兜底。理由：MQ 延迟消息在极端情况（脑裂、误删）可能不触发，扫表是最后保险。
  • 消费端铁律：消费时必须再查一次 DB 状态——用户 29:59 付款，30:01 关单消息到，不能误关。

MQ-8 ★ RocketMQ 的事务消息和 Seata 有什么区别？

🗣 人话：Seata 是「全程锁着，改完一起提交」，强一致但慢；MQ 事务消息是「先发信后做事，中间靠回查补」，最终一致但快。

要点： | | RocketMQ 事务消息 | Seata AT | |---|---|---| | 一致性 | 最终一致 | 准强一致（隔离性靠全局锁） | | 侵入性 | 低（加 TransactionListener） | 低（加 @GlobalTransactional） | | 性能 | 好 | 较差（全局锁会阻塞） | | 跨异构 | 不支持（只管自己的库） | 不支持 | | 适用 | 异步链路、削峰 | 同步核心链路 |

选型原则：核心链路（下单扣库存）要强一致 → Seata；非核心可补偿（通知、积分、日志）→ MQ 事务消息。

MQ-9 ★ Kafka 的消费者组和分区是什么关系？为什么消费者比分区多没用？

🗣 人话：分区像货架格子，一个消费者组一次只能占一个格子。货架有 5 格，派 8 个人来，多出来的 3 个只能站着看。

要点：

  • 一个分区同一时刻只能被组内一个消费者消费（保证分区内有序）。
  • 消费者数 > 分区数 → 多出来的空转，CPU 高但无产出，Rebalance 还会更频繁。
  • 想提高消费能力 → 加分区（但会破坏 key 的分区映射，慎改）+ 加消费者。
  • Rebalance 危害：消费暂停（stop the world）+ 可能重复消费 + 频繁 GC。优化：session.timeout（心跳检测）、max.poll.records（单批拉取量，配合 max.poll.interval.ms）、cooperative-sticky 增量 Rebalance 策略。

MQ-10 ⚠ RocketMQ 和 Kafka 在存储上的本质区别？

🗣 人话：RocketMQ 顺序写一个大文件，Kafka 也是顺序写大文件，但 Kafka 是每个分区一个文件，RocketMQ 是所有消息共用一个 CommitLog。

要点：

  • RocketMQ：所有 Topic 的消息写进同一个 CommitLog（顺序写，磁盘 IO 友好）；消费时通过 ConsumeQueue（逻辑队列，存消息在 CommitLog 的物理偏移）来定位。一条消息在 CommitLog 只存一份，各队列只存索引。
  • Kafka：每个 Partition 一个独立文件（.log + .index），消息在分区内顺序追加。
  • 后果：RocketMQ 扩队列不影响存储（只是多一份索引）；Kafka 扩分区会改变 key 的分布，且老分区数据不会自动迁移。

MQ-11 ⚠ 消费端异常该怎么处理？为什么不能 catch 住所有异常？

🗣 人话：能重试的异常要抛出去让 MQ 重试，不能重试的（脏数据）要跳过不然会卡死队列。

要点：

  • 不 catch 异常 → MQ 认为消费失败 → 按重试策略重投 → 超过 maxReconsumeTimes 进死信队列（DLQ）。
  • catch 住不抛 → MQ 认为消费成功 → 提交 offset → 消息永久丢失。这是最危险的写法。
  • 区分异常类型：
  • 可重试（下游超时、DB 抖动）：抛异常，让 MQ 重试。
  • 不可重试（参数非法、数据格式错、幂等命中）：记录日志 + 标记成功跳过，否则一条毒消息能卡住整个队列。
  • 注意：用 catch(Exception e) 全兜住是最常见的错误姿势。

MQ-12 ⚠ 你怎么排查「消息丢了」？

🗣 人话：先定位丢在哪一段——是发送端没发出去、Broker 没存住、还是消费端吞了。消息轨迹是最快的手段。

要点（标准排查流程）：

  1. 确认消息有没有发出去：查 mq_send_log / 本地消息表有没有这条记录、状态是什么。
  2. 查消息轨迹：mqadmin traceMsgById -n ns -i MSG_ID → 能看到从哪个 Broker 哪个队列发出、被哪个消费者消费、消费结果。RocketMQ 这招能省一半时间。
  3. Broker 侧：topicStatus 看队列分布和消费进度；consumerProgress 看 lag 和消费位点。
  4. 消费侧：查消费日志里有没有这条 msgId；查 DLQ 里有没有（viewMsgById -t %DLQ%GROUP_xxx）。
  5. 对账：定时任务比对 DB 业务数据与消费记录，这是最终裁判。

MQ-13 ⚠ 消息重复消费了几万次，怎么排查？

🗣 人话：先看是「同一条消息重复」还是「很多条消息都重复」——前者是幂等问题，后者是消费端异常（比如处理失败一直重试）。

要点：

  • 同一条重复 → 幂等没做对。检查：幂等键是不是错的（用了随机 UUID 而不是业务 ID）、幂等记录业务失败后没删、幂等和业务不在一个事务。
  • 很多条重复 → 消费端有问题：某条消息处理抛异常但被 catch 住还返回成功、下游超时但实际已执行、消费端 Rebalance 频繁（心跳超时，会把正在处理的消息重投）。
  • 排查命令：看该 msgId 的消费次数（轨迹里能看到）、看消费者日志里同一 msgId 出现次数、看 consumerProgress 的 DIFF 是否异常大。

MQ-14 ⚠ 消息队列和分布式事务有什么区别？什么场景必须用分布式事务？

🗣 人话：分布式事务是「一起成或一起败」，消息队列是「最终会对上」。前者慢但准，后者快但要兜底。

要点：

  • 分布式事务：跨资源操作需要原子性，如订单 + 库存 + 账户余额必须同时成功。方案：Seata AT（侵入低、有全局锁）、TCC（侵入高、无锁）、XA（性能差）。
  • 消息队列：最终一致。靠「本地消息表 + 重试 + 幂等 + 对账」达成。
  • 必须用分布式事务的场景：金融扣款、库存强一致、余额不能出现中间态。
  • 可以不用：通知类（发短信）、积分赠送、日志上报、缓存刷新——这些失败可以补偿。
  • 面试金句：「能用最终一致解决的，不要上分布式事务；分布式事务是把一致性换成了复杂度和性能成本。」

MQ-15 ⚠ 消息队列引入了哪些新问题？你怎么权衡？

🗣 人话：MQ 不是银弹，用它要付出：系统复杂度上升、一致性问题、运维成本、排查链路变长。

要点：

  • 四个代价：① 重复消费 ② 消息丢失 ③ 顺序错乱 ④ 堆积。
  • 额外代价：排查难度上升（一个请求横跨多个服务）、数据一致性窗口（写完立刻读可能不一致）、运维成本（监控、扩容、死信处理）。
  • 引入原则（要能说出来）：
  • 只把非核心、可补偿的环节异步化；核心链路（下单扣库存）不要为了"看起来高级"而异步。
  • 引入前先想清楚：如果 MQ 挂了，这笔业务怎么办？要有降级方案。
  • 中间件的引入成本 > 收益时不要引入。

ES 类（8 题）

ES-1 ★ 倒排索引是什么？为什么快？

🗣 人话：普通数据库是「翻到第几页看写了啥」，ES 是「先查词索引，直接告诉你哪几页有这个词」。

要点：

  • 正排 = 文档 → 词；倒排 = 词 → 文档列表（含位置、词频）。
  • 两层结构：
  • Term Dictionary（词典）：内存中，压缩为 FST（有限状态转换器），负责词 → 倒排表位置，查找 O(1)。
  • Posting List（倒排表）：磁盘上（.doc 文档ID、.tim 词频+位置），用跳表（SkipList）支持快速求交集。
  • 求交是核心：AND 查询 = 多个 posting list 求交，跳表让交集计算跳过大量元素。
  • 一句话：倒排索引把「查数据」变成了「查词」。

ES-2 ★ 为什么 ES 是"近实时"？写入流程是怎样的？

🗣 人话：写进去先放缓冲区并记日志，默认每秒刷一次生成新段，这时候才能被搜到——所以叫「近」实时。批量导入关掉刷新能快好几倍。

要点：

  • 流程：写 memory buffer + translog（防宕机丢）→ 每 1s refresh 生成新 segment（此时才可搜索）→ flush 落盘清 translog → 后台 merge 合并小 segment。
  • 关键参数：refresh_interval（批量导入时设 -1，导完手动 POST /_refresh，能快数倍）、translog.durability（request=每次都落盘，最安全；async=异步，性能好）。
  • merge 很吃 IO/CPU，要限流（indices.merge.max_num_threads）。
  • 结论：别用 ES 做实时强一致查询；写完立刻要读 → refresh=true（性能差）或直接读 MySQL。

ES-3 ★ 深分页为什么慢？怎么解决？

🗣 人话：from+size 是「每个分片都把前 N 条搬出来，协调节点再统一排序」，翻到第 1000 页等于搬了几十万条。

要点：

  • 原因：每个分片都要取 from+size 条，协调节点做全局排序 → 内存和 CPU 双爆。默认 index.max_result_window=10000。
  • 方案：
  • search_after（推荐）：用上一页最后一条的 sort 值当游标，实时、无深度限制。sort 字段必须唯一且有值（用 createTime + _id 组合）。
  • scroll：基于时间点快照，适合导出，导完必须 clear scroll。
  • PIT（Point In Time）：scroll 的升级版，避免导出期间数据变化导致重复/遗漏。
  • 限制最大页数、默认不支持跳页。
  • 别做：把 max_result_window 调成 10 万——那是把问题从「慢查询」变成「OOM」。

ES-4 ★ MySQL 和 ES 怎么同步？三种方案怎么选？

🗣 人话：双写最简单但容易不一致；发 MQ 解耦但要处理顺序和重复；Canal 订阅 binlog 最省心，业务代码一行不用改。

要点：

  • 方案对比： | | 一致性 | 侵入性 | 时延 | 适用 | |---|---|---|---|---| | 同步双写 | 弱 | 高 | 实时 | 简单场景 | | MQ 异步 | 最终一致 | 中 | 秒级 | 有 MQ 基建 | | Canal 订阅 binlog | 最终一致 | 零 | 秒级 | 推荐 | | 定时全量+增量 | 最终一致 | 零 | 分钟级 | 报表 |
  • Canal 链路：MySQL 开 binlog → Canal Server（伪装从库）→ 解析成 CanalEntry → 投递 MQ / 直写 ES。
  • 必须处理：全量初始化 + 增量追平、失败重试、删除同步、对账。
  • 幂等：用业务 ID 做 ES 文档 ID，重复写覆盖同一份，天然幂等。
  • 延迟问题：用户写完立刻搜不到 → 前端乐观更新，或搜索时先读主库回源。

ES-5 ★ 分片和副本怎么定？为什么不能改分片数？

🗣 人话：分片像把大表切成几块分开放，副本是每个分片的拷贝。分片数建索引时定死，之后改只能重建。

要点：

  • 分片数：单分片建议 20～50GB，最大 50GB。分片太多 → 集群元数据大、查询扇出慢；太少 → 单分片过大、恢复慢。
  • 副本数：生产至少 1。3 节点 → 1 主 1 副本（3 副本会因节点不足而 yellow）。副本数 ≥ 分片数会有一半分片没副本 → yellow。
  • 为什么不能改：分片数决定数据分布和路由，改了就等于数据重分布。方案：reindex（新索引 + 数据迁移 + alias 切换）或 split/shrink（有前置条件）。
  • 用 alias：业务代码访问 alias（order_index），切换时改 alias 指向新索引，应用无感知。

ES-6 ⚠ 字段类型 text 和 keyword 有什么区别？什么时候用哪个？

🗣 人话：text 会把内容切碎存（能模糊搜），keyword 原样存（能精确匹配和分组）。

要点：

  • text：分词，存倒排索引。用于全文搜索（商品标题、文章内容）。
  • keyword：不分词，整个值当一个 term。用于精确匹配（订单号、状态、用户 ID）、聚合分组、排序。
  • 标准做法：text + 子字段 keyword（title.keyword），既能搜又能精确匹配。
  • 大坑：聚合/排序的字段必须是 keyword 或数值类型（要有 doc_values）。把 status 建成 text → 聚合报错或很慢。
  • 中文分词：索引用 ik_max_word（细），搜索用 ik_smart（粗）。搜不到先查分词器和字段类型。

ES-7 ⚠ ES 集群红了/黄了怎么办？查询突然变慢怎么查？

🗣 人话：红 = 有主分片丢了（数据不完整），黄 = 副本没分配上（数据还在但不安全）。变慢先看是不是有大查询或 merge 风暴。

要点：

  • 查原因：_cluster/allocation/explain（直接告诉你为什么没分配），_cat/shards?v，_cat/nodes?v&h=name,heap.percent,cpu。
  • red：主分片没分配 → 立刻查节点是否掉线、磁盘是否满、是否有大量 unassigned shards。
  • yellow：副本没分配 → 节点数不足（3 节点放 2 副本就不够）、磁盘水位。生产可以接受 yellow（数据不丢），但要处理原因。
  • 查询变慢排查： 1. _tasks?actions=*search&detailed 找正在跑的大查询 → 杀掉 2. _cat/thread_pool/search?v 看线程池队列堆积 3. _cat/indices?v&s=store:desc 找大索引 → 检查 mapping 和分片数 4. _cat/segments?v 看 merge 是否堆积 5. 是不是深分页（from+size 大） 6. 是不是聚合范围太大（触发 circuit_breaking_exception）
  • 预防：慢查询日志 search.slowlog.threshold.query.warn=10s，索引模板设 ILM 生命周期。

ES-8 ⚠ 为什么不能把 ES 当数据库用？

🗣 人话：ES 强在搜，弱在存。它不保证事务、更新是覆盖式的（不是真正的更新）、默认数据 1 秒后才可见、不能当唯一数据源。

要点：

  • 无事务：只保证单文档操作原子，多文档操作没有 ACID。
  • 近实时：默认 1s 延迟，写完立刻读可能读不到。
  • 更新语义：是「删旧文档 + 加新文档」，文档 ID 相同才表现为覆盖，版本号会 +1。
  • 无 JOIN：跨索引关联要应用层拼装（ES 7.x 有 nested 和 join 字段，但都不是真 JOIN）。
  • 删除是标记：磁盘空间不立刻释放，要靠 merge 回收 → 大量删除要配合 ILM 重建索引。
  • 正确姿势：MySQL 是真相来源，ES 是查询视图。

其他中间件类（7 题）

OTHER-1 ★ 分布式锁怎么实现？Redisson 和手写 SETNX 的区别？

🗣 人话：手写 SETNX 有三个坑：没过期时间会死锁、到期释放前业务没做完锁就没了、释放时可能删了别人的锁。Redisson 用 Lua + 看门狗全解决了。

要点：

  • 手写 SETNX 三个必踩的坑： 1. SETNX 后没设过期 → 服务挂了锁永远不释放 → 必须用 SET key value NX EX 30 原子设置 2. 业务没执行完锁就过期 → 别人进来同时改数据 → 需要续期 3. 释放锁时 DEL 删掉了别人的锁 → 必须用 Lua 脚本比对 value 再删
  • Redisson 优势：
  • tryLock(waitTime, leaseTime, unit) 带超时
  • 看门狗自动续期（默认 30s 过期、每 10s 续期）
  • 解锁自动校验持有者（isHeldByCurrentThread）
  • 支持公平锁、读写锁、红锁（RedissonRedLock，多节点 Redis 场景）
  • 注意：Redisson 集群模式用的是 Redis 集群分布式锁，主从切换时的安全性依赖 Redis 持久化配置。
  • 根本解法：库存扣减这类最终必须靠 DB 的原子 SQL 兜底（UPDATE ... WHERE stock >= n），锁只是减少冲突。

OTHER-2 ★ Sentinel 的限流、熔断、降级有什么区别？

🗣 人话：限流是「不让你进太多」，熔断是「下游挂了直接不打了」，降级是「打不了就给个凑合的结果」。

要点：

  • 限流（FlowRule）：QPS 限流、并发数限流（线程池隔离）、热点参数限流（单个 userId 限 QPS）。资源名 + 阈值。
  • 熔断（DegradeRule）：按慢调用比例、异常比例、异常数触发。三个状态：Closed（正常）→ Open（熔断拒绝）→ Half-Open（试探）。
  • 降级：熔断/限流触发后返回兜底结果（默认数据、静态页、提示语）。
  • 区别：限流是主动按流量控制（下游还能扛，只是压力大）；熔断是被动发现下游不行了才断。
  • 降级设计原则：① 返回兜底数据 > 静态页 > 失败提示；② 降级路径绝不能再依赖故障的下游（否则故障扩散）；③ 降级要埋点告警。

OTHER-3 ★ Seata AT 模式的原理？为什么它能回滚？

🗣 人话：改数据前拍张照（before image），提交时如果失败了，用照片把数据改回去。它靠全局锁保证并发安全——被改的行在事务期间别人不能动。

要点：

  • 流程：① 解析 SQL 生成 before/after image → ② 校验 undo_log → ③ 写 undo_log → ④ 执行业务 SQL → ⑤ 提交；失败则读 undo_log 反向补偿。
  • 三个核心：
  • undo_log：记录回滚信息，每个参与方都要建表
  • 全局锁：事务期间锁住被修改的行（SELECT ... FOR UPDATE），防止其它事务读到脏数据
  • 默认隔离级别是「读未提交」（靠全局锁而非 MVCC 保证一致）
  • 三个限制：① 只支持关系型数据库；② 事务里的非 SQL 副作用（发 MQ、写 Redis）不会回滚 → 要用 TCC/Saga；③ 全局锁会影响并发。
  • 对比：AT 侵入低但有锁；TCC 无锁、性能好但要写三个方法且处理空回滚/幂等/悬挂。

OTHER-4 ★ Nginx 在架构里承担什么？和 Spring Cloud LoadBalancer 有什么区别？

🗣 人话：Nginx 在门口挡着（外部流量），LoadBalancer 在楼里调度（内部服务）。两个都要有。

要点：

  • Nginx 能做：反向代理、负载均衡（round-robin / least_conn / ip_hash / hash）、静态资源托管（不占 Tomcat）、限流（limit_req）、HTTPS 终结、灰度路由、gzip。
  • LoadBalancer 能做：服务间调用的负载均衡（@LoadBalanced + IRule），支持灰度/自定义路由规则（Nginx 做不到按用户标签路由）。
  • 区别：Nginx 在四/七层（L7 能看 URL），只认 IP+端口；LoadBalancer 在应用层，能读请求头做精细路由。
  • 两者都要配：Nginx 抗连接数，LoadBalancer 做服务发现后的精细调度。
  • 常见坑：proxy_read_timeout 不配（默认 60s）、client_max_body_size 默认 1m（上传失败）、上游没配 keepalive（TIME_WAIT 爆炸）。

OTHER-5 ★ 为什么 K8s 滚动更新会丢请求？怎么做优雅停机？

🗣 人话：K8s 杀 Pod 时，先发 SIGTERM，Spring Boot 默认立刻退出，在途请求就挂了。正确做法是先「告诉 K8s 别给我流量了」，再等一会儿。

要点：

  • 默认行为的问题：Spring Boot 收到 SIGTERM 后立即停止（server.shutdown=immediate），在途请求被切断。
  • 正确配置： 1. server.shutdown: graceful —— 开始优雅停机 2. spring.lifecycle.timeout-per-shutdown-phase: 30s —— 给 30s 处理在途请求 3. Nacos 主动注销（不等心跳超时，快速摘流量） 4. K8s preStop: sleep 30 —— 关键，等 K8s 把 Pod 从 Endpoints 摘掉（摘流量需要时间，否则优雅停机白配） 5. terminationGracePeriodSeconds: 60 —— 给足够时间
  • 面试金句：优雅停机配了没生效，90% 是因为少了 preStop 那几秒——K8s 摘流量比发 SIGTERM 慢，Pod 收到信号时流量还在进来。

OTHER-6 ⚠ 怎么设计一个「日志检索」功能？说说你对 ELK 的理解。

🗣 人话：应用把日志按 JSON 格式打出来，采集器搬到 ES，然后 Kibana 上按时间、关键字、traceId 查。

要点：

  • 链路：应用（结构化 JSON 日志）→ Filebeat（轻量采集，比 Logstash 省资源）→ Elasticsearch → Kibana。需要复杂清洗/多源聚合时才加 Logstash。
  • 三个关键设计： 1. 结构化输出：用 logstash-logback-encoder 输出 JSON，不要自己拼字符串（拼的没法聚合）。 2. 按天分索引：app-log-%{+yyyy.MM.dd}，别都写一个索引（ES 官方明确不建议超过 500GB/索引）。 3. traceId 贯穿：请求入口生成 traceId 打进所有日志，排查时按 traceId 一捞全链路。
  • 多行日志：Java 堆栈是多行，Filebeat 要配 multiline 合并，否则一条堆栈被拆成 20 条。
  • 生命周期：ILM 策略，热 3 天 → 温 7 天 → 删除 30 天后。
  • 与 SkyWalking 的区别：ELK 是日志检索，SkyWalking 是链路追踪（ APM），两者互补。

OTHER-7 ⚠ 你怎么保证「消息 + 数据库」的数据一致？本地消息表具体怎么实现？

🗣 人话：在同一个事务里，业务数据和一张消息表一起写进去；再有个定时任务每 5 秒扫没发出去的消息补发。业务成功消息就在，消息丢了也能补回来。

要点：

  • 核心：业务写库和写消息表在同一个本地事务里 → 要么都成功要么都失败。
  • 定时补发：扫描 status=INIT 的记录重发；成功标记 SUCCESS；失败累加重试次数，超过阈值告警。
  • 消费端幂等配套（DB 唯一索引）。
  • 对账兜底：定时任务比对「业务表该有的记录」和「消息表/消费记录」，差异告警。
  • 方案对比： | | 本地消息表 | RocketMQ 事务消息 | Seata AT | |---|---|---|---| | 一致性 | 最终一致 | 最终一致 | 准强一致 | | 侵入 | 中（多一张表） | 低 | 低 | | 额外依赖 | 无 | MQ | Seata Server | | 推荐场景 | 通用 | 已有 MQ | 强一致核心链路 |

60 秒面试话术：

「我们的订单链路是这样：下单时在同一个本地事务里写订单表和本地消息表，然后定时任务扫消息表发到 RocketMQ。这样做主要是为了解决本地事务和消息发送的原子性问题。

支付回调这块，我们用的是状态机——UPDATE t_order SET status='PAID' WHERE order_no=? AND status='WAIT_PAY'，靠受影响行数判断是不是重复回调。下游的积分、履约这些服务各消费一次，我们靠数据库唯一索引做最终幂等。

超时关单用了 RocketMQ 延迟消息做主路径，同时还有一个定时任务每 5 分钟扫一次超时订单兜底——因为极端情况下延迟消息可能不触发，扫表是最后一道保险。消费的时候我们会再查一次订单状态，避免把刚付的订单误关。

消息这块我们踩过几个坑：最早消费端 catch 住所有异常，导致消息静默丢失；后来改成可重试异常抛出、不可重试异常跳过加告警。还有就是毒消息卡队列，现在配了 maxReconsumeTimes 加上死信队列告警。」

查询流程：

@Service
@RequiredArgsConstructor
public class StoreSearchService {

    private final ElasticsearchClient esClient;
    private final StoreMapper storeMapper;
    private final RedisTemplate<String, Object> redisTemplate;

    /**
     * 搜索门店：ES 检索 + 结果聚合 + Redis 缓存热门查询。
     */
    public PageResult<StoreDoc> search(StoreQuery query) {
        // 关键点1：热门查询走 Redis 缓存（避免重复的 ES 查询打满集群）
        String cacheKey = "search:store:" + DigestUtils.md5Hex(JSON.toJSONString(query));
        List<StoreDoc> cached = redisTemplate.opsForList().range(cacheKey, 0, 19);
        if (cached != null && !cached.isEmpty()) {
            return new PageResult<>(cached, query.getTotal());
        }

        BoolQuery.Builder bool = new BoolQuery.Builder();
        if (StringUtils.hasText(query.getKeyword())) {
            bool.must(m -> m.multiMatch(mm -> mm
                    .query(query.getKeyword())
                    .fields("name^3", "address^2", "tags")));
        }
        if (query.getCityCode() != null) {
            bool.filter(f -> f.term(t -> t.field("cityCode").value(query.getCityCode())));
        }

        SearchRequest request = new SearchRequest.Builder()
                .index("store_index")
                .query(q -> q.bool(bool.build()))
                .sort(s -> s.field(f -> f.field("_score").order(SortOrder.Desc)))
                .from(query.getPage() * query.getSize())
                .size(query.getSize())
                .highlight(h -> h.fields("name",
                        f -> f.preTags("<em>").postTags("</em>")))
                .build();

        SearchResponse<StoreDoc> response = esClient.search(request, StoreDoc.class);

        List<StoreDoc> docs = response.hits().hits().stream()
                .map(Hit::source).collect(Collectors.toList());

        // 关键点2：热门查询结果缓存 5 分钟
        if (query.getKeyword() != null && query.getKeyword().length() >= 2) {
            redisTemplate.opsForList().rightPushAll(cacheKey, docs);
            redisTemplate.expire(cacheKey, Duration.ofMinutes(5));
        }
        return new PageResult<>(docs, response.hits().total().value());
    }
}

「搜索这块我们用 MySQL + ES 的组合。MySQL 是真相来源，ES 是查询视图。同步用的是 Canal 订阅 binlog，业务代码完全无侵入，秒级延迟。

索引设计上吃过亏——最早把 status 字段建成 text 类型，做聚合分组的时候直接报错；而且中文搜索搜不到，排查下来是分词器的问题。现在是 title 用 ik_max_word 索引、ik_smart 搜索，同时冗余一个 title.keyword 子字段，status 这些做精确匹配的字段统一用 keyword。

深分页我们没用 from+size，因为翻到后面会拖垮集群，现在用 search_after 加游标。导出用 scroll，但记得导完要 clear。

另外我们在 ES 前面加了一层 Redis 缓存热门查询词，因为发现很多用户搜的是同样的词，重复打 ES 收益很低。」

案例三：库存扣减与超卖（Redis + Redisson + DB 兜底 + Sentinel）

完整方案：

@Service
@RequiredArgsConstructor
public class InventoryService {

    private final RedissonClient redissonClient;
    private final StockMapper stockMapper;
    private final RedisTemplate<String, Integer> redisTemplate;

    /**
     * 扣库存：Redis 预扣 + DB 原子扣减（两道防线）。
     */
    public DeductResult deduct(Long skuId, Long userId, int quantity, String requestId) {

        // 【第一道】Redis 预扣，快速失败
        String stockKey = "stock:" + skuId;
        // 关键点：Lua 脚本保证「判断 + 扣减」原子
        Long result = redisTemplate.execute(new DefaultRedisScript<>(DEDUCT_LUA,
                Long.class), Collections.singletonList(stockKey),
                String.valueOf(quantity));

        if (result == null || result == 0L) {
            return DeductResult.fail("库存不足");
        }

        try {
            // 【第二道】DB 原子扣减（最终真相）
            // 关键点：这里不用 Redis 锁也可以，因为 SQL 本身就是原子的
            int rows = stockMapper.deductIfEnough(skuId, quantity);

            if (rows == 0) {
                // DB 说不够（Redis 数据过期/不一致），回补 Redis
                redisTemplate.opsForValue().increment(stockKey, quantity);
                return DeductResult.fail("库存不足");
            }

            // 关键点：扣减成功后发 MQ，异步创建流水/通知下游
            // 这里用本地消息表保证「扣库存」和「发消息」一致
            messageLogService.save(DeductMessageLog.of(requestId, skuId, quantity));

            return DeductResult.success();

        } catch (Exception e) {
            // DB 异常，回补 Redis
            redisTemplate.opsForValue().increment(stockKey, quantity);
            throw e;
        }
    }

    /** Lua 脚本：判断库存 + 扣减，原子执行 */
    private static final String DEDUCT_LUA =
            "local stock = tonumber(redis.call('GET', KEYS[1])) " +
            "if stock == nil then return 0 end " +
            "if stock < tonumber(ARGV[1]) then return 0 end " +
            "redis.call('DECRBY', KEYS[1], ARGV[1]) " +
            "return 1";
}

面试话术：

「超卖这个问题我们分两层解决。Redis 预扣是快路径，用 Lua 脚本保证判断和扣减的原子性，秒级返回，绝大部分请求在这里就结束了。

但 Redis 不是真相——它会过期，主从切换也可能丢数据。所以下面还有一道 DB 原子扣减：UPDATE t_stock SET stock = stock - ? WHERE sku_id = ? AND stock >= ?，靠这条 SQL 保证最终不会超卖。Redis 扣成功但 DB 扣失败的情况，用 Lua 回补 Redis。

我们不用 Redis 分布式锁来兜底，因为 DB 的原子 SQL 已经够了，加锁反而多一层复杂度和故障点。不过在活动开始瞬间我们用 Redisson 锁做了预热，避免大量并发同时打 DB。

还有一个细节是幂等：同一个 requestId 重复提交要返回第一次的结果，我们用 requestId 做流水表的唯一索引。」

/**

 * 应用内埋点：慢请求日志（比 APM 轻，排查时最实用）。
 * 关键点1：超过阈值才打印，避免日志刷屏
 * 关键点2：必须带 traceId，否则查到日志也不知道是哪个请求
 */
public class SlowRequestFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse resp,
                                    FilterChain chain) throws ServletException, IOException {
        long start = System.currentTimeMillis();
        try {
            chain.doFilter(req, resp);
        } finally {
            long cost = System.currentTimeMillis() - start;
            if (cost > 1000) {
                log.warn("慢请求 uri={} cost={}ms traceId={} params={}",
                        req.getRequestURI(), cost,
                        MDC.get("traceId"), Arrays.toString(req.getParameterMap().values().toArray()));
            }
        }
    }
}

三个最容易忽略但很加分的地方

  1. 每讲一个中间件，一定要说它的"代价"

    「用 MQ 换来了解耦和削峰，代价是引入了重复、丢失、乱序、堆积这四个问题，所以我们做了 XXX 保证。」

这句话一说出来，面试官立刻知道你不是只会用，是真的踩过坑。

  1. 每讲一个方案，一定要说"为什么不用另一种"

    「ES 同步我们没用双写，因为双写在业务代码里要管 ES 写失败，耦合度高还容易不一致；也没用 MQ，因为要业务代码配合；最后选 Canal，因为它对业务零侵入，而且天然按 binlog 顺序。」

有对比才有判断力。

  1. 一定要有一个"出过事"的完整故事

    「我们曾经出过一次消费端把异常全 catch 住的问题，表现为订单状态一直不流转，排查了半天才定位到是异常被吞了。之后我们改了异常分类处理策略，还加了死信队列告警。」

E. 面试前最后 5 分钟扫一遍

□ MQ 不丢三段式：生产端检查 SendStatus / Broker 同步刷盘+同步复制 / 消费端手动 ACK
□ 幂等：DB 唯一索引 + 状态机；SETNX 不能先占位后处理
□ 顺序：同 key 同队列 + ORDERLY；扩队列会破坏映射
□ 延迟：MQ 定时消息（主）+ 定时扫表（兜底）；消费时再查一次状态
□ 事务消息：半消息 → 本地事务 → COMMIT/ROLLBACK → 回查最多 15 次 → 必须对账
□ 堆积：先定位原因，再扩容（≤ 分区数）、提速、降级、跳过、补偿
□ ES 倒排：词 → 文档列表；FST 在内存 + Posting List 用跳表
□ ES 近实时：1s refresh 生成 segment 才可搜
□ ES 深分页：search_after（推荐）/ scroll（导出）+ clear
□ ES 同步：Canal 订阅 binlog（业务无侵入）；全量 + 增量 + 对账
□ ES 字段：text 分词 / keyword 精确；聚合排序字段必须 keyword
□ Redis 锁：SET NX EX + Lua 删锁 / Redisson tryLock + 看门狗
□ Seata AT：undo_log + 全局锁；只支持关系库；不撤销 MQ/Redis 副作用
□ Sentinel：限流主动、熔断被动、降级兜底；降级不能依赖故障下游
□ K8s 优雅停机：graceful + preStop sleep + 主动注销，少了 preStop 白配
□ 每个中间件都要能说出「代价」和「为什么不用另一种」
