一、Java 基础与语言特性（10 题）

🗣 人话版：这章在问「这门语言的地基稳不稳」。String 为什么不能改、equals 和 hashCode 为什么要配套、泛型为什么运行时「标签就撕了」——面试官不是要你背定义，是要你说出不这么干会出什么事。

Q1 ★ String 为什么不可变？String s = "a" + "b" 创建了几个对象？

🗣 人话：字符串一旦造出来就是刻在石头上的字，改不了；想改只能重新刻一块。所以它能放心被共享、能当缓存 key 不怕被人偷偷改。至于 a+b：两边都是写死的常量，编译器当场就合成 ab，只造一个；是变量拼就在运行时拼，循环里拼串记得自己 new 个 StringBuilder。

要点：final char[]（JDK9 起 byte[] + coder 压缩）保证引用和内容都不可改，换来线程安全、可缓存 hash、字符串常量池复用、安全（类名/URL 不被篡改）。 字面量 "a"+"b" 编译期常量折叠，只留 "ab" 一个常量池对象；如果是变量拼接，JDK8 编译成 StringBuilder.append，JDK9+ 用 invokedynamic + StringConcatFactory，循环里拼串仍要用 StringBuilder 显式指定容量。

Q2 ★ == 与 equals、hashCode 的契约

🗣 人话：== 问「是不是同一个盒子」，equals 问「盒子里的东西一不一样」，hashCode 是盒子上贴的标签。两个东西相等，标签必须也相等，不然扔进 HashMap 就像放进不同抽屉，回头找不着。所以改了 equals 一定要顺手改 hashCode。

要点：== 比引用（基本类型比值）；equals 默认也是引用比较，需重写。 契约：equals 相等则 hashCode 必须相等，反之不成立。违反会导致 HashMap/HashSet 查不到（放在不同桶）。重写 equals 必须同时重写 hashCode，用 Objects.hash，注意 null 与浮点。

Q3 ★ 接口默认方法、抽象类怎么选？

🗣 人话：抽象类是「半成品老爹」，能存属性、有构造器，但一个儿子只能认一个爹；接口是「能力证书」，能考很多张。JDK8 给接口加默认方法，是给老接口补功能又不想让所有实现类跟着改——代价是两本证书有同名方法时，你得自己说清楚用哪本。

要点：抽象类单继承、可有状态和构造器；接口多实现、只能有 static final 常量（JDK9 后可 private 方法）。 选型：需要模板方法/共享状态用抽象类；需要能力扩展/多实现用接口。JDK8 默认方法是为了给老接口加方法不破坏实现类（如 Collection.stream()），代价是钻石继承冲突必须显式 Interface.super.method()。

Q4 重载与重写、静态绑定

🗣 人话：重载是「同名不同参数，编译时看你手里拿的什么类型就选哪个」；重写是「儿子把爹的方法重做一遍，运行时看实际是哪个儿子」。记一句就够：编译看左边，运行看右边。

要点：重载是编译期按静态类型选方法，重写是运行期按实际类型动态分派。经典坑：null 传参时选最具体的子类重载；父类引用调重载方法走父类版本。private/static/final 方法不能被重写。

Q5 ★ 泛型擦除带来了哪些限制？怎么绕过？

🗣 人话：泛型只是给编译器看的标签，进 JVM 之前标签就被撕了，运行时大家都叫 List。所以你不能问「这是不是 String 的 List」（问不出来），也不能 new 泛型数组。要拿真实类型，得靠别人把 Class 对象递给你——Jackson、MyBatis 都这么干。

要点：擦除到边界（无界 Object），运行期拿不到 T.class，因此不能 new T[]、不能 instanceof T、静态成员不能用 T、基本类型不能做参数（自动装箱）。 绕过：List<String> 与 List<Integer> 运行时同一个类 → 用 Class<T> 显式传入、TypeReference/ParameterizedType 解析（Jackson、MyBatis 都这么干）。桥接方法是编译器为协变生成的合成方法。

Q6 ★ 异常体系与 finally 的坑

🗣 人话：Error 是「天塌了」（比如内存没了），别接；Exception 分两种：编译器逼你处理的（受检）和运行时才炸的。finally 里千万别写 return，它会把 try 里的异常和返回值一起吞掉，这种 bug 能让人找一整天。

要点：Throwable → Error（OOM、StackOverflowError，不该 catch）/ Exception → 受检 IOException、非受检 RuntimeException。 坑：finally 里 return 会吞掉异常和返回值；try-with-resources 按逆序关闭且后关闭的异常会被 addSuppressed；finally 里抛异常覆盖原异常。

Q7 ★ 反射、动态代理、字节码增强的区别

🗣 人话：反射是「运行时掀开盖子看这个类有啥」；动态代理是「找个替身接活」；CGLIB 是「给你生个儿子，儿子在方法前后加料」。Spring 的 AOP 全靠后两个。替身有个死穴：你在类里自己叫自己，替身根本不知道。

要点：

  • 反射：运行期拿 Class 元信息，性能在 JDK8 后靠 MethodHandle/inflation 大幅优化，但仍有开销。
  • JDK 动态代理：基于接口，生成 $Proxy0 实现类，InvocationHandler 拦截；Spring AOP 默认。
  • CGLIB/ByteBuddy：继承生成子类，可代理无接口类，final 类/方法代理不了；Spring Boot 2.x 起默认 proxyTargetClass=true。 三者都是"不改进源码改行为"，AOP 选型要看是否有接口 + 调用是否走代理对象（自调用失效）。

Q8 ★ JDK 8 → 17/21 有哪些真用得上的特性？

🗣 人话：8 是分水岭（Lambda、Stream），11 是过渡，17 是现在最稳的选择，21 是虚拟线程。面试抓一句就够：升级主要图两样——GC 更省心、虚拟线程能把「干等 IO」的成本打下来。

要点：8（Lambda、Stream、Optional、CompletableFuture、新时间 API）→ 9（模块化、List.of）→ 11（var、HttpClient、ZGC 实验）→ 17（密封类、record、文本块、强封装 JDK 内部 API）→ 21（虚拟线程、switch 模式匹配、分代 ZGC、SequencedCollection）。 生产关注点：升级主要动机是 GC 与虚拟线程；record 适合 DTO；虚拟线程解决的是阻塞型 IO 的线程成本，不是 CPU 密集，且要小心 synchronized 钉住载体线程（JDK21 已缓解但仍建议 ReentrantLock）、连接池大小成为新瓶颈。

Q9 Optional 用错的典型场景

🗣 人话：Optional 是「可能没有」的盒子，只适合当返回值，提醒你别忘了判空。别拿它当字段、当参数，也别 isPresent()+get() 绕一圈——那不还是判空嘛。

要点：不要做字段/方法参数（不可序列化、增加调用方负担）、不要 isPresent()+get()（等于 null 判断）、不要 Optional.of(null)。正确用法是返回值表达"可能没有"，配合 map/flatMap/orElseGet 链式短路。

Q10 Stream 的惰性求值与并行流的坑

🗣 人话：Stream 像流水线，中间环节都不动手，只有最后一道工序才开工。而且一条流只能用一次，用完就废。parallelStream 听着爽，但它偷用公共线程池，会把别人正在干的活挤掉，IO 多的场景反而更慢。

要点：中间操作惰性、终止操作触发；流只能消费一次；parallelStream 默认用 ForkJoinPool.commonPool（并行度 = CPU-1），在 Web 容器里会抢占公共池、拖垮其他并行任务，且 ThreadLocal 在 worker 线程里拿不到。IO 密集或数据量小（<1w）别用并行流；要并行就自定义 ForkJoinPool。

二、集合框架（9 题）

🗣 人话版：HashMap 就是个抽屉柜：先算个位置把东西塞进去，位置撞了就在同一个抽屉里排队，队伍太长就改成树，柜子装到 3/4 就换个大柜子。这章只要记住三件事：怎么算位置、撞了怎么办、满了怎么办。

Q11 ★ HashMap 的 put 全过程（1.8）

🗣 人话：先按 key 算个座位号，空着就直接坐；有人了就看是不是同一个人（hash 一样、equals 也相等），是就顶掉；不是就排队；队伍超过 8 个且柜子够大，就改成树形排队；人超过容量的 3/4，就换个大柜子，所有人重新找座。

要点：hash(key) = h ^ (h>>>16)（高低位混合，减少碰撞）→ 桶为空直接放 → 否则比 hash 再比 equals，相同则覆盖 → 链表尾插 → 链表长度 ≥8 且数组长度 ≥64 才树化（否则先扩容）→ size > threshold(容量×0.75) 扩容翻倍。 扩容：容量 2 的幂，元素要么留在原位，要么移动 oldCap（hash & oldCap 判断），1.8 用 4 个指针拆成高低位两条链，避免 1.7 头插成环导致的 CPU 100%。

Q12 ★ 为什么容量是 2 的幂？负载因子 0.75？

🗣 人话：容量取 2 的幂，是为了把「取余」换成「按位与」，快得多，算出来的座位也更匀。0.75 就是「别太挤也别太浪费」的经验值——挤了老撞车，空了费地方。

要点：(n-1) & hash 等价取模但快得多，且 n-1 低位全 1 才能均匀分布；扩容时可用位运算判断高低位。 0.75 是空间与冲突的折中：泊松分布下 0.75 时链表长度 8 的概率约 6e-8；调低浪费空间、调高冲突剧增。

Q13 ★ ConcurrentHashMap 1.7 与 1.8 的差别

🗣 人话：1.7 是把柜子分成 16 个区，一区一把锁，不同区互不干扰；1.8 更细，谁的那个抽屉被动了就只锁抽屉头。所以同时写的人一多，1.8 几乎不打架。

要点：1.7 = Segment 分段锁（默认 16，继承 ReentrantLock），锁粒度是段；1.8 去掉 Segment，CAS + synchronized 锁单个桶头节点，锁粒度更细，size 用 baseCount + CounterCell[] 分散计数（类似 LongAdder）。 并发扩容：多线程协助 transfer，用 ForwardingNode 标记已迁移桶。get 无锁（volatile 读数组元素与 Node 的 val/next）。

Q14 ★ 为什么 HashMap 线程不安全？多线程下会怎样？

🗣 人话：1.7 多线程一起扩容会把队伍接成一个圈，之后谁来查都转圈转死，CPU 直接打满。1.8 不成环了，但照样会丢数据、size 算不准。要并发就直接用 ConcurrentHashMap，别硬扛。

要点：1.7 头插 + 并发扩容会形成环形链表，get 死循环打满 CPU；1.8 改成尾插避免成环，但仍会丢数据、size 不准、并发扩容互相覆盖。要并发就用 ConcurrentHashMap；Collections.synchronizedMap 是全表锁，只有需要原子复合操作（putIfAbsent/computeIfAbsent）时才体现价值。

Q15 ArrayList 扩容与 LinkedList 的真实差异

🗣 人话：ArrayList 是「一排连着的座位」，找第几个直接算地址；LinkedList 是「手拉手的一串人」，找第 100 个得一个个数过去。删中间元素 ArrayList 要挪座位，但整体还是它快——CPU 就喜欢连续内存。

要点：ArrayList 默认 10（首次 add 才分配），扩容 old + (old>>1)，用 Arrays.copyOf；LinkedList 是双向链表，get(i) 是 O(n)（会二分方向但仍线性）。 实践：99% 场景用 ArrayList（CPU 缓存友好、内存紧凑），LinkedList 只在频繁头尾增删做 Deque 时用。ArrayList 删除中间元素是 System.arraycopy 搬移，不是链表"更快"。

Q16 ★ fail-fast 与 fail-safe

🗣 人话：一边 foreach 一边删元素，等于一边点名一边把人拽走，点到后面就乱套，直接抛异常。要删就用迭代器的 remove 或 removeIf。CopyOnWriteArrayList 是「每次改都复制一份新的」，读的人永远不受影响，适合读多写极少。

要点：modCount 与期望值不一致抛 ConcurrentModificationException，foreach 中 remove 必炸。正确姿势：Iterator.remove()、removeIf、或用 CopyOnWriteArrayList（写时复制，读无锁，适合读多写极少，如监听器列表；写会全量复制，大集合禁用）。

Q17 TreeMap / LinkedHashMap 的用途

🗣 人话：TreeMap 是「永远排好序的字典」，找「比这个大的最近一个」特别顺手；LinkedHashMap 是「记得你摸过谁」的 HashMap，把 accessOrder 打开、重写一个方法，就是一个现成的 LRU。

要点：TreeMap 红黑树，按 key 排序，支持 floorKey/ceilingKey/subMap（做区间查询、排行榜同分处理很好用）；LinkedHashMap 哈希 + 双向链表，accessOrder=true + 重写 removeEldestEntry 就是现成的 LRU。

Q18 集合去重与排序的坑

🗣 人话：List 的 contains 是挨个问一遍，数据一多就慢，去重直接上 HashSet。TreeSet 判重看的是「比大小结果为 0」，不看 equals——两个东西 equals 不相等但比出来一样大，它就给你吞掉一个。Arrays.asList 只是套在原数组上的壳，加不了删不了。

要点：List.contains 是 O(n)，大批量用 HashSet；distinct() 依赖 hashCode/equals；TreeSet 去重看 compareTo 返回 0（和 equals 不一致会"莫名丢元素"）；Arrays.asList 返回定长视图，add 抛 UnsupportedOperationException；List.of 连 set 都不行且不接受 null。

Q19 大集合内存占用怎么优化？

🗣 人话：HashMap 里每个键值对都是一个对象还带包装，百万级很吓人。真要装百万级数字，用专给基本类型做的集合（fastutil），或者干脆别放内存。另外 subList 只是个「窗口」，它一直拽着整个大 List，大对象就回收不掉。

要点：HashMap 每个 Node 约 32B + 装箱对象；百万级 KV 优先考虑基本类型专用集合（fastutil/HPPC）或换存储（Redis/本地缓存）。Integer 缓存 -128~127，超出范围 == 不可靠。subList 是视图，持有原 List 引用，会导致大对象无法回收。

三、并发编程（16 题）

🗣 人话版：并发说白了就一句话：多个线程同时动同一份数据，会出三种乱子——看不见（可见性）、被插队（原子性）、顺序乱（有序性）。锁、volatile、CAS、线程池，全是在治这三种病。答题先说「我要治哪种病」，再说用什么药。

Q20 ★ JMM 与 happens-before

🗣 人话：JMM 全称 Java Memory Model，是一份「多线程读写共享变量时，你该看到什么」的规则书——注意，它不是堆、栈、元空间那套内存分区，那是 JVM 内存结构，两回事，别混。 规则书里就两个角色：主内存是公共黑板，工作内存是每个线程自己的小本本。线程改共享变量先记本上，什么时候抄到黑板、什么时候必须重新从黑板读，都由这本规则书管。 happens-before 就是其中最关键的几条「什么时候必须抄给对方看」的规定——它不是时间先后，是「我干完的事你一定看得见」。

要点：JMM 抽象出主内存 + 工作内存，解决可见性/有序性。happens-before 8 条规则中最常用的：程序次序、volatile 写先于读、synchronized 解锁先于加锁、Thread.start() 先于线程内、线程内先于 join() 返回、传递性。 注意：happens-before 不等于时间先后，它是"前一个操作的结果对后一个可见"的保证。

Q21 ★ volatile 到底保证了什么？不保证什么？

🗣 人话：volatile 就是「别记小本本，直接写黑板，读也从黑板读」，所以别人立刻看得见；它还拦着编译器和 CPU 别乱调顺序。但它管不了「两个人同时加一」——i++ 是读、加、写三步，中间照样能被插队。

要点：保证可见性（写后立即刷主存 + 读前失效本地副本）和禁止指令重排（内存屏障：写前 StoreStore、写后 StoreLoad；读后 LoadLoad/LoadStore）。 不保证原子性（i++ 三步：读-改-写）。典型用途：状态标志位、DCL 单例的 instance、ConcurrentHashMap 的节点可见性。AtomicInteger 用 CAS 解决原子性。

Q22 ★ synchronized 的锁升级

🗣 人话：一开始没人抢，锁就认住一个人（偏向锁）；有人来抢了，就变成 CAS 抢一下、短时间等着（轻量级）；抢的人多、等得久，就交给操作系统排队（重量级，要进内核，贵）。只能升不能降，因为降级本身就得先暂停。

要点：无锁 → 偏向锁（同一线程重入，Mark Word 记线程 ID；JDK15 起默认禁用、18 移除，因为撤销成本高）→ 轻量级锁（CAS 自旋抢 Mark Word，适合短临界区）→ 重量级锁（ObjectMonitor，entryList 等 OS 互斥量，涉及用户态/内核态切换）。 锁只能升不能降（除 STW 时可能降级）。synchronized 是非公平、可重入、不可中断。

Q23 ★ AQS 的核心设计

🗣 人话：AQS 就是「一个计数器 + 一条排队队伍」。state 表示「现在能不能进」，抢不到的进队列里 park 着睡，前一个出来时叫醒下一个。ReentrantLock、CountDownLatch、Semaphore 都是这套壳子，只是 state 的含义不一样。

要点：一个 volatile int state + CLH 双向队列（FIFO，节点 waitStatus）。tryAcquire/tryRelease 由子类实现（ReentrantLock 用 state 记重入次数）。 抢锁失败入队并 LockSupport.park()，释放时 unpark 后继。区分独占/共享模式（CountDownLatch、Semaphore 是共享）。Condition 用条件队列，await 释放锁并挂起，signal 转移到同步队列。

Q24 ★ ReentrantLock 与 synchronized 怎么选？

🗣 人话：synchronized 是自动门，进出自带；ReentrantLock 是手动门，能定时、能被叫停、还能开好几条队。平时用自动门省事，需要「等太久就算了」或者多条等待队列时才用手动门。虚拟线程场景优先手动门，免得卡住底层线程。

要点：ReentrantLock 多出：可中断（lockInterruptibly）、超时（tryLock(time)）、公平锁、多条件队列。synchronized 简单、JVM 持续优化、不会忘记释放。 实践：需要超时/中断/多 Condition（如阻塞队列的 notFull/notEmpty）用 Lock，否则用 synchronized。虚拟线程场景优先 ReentrantLock，避免 pinning。

Q25 ★ CAS 与 ABA

🗣 人话：CAS 是「我看一眼是 A，就把它改成 B，不是 A 就重来」——不用锁，但一直失败就空转烧 CPU。ABA 是「我走的时候是 A，回来还是 A，其实中间被人改成 B 又改回来了」，加个版本号就认得出来。LongAdder 是把一个计数器拆成很多份，各加各的，最后汇总。

要点：CAS = Unsafe.compareAndSwapInt，底层 lock cmpxchg（单核不加 lock 前缀）。三大问题：ABA（用 AtomicStampedReference 加版本号）、自旋开销（高竞争下 CPU 空转，用 LongAdder 分散热点）、只能保证一个变量（多变量用 AtomicReference 封装或加锁）。 LongAdder 用 Cell[] 分摊写竞争，sum() 非强一致，适合统计计数。

Q26 ★ 线程池 7 个参数与执行流程

🗣 人话：7 个参数就是「常驻几个人、最多几个人、闲多久裁人、排队的地方多大、怎么起名、满了怎么办」。干活顺序很反直觉：先招满正式工，再排队，队满了才招临时工，还满才拒绝。所以队列无界的话，临时工永远招不上来。

要点：corePoolSize / maximumPoolSize / keepAliveTime / unit / workQueue / threadFactory / handler。 流程：核心线程未满 → 建核心线程；否则入队；队列满 → 建非核心线程到 max；再满 → 拒绝策略（AbortPolicy 抛异常、CallerRunsPolicy 回退调用方天然限流、DiscardPolicy 静默丢、DiscardOldestPolicy 丢最老）。 ⚠ 追问：核心线程满了为什么先入队而不是先扩容（ThreadPoolExecutor 的设计是为了在低并发时控制线程数，代价是队列无界时 max 永远用不上）。所以要用有界队列，否则 max 形同虚设且会 OOM。

Q27 ★ 线程池参数怎么定？

🗣 人话：纯 CPU 的活，人多了反而抢 CPU，N+1 就够；等 IO 的活大家都在等，可以多放人，2N~4N 起步再压测调。关键不是背公式，是「核心业务单独一个池」，别让导出任务把下单接口的线程吃光。

要点：CPU 密集 ≈ N+1；IO 密集 ≈ N × (1 + 等待时间/计算时间)，常用 2N~4N 起步，靠压测收敛。 工程做法：核心业务独立线程池（隔离，避免互相拖垮）；用 ThreadPoolExecutor 手动创建（禁止 Executors.newFixedThreadPool：无界队列 OOM；禁止 newCachedThreadPool：max=Integer.MAX_VALUE 线程爆炸）；配 ThreadFactory 起有意义的名字 + UncaughtExceptionHandler；监控 activeCount/queueSize/completedTaskCount 打点到 Prometheus。

Q28 ★ 线程池里异常会吞掉吗？submit 和 execute 的区别

🗣 人话：execute 出异常会直接报出来；submit 把异常包进了 Future，你不 get 就永远不知道它炸了——这就是「任务悄悄失败」的经典原因。要么统一 try-catch 打日志，要么干脆别用 submit。

要点：execute 异常直达 UncaughtExceptionHandler；submit 包成 FutureTask，异常存进 outcome，不 get() 就永远看不到。这就是"任务静默失败"的常见原因。解决：包一层 try-catch 打日志，或统一用 execute。

Q29 ★ ThreadLocal 原理与内存泄漏

🗣 人话：ThreadLocal 是给每个线程发一个自己的储物柜：柜子上的名牌（key）可以被回收，但柜子里的东西（value）还锁着。线程池的线程不死，东西就一直堆着，于是泄漏。所以用完必须 remove，线程池里尤其要。

要点：每个 Thread 持有 ThreadLocalMap，key 是 ThreadLocal 的弱引用，value 是强引用。key 被回收后 entry 变 null key，value 无法访问但被线程持有 → 线程池里线程长期存活 → 泄漏。 必须 try/finally 里 remove()。InheritableThreadLocal 父子传递，但线程池复用会串数据，要用 TransmittableThreadLocal（阿里 TTL）。ThreadLocalRandom 用种子存在 Thread 里避免竞争。

Q30 ★ CountDownLatch / CyclicBarrier / Semaphore 区别

🗣 人话：CountDownLatch 是「等所有人都到齐再开饭」，只用一次；CyclicBarrier 是「几个人约好到齐了一起出发」，能反复用；Semaphore 是「门口发多少张票，同时只能进这么多人」。

要点：CountDownLatch 一次性、主线程等多个任务（await），state 减到 0 唤醒；CyclicBarrier 可循环、线程之间互相等，到齐执行 barrierAction；Semaphore 限流/限并发，acquire/release 可公平。 场景：批量并行查询用 Latch（配超时！否则一个慢请求拖死整个接口）、多阶段计算用 Barrier、接口限流/连接池用 Semaphore。

Q31 ★ CompletableFuture 常见用法与坑

🗣 人话：它就是「先把活派出去，回头再取结果」，还能让几个下游并行跑。两个坑：默认用的是公共线程池（IO 任务会互相挤），异常不 join 就没人知道。

要点：supplyAsync（默认 ForkJoinPool.commonPool，必须传自定义线程池）、thenApply（同步）/thenApplyAsync、thenCompose（串行依赖）、thenCombine（并行聚合）、allOf/anyOf、exceptionally/handle。 坑：不 join() 的异常静默丢失；allOf 要各自 exceptionally 兜底否则整体失败；默认池只有 CPU-1 个线程，IO 任务会排队。超时用 orTimeout（JDK9+）。

Q32 守护线程、线程状态与中断

🗣 人话：中断不是「掐死你」，是「递个纸条说该停了」，你爱停不停。sleep/wait 收到纸条会直接抛异常并把纸条收走，所以捕获之后要么继续往上抛，要么自己再举一次旗，别当没看见。

要点：6 状态 NEW/RUNNABLE/BLOCKED/WAITING/TIMED_WAITING/TERMINATED；BLOCKED 只针对 synchronized，LockSupport.park 是 WAITING。 中断是协作式：interrupt() 只设标志位，sleep/wait/join 会抛 InterruptedException 并清标志。捕获后要么继续抛，要么 Thread.currentThread().interrupt() 恢复标志，不要吞掉。

Q33 ★ 死锁的四个条件与排查

🗣 人话：两个人各拿一半东西，又都等对方手里那半，谁也不撒手。破法最简单的就是「大家按同一个顺序拿」。线上 jstack 一搜 Found one Java-level deadlock，谁等谁写得清清楚楚。

要点：互斥、占有且等待、不可抢占、循环等待。破坏任一即可（最常用：统一加锁顺序、tryLock 超时）。 排查：jstack <pid> 搜索 Found one Java-level deadlock，看线程持有的锁与等待的锁；jconsole/Arthas thread -b 也能直接定位阻塞其他线程的线程。

Q34 ★ 生产者-消费者，为什么用 while 而不是 if 判断条件？

🗣 人话：wait 醒来不等于条件就成立了（可能被别人先抢了，也可能是假醒），所以得用 while 再检查一遍——醒了先看看锅里还有没有。用 if 就会端着空锅往下走。

要点：wait() 可能虚假唤醒（spurious wakeup），被唤醒时条件不一定成立，必须 while 重新检查。必须在同步块内调用 wait，否则 IllegalMonitorStateException；wait 会释放锁，notify 不释放。 实践直接用 BlockingQueue（ArrayBlockingQueue 有界、LinkedBlockingQueue 默认 Integer.MAX_VALUE 是坑）。

Q35 ★ 怎么让三个线程按顺序打印 ABC？

🗣 人话：核心不是「叫醒所有人再抢」，而是「精确叫醒下一个」：A 干完只叫 B，B 干完只叫 C。三个 Condition 或者三个信号量接力最干净。

要点：ReentrantLock + 3 个 Condition 精确唤醒；或 Semaphore(1) 接力 acquire/release；或 AtomicInteger + 自旋（CPU 空转不推荐）。核心是精确唤醒下一个，而不是 notifyAll 全醒再抢。

Q36 AtomicInteger 与 synchronized 的性能对比

🗣 人话：人少的时候 CAS 不用排队，确实快；人一多，大家一直抢失败重试，反而比排队锁更慢，这时候用 LongAdder 拆成多份。别信「无锁一定快」。

要点：低竞争 CAS 无锁更快；高竞争下 CAS 自旋失败率飙升，性能反而不如锁，此时用 LongAdder。别迷信"无锁一定快"，要看竞争度。

Q37 线程安全的三个特性怎么落地？

🗣 人话：原子性＝这事要么全干要么不干；可见性＝我改了你马上看得见；有序性＝别偷偷调换我的顺序。最省事的办法其实是「别共享」——方法里的局部变量谁也碰不到，天然安全。

要点：原子性（Atomic*/锁）、可见性（volatile/锁）、有序性（volatile/happens-before）。 无状态对象天然安全；不可变对象（final + 安全发布）最省心；栈封闭（方法内局部变量）最容易被忽略但最有效。

Q38 ForkJoin 与工作窃取

🗣 人话：大活拆成小活，每人一条双端队列，自己从这头拿，干完了去别人那头偷。适合能拆的纯计算，不适合干等 IO。

要点：大任务递归拆成子任务放进双端队列，线程从自己队头取、空闲时从别人队尾窃取，减少竞争。适合可分割的 CPU 密集计算（归并、求和）；parallelStream 底层就是它。阻塞型任务不适合。

Q39 伪共享是什么？

🗣 人话：CPU 取数据是一拿拿一整行（64 字节）。两个线程改的是同一行里的不同变量，也会互相把对方的缓存作废，来回折腾。办法是在中间塞点没用的空位，把它们隔到两行去。

要点：CPU 缓存行 64B，两个线程改同一缓存行里的不同变量会互相失效（false sharing）。用缓存行填充（@Contended，需 -XX:-RestrictContended）解决。LongAdder 的 Cell 就做了填充。

Q40 ★ 虚拟线程（JDK21）能解决什么，不能解决什么？

🗣 人话：虚拟线程是「把等 IO 的时间让出来」，让一个操作系统线程能伺候上万个任务。它治不了 CPU 忙，也治不了数据库连接不够——连接池才是真瓶颈。也别拿池子装它，它本来就便宜。

要点：解决阻塞型 IO 的线程成本（几 KB 栈、由 JVM 调度到少量载体线程），万级并发连接不需要线程池排队。 不能解决：CPU 密集（还是那几个核）、数据库/下游连接池上限（连接数才是真瓶颈）、synchronized 块内阻塞会 pin 住载体线程（JDK21 已大幅缓解，仍建议 ReentrantLock）、ThreadLocal 大量使用会内存膨胀。不要池化虚拟线程。

四、JVM 与性能调优（12 题）

🗣 人话版：把 JVM 想成仓库 + 清洁工：对象往仓库（堆）里放，清洁工定期扫垃圾（GC）。调优也就两件事——别让垃圾堆太快（少造对象、别泄漏），别让扫垃圾时把业务停太久（选对收集器、把停顿调小）。

Q41 ★ JVM 运行时内存区域划分

🗣 人话：每个线程有自己的小桌子（栈、程序计数器），大家共用一个仓库（堆）和一个放类信息的地方（元空间）。仓库外面还有块临时堆场（直接内存），Netty 用的就是它，OOM 时经常是它出事。

要点：

  • 线程私有：程序计数器（唯一不会 OOM）、虚拟机栈（栈帧：局部变量表/操作数栈/动态链接/返回地址）、本地方法栈。
  • 线程共享：堆（新生代 Eden + 2×Survivor，老年代）、方法区（JDK8 起元空间在本地内存，字符串常量池和静态变量移到堆）。
  • 直接内存（DirectByteBuffer，受 -XX:MaxDirectMemorySize 限制，堆外 OOM 常见来源）。

Q42 ★ 对象创建过程与内存布局

🗣 人话：先确认类加载好了 → 在堆里划一块地（多线程同时划就各划各的 TLAB，免得抢）→ 全填 0 → 盖上对象头（记着是哪个类、锁状态、GC 年龄）→ 最后才跑构造方法。所以「字段有默认值」是填 0 那一步给的。

要点：类加载检查 → 分配内存（指针碰撞/空闲列表，并发用 TLAB 每线程预分配 + CAS）→ 零值初始化 → 设置对象头（Mark Word：hash/GC 分代年龄/锁标志；Klass Pointer，开启压缩指针 4B）→ 执行 <init>。 布局：对象头 + 实例数据 + 对齐填充（8 字节对齐）。-XX:+UseCompressedOops 默认开（堆 <32G 时）。

Q43 ★ 怎么判断对象可回收？为什么不用引用计数？

🗣 人话：判断死没死，不是数有几个人引用它，而是看「从根上能不能摸到它」，摸不到就是垃圾。为什么不用计数？两个人互相引用，计数永远不是 0，就永远回收不掉。

要点：可达性分析，GC Roots 包括：栈中局部变量、静态变量、常量、JNI 引用、活动线程、同步锁对象。 不用引用计数是因为循环引用无法回收，且增减计数有性能开销。对象"死亡"至少两次标记，finalize() 可自救一次（已废弃，别用）。

Q44 ★ 垃圾回收算法与分代假设

🗣 人话：清垃圾三招：扫一遍做标记再扔掉（留一地洞）、把活的搬到一边再整块清空（快，但要搬）、标记完把活的往前挪紧（没洞，但搬得累）。新生代对象死得快，用搬的最划算；老年代活得久，用挪的。

要点：标记-清除（碎片）、标记-复制（新生代，Eden:Survivor=8:1:1，浪费 10%）、标记-整理（老年代，无碎片但移动成本高）。 分代假设：绝大多数对象朝生夕死、熬过越多次 GC 越难死。所以新生代用复制、老年代用整理。

Q45 ★ 对象什么时候进老年代？

🗣 人话：熬过很多次 GC 还没死（年龄到了）、同龄人太多一下占满半个幸存区、本身就是个大块头、老年代实在塞不下了——这几种都会被提前送进老年代。

要点：① 年龄达阈值（-XX:MaxTenuringThreshold，默认 15，CMS 默认 6）；② 动态年龄判断（Survivor 中同龄对象总和 > 一半，≥ 该年龄直接晋升）；③ 大对象直接进老年代（-XX:PretenureSizeThreshold，只对 Serial/ParNew 有效）；④ 空间分配担保（Minor GC 前检查老年代剩余是否 > 新生代全部对象之和，不满足则 Full GC）。

Q46 ★ CMS 的问题，为什么被废弃？

🗣 人话：CMS 主打「边干活边打扫，尽量不停工」，但它只扫不搬，地上全是洞，来个大的就塞不进去，只能停工大扫除（还是单线程，停很久）。所以被 G1 取代，JDK14 直接删了。

要点：并发标记清除，主打低停顿。问题：标记-清除产生碎片 → 大对象分配失败触发 Full GC（Serial Old 单线程，停顿超长）；并发模式失败（预留空间不足）；浮动垃圾；CPU 敏感（默认回收线程 (核数+3)/4）。 JDK9 废弃、JDK14 移除。替代：G1。

Q47 ★ G1 的内存结构与回收流程

🗣 人话：G1 把堆切成两千来个小格子，每次只挑「垃圾最多」的格子先收，所以叫 Garbage First。你告诉它「每次最多停 200ms」，它自己决定收几个格子。堆在 4G~64G 之间最合适。

要点：堆分成 2048 个大小相等的 Region（1~32MB，2 的幂），逻辑上分 Eden/Survivor/Old/Humongous（>50% Region 的大对象）。Mixed GC 优先回收"垃圾最多"的 Region（Garbage First），可预测停顿模型 -XX:MaxGCPauseMillis（默认 200ms）。 流程：初始标记(STW) → 并发标记（SATB 快照解决漏标）→ 最终标记(STW) → 筛选回收(STW，并行复制)。 适用：堆 4G~64G、停顿敏感。超大堆（>64G）考虑 ZGC。

Q48 ★ ZGC 的关键机制

🗣 人话：ZGC 的狠招是把标记信息塞进指针本身，一边搬东西一边还能让业务线程正常访问，所以停顿只有零点几毫秒，堆再大也不变。代价是吞吐略降、内存多占一点。

要点：染色指针（把标记信息存在指针里）+ 读屏障 + 并发转移，STW 只有初始标记/最终标记，停顿 <1ms 且与堆大小无关（TB 级也能做到）。JDK21 起支持分代 ZGC。代价：吞吐略降、需要 -XX:+UseZGC、内存占用略高。

Q49 ★ 类加载过程与双亲委派

🗣 人话：加载类像「办事先找上级」：儿子先问爹，爹问爷爷，爷爷办不了才轮到自己。这样能保证 java.lang.String 只有一个官方版本，别人伪造不了。要打破它，就是「儿子必须先自己来」：SPI、Tomcat 的应用隔离。

要点：加载 → 验证 → 准备（静态变量赋零值）→ 解析（符号引用转直接引用）→ 初始化（<clinit>，执行静态赋值和静态块，父类先于子类）。 双亲委派：先委托父加载器，父加载不了才自己加载。作用：保证核心类唯一（避免自定义 java.lang.String 被加载）、防止类被篡改。打破场景：SPI（Thread.contextClassLoader）、Tomcat（WebApp 类隔离，先自己加载）、OSGi/热部署。

Q50 ★ 什么情况会 OOM？怎么定位

🗣 人话：OOM 分好几种，报错那句话就是线索：heap space 是对象太多、Metaspace 是类太多、native thread 是线程开太多、Direct buffer 是堆外内存没释放。定位就一招：出事自动 dump，拿 MAT 看「谁占得最多、是谁一直拽着它」。

要点：Java heap space（对象太多/泄漏/堆太小）、Metaspace（动态生成类过多、CGLIB 滥用）、unable to create new native thread（线程数超限，栈 -Xss 太大或线程泄漏）、Direct buffer memory（Netty 未释放 ByteBuf）、GC overhead limit exceeded（GC 时间占比 >98% 且回收 <2%）。 定位套路：-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path → MAT 看 Dominator Tree / Leak Suspects → 找到持有链的最大的 GC Root。

Q51 ★ 线上 CPU 100% 怎么排查（标准答案）

🗣 人话：四步：top 找出哪个进程，top -Hp 找出哪个线程，把线程号转成 16 进制，jstack 里搜这个号看它在干嘛。但先瞟一眼 jstat——如果是 GC 线程在忙，那是内存问题，不是代码死循环。

要点：

  1. top 找高 CPU 进程 → top -Hp <pid> 找高 CPU 线程；
  2. 线程号 printf "%x" <tid> 转十六进制；

  3. jstack <pid> | grep -A 30 <hex> 定位栈； 或者直接 arthas：thread -n 3（最忙的 3 个线程）、thread -b（死锁）。

  4. 常见原因：死循环/正则回溯、频繁 Full GC（用 jstat -gcutil <pid> 1000 先排除，这种情况 CPU 高但栈里是 GC 线程）、大量线程上下文切换（vmstat 看 cs）。

Q52 ★ 内存泄漏怎么查？（实战版）

🗣 人话：先 jmap -histo 看「哪个类的对象多得离谱」，再 dump 下来用 MAT 看「是谁一直攥着它不放」。最常见的凶手：静态 Map 当缓存没人清、ThreadLocal 忘了 remove、线程池队列堆成山、监听器注册了没注销。

要点：jmap -histo:live <pid> | head -20 看对象数量 TOP → jmap -dump:live,format=b,file=heap.hprof <pid> → MAT 打开看 Retained Heap 排序 + Path to GC Roots（排除弱引用）。 高频泄漏源：静态 Map 当缓存无淘汰、ThreadLocal 未 remove、ThreadPoolExecutor 队列堆积、监听器/回调未注销、Inflater/Connection 未关闭、subList/Arrays.asList 持有大数组。

Q53 ★ 频繁 Full GC 排查思路

🗣 人话：先看老年代「收完还剩多少」：收完还是满的，就是有东西一直被引用（泄漏）；收完能降但很快又满，多半是一次性加载了太多数据，或者对象晋升太快。元空间不够也会触发 Full GC，这个最容易被忽略。

要点：jstat -gcutil 1000 看 O（老年代）是否回收后仍高位、FGC 次数增速。 可能原因：① 内存泄漏（对象一直被引用）；② 大对象/超大集合一次性加载（select * 百万行）；③ 晋升过快（Survivor 太小、动态年龄判断提前晋升）；④ 元空间不足引发 Full GC（反射/动态代理生成类）；⑤ 显式 System.gc()（-XX:+DisableExplicitGC）；⑥ G1 的 Humongous 分配失败。

Q54 常用 JVM 参数与生产配置

🗣 人话：生产上记几条：最小堆最大堆设成一样（免得来回扩缩）、开 G1 并给个停顿目标、出事自动 dump、GC 日志打开、容器里用 MaxRAMPercentage 别写死 -Xmx（不然它会无视容器的内存限制）。

要点：-Xms=-Xmx（避免动态扩容抖动）、-Xmn 或 -XX:NewRatio、-XX:SurvivorRatio=8、-XX:MetaspaceSize/MaxMetaspaceSize、-XX:+UseG1GC -XX:MaxGCPauseMillis=200 -XX:G1HeapRegionSize=8m、-XX:+HeapDumpOnOutOfMemoryError、-Xlog:gc*:file=gc.log:time,uptime:filecount=10,filesize=50M（JDK9+ 统一日志）、-XX:+ExitOnOutOfMemoryError（容器里让 Pod 重启而不是僵死）。 容器里务必 -XX:MaxRAMPercentage=75（别用 -Xmx 写死，否则忽略了 cgroup limit）。

Q55 JIT、逃逸分析与锁消除

🗣 人话：代码跑热了 JVM 会把它编译成机器码，所以「第一次慢、后面快」。逃逸分析是「这个对象没跑出方法」，那就能直接在栈上分配、甚至拆成几个变量，连 GC 都省了；锁只有自己用，也能直接抹掉。压测不预热，数据全是假的。

要点：热点代码（方法调用 1w 次 / 循环回边 2w 次）触发 C1/C2 编译；逃逸分析判断对象是否逃出方法，未逃逸可栈上分配 + 标量替换（减少 GC 压力）、锁消除（StringBuffer 局部变量去掉同步）。 -XX:+DoEscapeAnalysis 默认开。注意：-Xint 关闭 JIT 后压测数据完全不可信。JIT 还会导致"第一次慢后面快"和"去优化"，压测要预热。

五、MySQL（16 题）

🗣 人话版：MySQL 的面试就三问：怎么找得快（索引）、好几个人同时改怎么办（事务和锁）、数据太多了怎么办（分库分表）。答索引一定要主动提「回表」，那是所有优化的起点。

Q56 ★ InnoDB 的索引为什么用 B+ 树？

🗣 人话：B+ 树又矮又胖，三层就能装千万行，一次磁盘 IO 读一层，查一行只要两三次 IO；叶子之间还是链表，范围查、排序特别顺。这就是为什么不用二叉树（太高）也不用 Hash（只能等值查）。

要点：B+ 树矮胖（3~4 层可存千万级）、非叶子只存键不存数据 → 单页扇出大；叶子节点双向链表，范围查询和排序友好；相比 B 树，数据只在叶子，查询稳定为树高。 对比：Hash 索引只支持等值；跳表内存开销大且磁盘不友好；二叉树层数太高 IO 太多。

Q57 ★ 聚簇索引与二级索引、回表

🗣 人话：主键索引的叶子直接挂着整行数据（书的本体），普通索引的叶子只挂主键（书的目录）。按目录找到页码，还得翻回本体拿内容，这就是回表。若目录上已经写着你要的东西，就不用翻了——这叫覆盖索引，所以 select * 最容易破功。

要点：聚簇索引（主键）叶子存整行数据；二级索引叶子存主键值。通过二级索引查非索引列要回表（再走一次聚簇索引）。 覆盖索引可避免回表（explain 的 Extra: Using index）。所以 select * 是最容易破覆盖索引的写法。主键建议自增：随机主键（UUID）导致页分裂、页利用率低。

Q58 ★ 最左前缀原则与索引失效

🗣 人话：联合索引像电话簿先按姓再按名排，你直接查「名」是用不上的，必须从最左边开始连续用。范围查询后面那列也用不上了（但能靠索引下推少回表）。失效常见原因：列上套函数、类型对不上、前面带 %、or 里有没索引的列。

要点：联合索引 (a,b,c) 只能从 a 开始连续匹配；范围查询（>、<、between、like 'x%'）之后的列失效（但 a=1 and b>2 and c=3 中 c 仍可用索引下推 ICP 过滤，减少回表）。 失效场景：函数/表达式作用于索引列（where date(create_time)=...）、隐式类型转换（字符串列传数字，如 phone=138xxx）、!=/not in（可能全表）、or 中有非索引列、前导模糊 %x、字符集不一致 join、优化器判定回表成本高于全表扫（区分度低的列）。

Q59 ★ explain 重点看什么？

🗣 人话：就看四列：type（怎么找的，ALL 是全表扫，最差）、key（用了哪个索引）、rows（预计扫多少行）、Extra（有没有 filesort、temporary，有就得优化）。key_len 能看出联合索引用了几列。

要点：type（system > const > eq_ref > ref > range > index > ALL，至少 range）、key（实际用的索引）、key_len（用了联合索引几列）、rows（预估扫描行数）、filtered、Extra（Using index 覆盖索引 / Using filesort 需优化排序 / Using temporary 需优化分组 / Using index condition ICP）。 explain analyze（8.0.18+）能看实际耗时，比预估准。

Q60 ★ 事务隔离级别与解决的问题

🗣 人话：四种级别就是「你愿意为一致性付出多少并发」。MySQL 默认可重复读，同一事务里反复查结果一样。它还额外用间隙锁挡住了大部分幻读——但不是全部。

要点：读未提交（脏读）、读已提交（RC，解决脏读）、可重复读（RR，MySQL 默认，解决不可重复读）、串行化。 ⚠ MySQL 的 RR 通过 MVCC + 间隙锁 还额外解决了大部分幻读（快照读靠 ReadView，当前读靠 Next-Key Lock），但不是全部（先快照读再当前读仍可能"看到"新行）。

Q61 ★ MVCC 实现原理

🗣 人话：每行都藏着两个暗号：「最后是谁改的」和「上一个版本在哪」。改一次就在 undo 里留份旧版本，串成一条链。你查的时候举着一份「快照名单」，顺着链往前找，找到你出生之前就存在的那个版本。RC 每次查都重新领名单，RR 全程用同一份——差别就在这。

要点：隐藏字段 DB_TRX_ID（最后修改事务）、DB_ROLL_PTR（指向 undo log 版本链）、DB_ROW_ID；undo log 版本链；ReadView（m_ids 活跃事务列表、min_trx_id、max_trx_id、creator_trx_id）。 可见性判断：trx_id < min_trx_id 可见；>= max_trx_id 不可见；在 m_ids 中不可见；否则可见。 RC 每次 SELECT 都新建 ReadView；RR 只在第一次 SELECT 建，之后复用——这就是两者差异的根因。

Q62 ★ redo log / undo log / binlog 各自作用

🗣 人话：redo 是「先记草稿，断电也能照着补回来」（保证不丢）；undo 是「改之前的原样」，用来反悔和给别人看旧版本；binlog 是「流水账」，主从复制和备份靠它。redo 和 binlog 要一致，中间就加了一道「先准备、再记账、最后确认」。

要点：redo（InnoDB 物理日志，循环写，保证崩溃恢复的持久性，innodb_flush_log_at_trx_commit=1）；undo（逻辑日志，回滚 + MVCC）；binlog（Server 层逻辑日志，归档/主从复制，sync_binlog=1）。 两阶段提交：写 redo（prepare）→ 写 binlog → 提交 redo（commit），用 XID 关联，保证两者一致。崩溃恢复时 redo 是 prepare 且 binlog 完整则提交，否则回滚。

Q63 ★ 隔离级别与锁：间隙锁、Next-Key Lock

🗣 人话：可重复读下为了防止「查的时候突然多出一行」，MySQL 不光锁住存在的行，还把行与行之间的空隙一起锁了，让你插不进来。唯一索引精确命中时会退化成只锁那一行；没走索引的更新会直接把整张表锁了——这是很多线上卡死的元凶。

要点：RR 下为解决幻读，当前读加 Next-Key Lock = 记录锁 + 间隙锁，锁住左开右闭区间 (a, b]。 注意：唯一索引等值命中时会退化为记录锁；没有索引的更新会锁全表（升级为表锁）；间隙锁之间不互斥（都是"阻止插入"），只有插入意向锁与之冲突。 RC 下没有间隙锁（只锁行），所以并发更高但可能幻读，很多互联网公司默认改成 RC + 行格式 ROW。

Q64 ★ 死锁怎么产生、怎么排查

🗣 人话：两个事务一个先改 A 再改 B，另一个先改 B 再改 A，互相等。show engine innodb status 能看到最近一次死锁的现场。根治就是「大家都按同一个顺序改」，再加短事务、条件列有索引。

要点：两个事务以不同顺序持有/等待行锁（如 update A where id=1 与 update B where id=2 交叉）。 排查：show engine innodb status 看 LATEST DETECTED DEADLOCK；information_schema.innodb_trx + performance_schema.data_locks（8.0）看持锁等待。 解决：统一加锁顺序、缩短事务、拆分大事务、给条件列加索引（避免锁范围扩大）、innodb_lock_wait_timeout 兜底 + 应用层重试。

Q65 ★ 慢 SQL 怎么优化（给一套流程）

🗣 人话：顺序别搞反：先开慢日志找出最耗时的几条，explain 看它到底怎么执行的，然后才是加索引 / 改 SQL / 少查数据，最后才轮到分库分表。上来就说分库分表的，一般是没看过执行计划。

要点：① 开慢查询日志（slow_query_log、long_query_time=1、pt-query-digest 聚合 TOP）；② explain 看执行计划；③ 优化手段排序：加/改索引（覆盖索引） > 改写 SQL（去掉函数、拆 OR、分页优化） > 减少回表/减少数据量（只查必要列、加 limit） > 表结构/归档 > 分库分表。 拒绝"上来就分库分表"：先看是不是缺索引或 SQL 写错。

Q66 ★ 深分页 limit 1000000, 10 怎么优化？

🗣 人话：limit 1000000,10 的意思是「翻完前一百万个，只把最后一条给我看」，前面全白扔。两个解法：先在索引上把 id 翻出来再去取整行（延迟关联）；或者记住上一页最后一个 id，用 where id > ? 接着翻（最快，但不能跳页）。

要点：原因：扫描并丢弃前 100w 行。方案：

  1. 延迟关联：select * from t join (select id from t order by id limit 1000000,10) x using(id)，先在覆盖索引上分页；
  2. 游标/书签：where id > 上次最大id order by id limit 10（推荐，O(1) 定位，但只能顺序翻页）；
  3. 业务上限制最大页数（如只允许看前 100 页）。

Q67 ★ 大表加字段 / 加索引 / 改字段类型怎么做？

🗣 人话：8.0 加字段是改元数据，秒级；但加索引还是得重建，用 Online DDL，期间能读写但吃 IO。生产上更稳的是 gh-ost 这类工具：建影子表，边同步边改，最后换个名字，业务几乎无感。

要点：MySQL 8.0 支持 Instant Add Column（ALGORITHM=INSTANT，只改元数据，秒级）；但加索引仍要Online DDL（ALGORITHM=INPLACE, LOCK=NONE），期间可读写但占 IO。 生产做法：低峰执行 + pt-online-schema-change / gh-ost（建影子表 + 触发器/binlog 同步 + 改名），避免主从延迟和锁表。改字段类型基本都要重建表，用 gh-ost。

Q68 分库分表怎么选分片键？会带来什么问题？

🗣 人话：分片键要「散得匀」且「大多数查询都带它」，一般就是 user_id 或 order_id。拆完麻烦才刚开始：跨库 join、跨库分页排序、分布式事务、全局 ID、扩容搬数据，全得单独解决。

要点：分片键要分布均匀 + 大多数查询能带上（如 user_id、order_id）。用 hash(user_id) % N 或一致性哈希/基因法（订单号里嵌入 user_id 后几位，保证按用户和按订单都能路由）。 带来的问题：跨分片 join、跨分片分页/排序/聚合、分布式事务、全局唯一 ID、扩容迁移（成倍扩容或双写迁移）。对策：冗余字段、宽表、ES 做查询、ShardingSphere、雪花 ID。

Q69 ★ 分布式 ID 方案对比

🗣 人话：UUID 别拿来当 MySQL 主键（无序，页分裂）。号段模式是「一次领 1000 个号，用完再领」，数据库压力直接降一千倍。雪花是「时间戳 + 机器号 + 序列」，趋势递增很好用，就怕服务器时钟往回跳。

要点：UUID（无序、太长，不要做 MySQL 主键）；数据库自增/号段（Leaf-segment 双 buffer，依赖 DB）；雪花算法（时间戳+机器位+序列，趋势递增，依赖时钟，回拨要处理）；Redis INCR（性能好但依赖 Redis）；美团 Leaf-snowflake（ZK 分配 workerId）。

Q70 ★ count(*)、count(1)、count(列) 的区别

🗣 人话：count() 和 count(1) 一样快，别纠结；count(列) 会跳过 null，语义不一样。InnoDB 没存总数，所以 count() 必须真数——这就是大表 count 慢的原因。要么维护计数表，要么别实时数。

要点：count(*) 和 count(1) 语义相同，InnoDB 做了优化（选最小的二级索引扫）；count(列) 要判断非 null，不统计 null。count(*) 在 InnoDB 里必须真扫（MVCC 下每行可见性不同，不能像 MyISAM 存总数）。 优化：维护计数表/Redis 计数（注意一致性）、或 explain 的 rows 估算。

Q71 为什么建议用自增主键？没有主键会怎样？

🗣 人话：自增是「往后排着放」，写得顺、页是满的；UUID 是「随机插」，插得到处都是，页分裂、碎片、索引还都变大（二级索引里存的就是主键）。没主键 InnoDB 也会偷偷造一个隐藏的，但那是全局共享的，有争用。

要点：自增主键顺序写入，页利用率高、无页分裂；随机主键导致随机 IO + 页分裂 + 碎片。InnoDB 必须有聚簇索引，无主键时用唯一非空索引，都没有则建 6 字节隐藏 ROW_ID（全局共享，有争用风险）。 二级索引都存主键，主键越长所有索引越大，所以别用 UUID/长字符串做主键。

Q72 ★ 主从延迟怎么解决？

🗣 人话：主库写完了，从库还在慢慢追，所以「刚写完就去从库读」会读不到。解法：这段时间强制走主库、半同步复制、把大事务拆小、监控延迟报警。本质是「接受短暂不一致，但别让用户看见」。

要点：原因：从库单线程回放（5.7+ 支持并行复制，按组提交/逻辑时钟）、大事务、无主键表更新、从库压力大。 解决：强制走主库（刚写完要读的场景）、半同步复制（after_sync）、seconds_behind_master 监控 + 报警、拆大事务、缓存兜底（写后删缓存，读时回填）、业务容忍（异步通知）。

Q73 ★ 索引区分度、什么时候不该建索引？

🗣 人话：一列只有男/女两个值，建了索引也筛不掉多少，不如不建。还有几种别建：天天改的列、几乎不查的列、表本来就很小、已经是联合索引最左列的。索引不是越多越好，每个都要跟着写。

要点：区分度 = count(distinct col)/count(*)，低于 0.1 基本没意义（如性别）。不该建：更新极频繁的列、很少作为查询条件的列、表很小、已有联合索引的最左列（重复）。 索引不是越多越好：每个索引增加写放大、占空间、影响优化器选择。

Q74 事务的 ACID 靠什么保证？

🗣 人话：原子性靠 undo（能反悔），持久性靠 redo（断电也能补），隔离性靠锁和 MVCC（各看各的），一致性是前面三个加业务约束一起保证的结果。

要点：A 靠 undo log；C 靠约束 + 应用逻辑 + 其他三者共同；I 靠锁 + MVCC；D 靠 redo log + WAL。

Q75 MySQL 与 Redis 双写一致性（先给结论）

🗣 人话：标准做法是「先改数据库，再删缓存」，不是改缓存。改缓存两次写的顺序一乱就永久脏了，而删掉下次自然重建。删也可能失败，所以加延迟双删，或者直接订阅 binlog 去删。要强一致就别靠缓存，直接读库或加锁。

要点：Cache Aside + 先更新 DB 再删除缓存（不是更新缓存），配合延迟双删（删缓存 → 更新 DB → 延迟 500ms 再删）或订阅 binlog（Canal）异步删缓存。 为什么不是"先删缓存再更新 DB"：并发读会把旧值回填。为什么删而不是更新：并发写会导致缓存与 DB 顺序错乱、且很多缓存是聚合结果（算不出来）。 强一致就加分布式锁或直接读 DB，缓存只做最终一致 + 过期时间兜底。

六、Redis（14 题）

🗣 人话版：Redis 就是一块放在内存里的公共白板，谁都能秒读秒写。所以它的问题永远围绕两件事：白板上的字跟数据库对不对得上（一致性），白板被擦掉或者写满了怎么办（穿透、雪崩、淘汰）。

Q76 ★ Redis 为什么快？单线程还是多线程？

🗣 人话：快不是因为「单线程」这三个字，而是：数据全在内存、一个线程不用抢锁、用 epoll 一个人盯很多连接。6.0 之后收发的活分给几个线程了，但执行命令还是单线程——所以一个慢命令能卡住所有人。

要点：纯内存 + IO 多路复用（epoll） + 单线程避免锁竞争/上下文切换 + 高效数据结构（SDS、跳表、listpack、intset）。 6.0 起网络 IO 多线程（io-threads，默认只处理读写和协议解析，命令执行仍是单线程）；4.0 起有后台线程做异步删除（UNLINK、lazyfree）。 ⚠ 别答"单线程所以快"，要答"避免了并发竞争 + 内存操作 + 多路复用"。

Q77 ★ 五种基本类型与底层编码

🗣 人话：String 是字符串/计数/锁；Hash 是「一个小对象」；List 是队列；Set 是去重集合；ZSet 是带分数的排行榜。元素少的时候 Redis 用紧凑编码省内存，多了才换成正经哈希表和跳表。

要点：

  • String：SDS（记录长度、二进制安全、预分配），可用于计数、分布式锁、Session。
  • Hash：元素少用 listpack（7.0 前 ziplist），超阈值转 hashtable（hash-max-listpack-entries 128 / -value 64）。
  • List：quicklist（listpack 组成的双向链表）。
  • Set：全整数用 intset，否则 hashtable。
  • ZSet：元素少用 listpack，否则 跳表 + 字典（字典保证 O(1) 查分，跳表保证范围查询和排名）。 新类型：Bitmap（签到、去重）、HyperLogLog（UV 估算，12KB 误差 0.81%）、GEO（附近的人）、Stream（消息队列）。

Q78 ★ 跳表 vs 红黑树，为什么 ZSet 用跳表？

🗣 人话：跳表就是「链表加几层快速通道」，找的时候先坐快车再走小路。它比红黑树好写，范围查特别顺（底下本来就是条有序链表），Redis 就选了它。层级是随机掷出来的，不是严格排的。

要点：跳表实现简单、范围查询天然友好（底层链表 + 多级索引）、并发/内存控制容易；红黑树范围查询要中序回溯。跳表平均 O(logN)，最坏 O(N)（概率极低）。Redis 用概率晋升（1/4）而非严格分层。

Q79 ★ RDB 与 AOF 怎么选？

🗣 人话：RDB 是「拍张照片」，恢复快、文件小，但两次拍照之间的数据会丢；AOF 是「记流水账」，最多丢 1 秒，但文件大、恢复慢。生产上一般两个都要：AOF 重写时前半段直接写成 RDB 格式，又快又安全。

要点：RDB 是二进制快照（bgsave fork + COW），恢复快、体积小，但会丢最后一次快照后的数据；AOF 是命令追加（appendfsync everysec 默认，最多丢 1s），可读、可修复，但文件大、恢复慢、有重写开销。 生产：混合持久化（aof-use-rdb-preamble yes），AOF 重写时前半段写 RDB 格式，兼顾恢复速度和数据安全。

Q80 ★ 过期删除策略与内存淘汰

🗣 人话：Redis 删过期 key 是「抽查」——定期随机抽一批看，过期的扔掉；你不查它，它可能一直占着内存。内存满了按策略淘汰，纯缓存建议 allkeys-lfu（按「谁最不常被用」踢）。

要点：惰性删除 + 定期删除（每 100ms 随机抽查 20 个，过期比例 >25% 继续）。所以过期 key 不一定立刻释放内存。 淘汰策略 8 种：noeviction（默认，写满报错）、allkeys-lru/lfu/random、volatile-lru/lfu/random/ttl。缓存场景用 allkeys-lfu（LFU 抗"偶发批量访问"，4.0+）；纯缓存别用 volatile-*（没设过期时间的 key 永远不淘汰）。

Q81 ★ 缓存穿透、击穿、雪崩

🗣 人话：穿透是「查一个根本不存在的东西」，每次都穿过去打库 → 布隆过滤器 + 缓存空值；击穿是「一个热点 key 突然过期」，一堆人同时回源 → 加锁让一个人去重建；雪崩是「一大批 key 同时过期或 Redis 挂了」→ TTL 加随机、多级缓存、熔断兜底。

要点：

  • 穿透（查不存在的数据，打到 DB）：布隆过滤器 + 缓存空值（短 TTL）。
  • 击穿（热点 key 失效瞬间大量请求）：互斥锁/单飞（SETNX 重建，其他线程等待或返回旧值）+ 逻辑过期（不设 TTL，异步刷新，永远返回旧值）。
  • 雪崩（大量 key 同时失效或 Redis 挂）：TTL 加随机值、多级缓存、熔断降级、集群高可用（哨兵/Cluster）。

Q82 ★ 热 key / 大 key 怎么发现和处理？

🗣 人话：大 key 是「一个 key 里塞了几万个元素」，删它、传它都能把单线程堵住；热 key 是「一个 key 被所有人同时访问」，能把一台机器的网卡打满。大 key 要拆，热 key 要复制到本地缓存或多副本。

要点：

  • 发现：redis-cli --bigkeys、MEMORY USAGE key、SLOWLOG；热 key 用 monitor（慎用，影响性能）、客户端埋点、京东 hotkey。
  • 大 key 危害：单线程阻塞（删除/网络传输）、集群倾斜、主从同步卡顿。
  • 处理：拆分（Hash 分桶 user:1:part1）、UNLINK 异步删、压缩、热 key 本地缓存多副本。

Q83 ★ 分布式锁怎么做？（Redisson 版）

🗣 人话：加锁必须一条命令搞定（SET NX + 过期时间），别分两步。解锁要用 Lua 先看是不是自己的再删，不然可能删掉别人的锁。Redisson 还带个看门狗，业务没跑完自动续期。主从切换那一瞬间可能丢锁，要求绝对互斥就换 ZK。

要点：SET key value NX PX 30000（必须 NX + 过期时间原子设置，value 用 UUID 标识持有者）。 释放要用 Lua 原子判断再删，否则可能删掉别人的锁。Redisson 用 Hash 结构 + 看门狗（watchdog）自动续期（默认 30s，每 10s 续一次），解决业务超时。 ⚠ 追问：主从切换丢锁 → 用 RedLock（多节点多数派），但 RedLock 本身有争议（时钟漂移），要求强一致就用 ZooKeeper/etcd 或 DB 唯一索引。看门狗只在未显式指定 leaseTime 时生效。

Q84 ★ 缓存与数据库一致性（进阶）

🗣 人话：延迟双删的那个「延迟」要大于主从同步时间加一次读的耗时，一般半秒到一秒。最靠谱的还是订阅 binlog 异步删缓存——业务不用管，删失败还能重试。

要点：见 Q75。补充：延迟双删的延迟时间 = 主从同步延迟 + 业务读耗时，一般 500ms~1s；binlog 订阅（Canal + MQ）是最可靠的最终一致方案，能避免"删缓存失败"。 不要把缓存当数据源，热点数据加本地缓存（Caffeine）时用 MQ 广播失效。

Q85 ★ Redis 主从、哨兵、Cluster 的区别

🗣 人话：主从是「一个写多个读」，挂了自己不会站起来；哨兵是「请几个保安盯着，主挂了投票换一个」；Cluster 是「数据分片，一摊变好几摊」，最少 3 主 3 从。分片之后跨 key 操作就麻烦，得用 hash tag 把相关的 key 塞进同一个槽。

要点：主从解决读扩展和备份（异步复制，可能丢数据）；哨兵解决主从切换（3 个以上奇数节点，quorum 判定客观下线，Raft 选 leader 执行故障转移）；Cluster 解决容量（16384 个 slot，CRC16(key)%16384，节点间 gossip，需要至少 3 主 3 从）。 限制：Cluster 下多 key 操作要求同一 slot（用 {tag} hash tag）、不支持多 DB、事务只支持同节点。

Q86 ★ Redis 事务与 Lua 的区别

🗣 人话：Redis 事务不是真事务——中间一条命令错了，别的照样执行，还不回滚。想「要么全做要么不做」就用 Lua，整段一起执行，中间还能读结果做判断。但脚本里别写耗时逻辑，会把整个实例卡死。

要点：MULTI/EXEC 不支持回滚（语法错误整体不执行，运行时错误其他命令照常执行），且无法拿到中间结果做条件判断。所以复杂原子操作要用 Lua 脚本（单线程执行、原子、可读中间值），或用 Redis Function（7.0）。 注意：Lua 里不要写耗时逻辑（阻塞整个实例），KEYS 命令禁用（用 SCAN）。

Q87 ★ Pipeline 与批量命令的区别

🗣 人话：Pipeline 是把十句话攒一起一次说完，省的是来回往返的时间，但它不是原子的，中间可能插进别人的命令。MGET 是一条命令取多个值，那个才原子。

要点：Pipeline 是客户端攒一批命令一次发送，减少 RTT（N 次 1ms 变 1 次），但不保证原子性，命令之间有依赖不能用。MGET/MSET 是服务端单命令，原子。注意 pipeline 批次别太大（内存 + 阻塞）。

Q88 ★ Redis 内存碎片与 fork 的影响

🗣 人话：Redis 做快照要 fork 子进程，内存不够时靠「写时复制」顶着——写得多内存可能翻倍，所以机器要留一半余量。堆越大 fork 越慢，主线程会卡一下，所以单实例别搞太大，10G 以内比较稳。

要点：mem_fragmentation_ratio > 1.5 考虑 activedefrag（7.0 前需编译开启）或重启。bgsave/AOF rewrite 用 fork + COW，内存翻倍风险 → 机器内存留 50% 余量；fork 时主线程阻塞（堆越大越久），大实例要控制单实例内存（建议 ≤10G）。

Q89 ★ Redis 做消息队列行不行？

🗣 人话：List 能当个简单队列，但没有消费组、没有 ACK；Pub/Sub 一断线消息就没了；Stream 好一些，有消费组和 ACK，但重试、死信、堆积还是不如专业 MQ。轻量场景能用，重要的别用。

要点：List + BRPOP 简单但不能多消费组、无 ACK；Pub/Sub 不持久化、断连丢消息；Stream 支持消费组、ACK、pending 列表，适合轻量场景。但没有完善的重试/死信/堆积能力，重要业务还是 Kafka/RocketMQ。

Q90 ★ 缓存预热、降级、限流在缓存层的落地

🗣 人话：预热是大促前先把热点数据塞进缓存，别让用户来当第一个；降级是 Redis 挂了就返回兜底数据，别让流量全砸到数据库；限流可以用 Redis + Lua 做，但别忘了 Redis 自己也可能扛不住。

要点：预热（启动/大促前批量加载热点）、降级（Redis 不可用时读本地缓存或返回兜底值，别让缓存故障拖垮 DB）、限流（Redis + Lua 做滑动窗口/令牌桶，但要考虑 Redis 本身是瓶颈）。

Q91 ★ 为什么不要把 Redis 当数据库？

🗣 人话：Redis 的持久化是「尽量不丢」，不是「保证不丢」；没有强事务、没有复杂查询、内存还贵。它的定位是缓存和加速，不是记账本。

要点：持久化是异步/准实时（可能丢数据）、无强事务、无复杂查询、内存成本高、单线程下大 key 会拖垮全实例。定位是缓存 + 高性能中间件，不是 OLTP 存储。

Q92 ★ Cluster 扩容时 slot 迁移对业务的影响

🗣 人话：迁移时 key 可能已经搬到新节点，客户端会收到 ASK 说「去那边问」；永久搬走了收到的是 MOVED，客户端得更新自己的路由表。大 key 迁移会卡很久，所以挑低峰做、还要限速。

要点：CLUSTER SETSLOT 迁移期间，若 key 已迁走则返回 ASK 重定向（客户端要发 ASKING 再请求目标节点），未迁走正常处理；MOVED 是永久重定向（客户端要刷新 slot 缓存）。迁移是逐 key 同步复制，大 key 会长时间阻塞，建议低峰 + 限速（cluster-migration-barrier）。

七、Spring 全家桶（14 题）

🗣 人话版：Spring 干的事说白了就两件：帮你造对象（IoC）、帮你在方法前后加料（AOP）。所有八股——生命周期、循环依赖、事务失效——都是这两件事的细节。答题先归位：这事发生在「造对象」阶段还是「加料」阶段。

Q93 ★ Bean 的生命周期（完整链路）

🗣 人话：先 new 出来 → 把依赖塞进去 → 回调一堆 Aware（告诉你我叫啥、在哪个容器）→ 初始化前处理 → @PostConstruct → afterPropertiesSet → init-method → 初始化后处理（AOP 代理就在这一步生成）→ 用 → 销毁。记住代理是「初始化之后」才套上去的。

要点：实例化（instantiate）→ 属性填充（populateBean，DI）→ Aware 回调（BeanNameAware/BeanFactoryAware/ApplicationContextAware）→ BeanPostProcessor.postProcessBeforeInitialization → @PostConstruct → InitializingBean.afterPropertiesSet → init-method → BeanPostProcessor.postProcessAfterInitialization（AOP 代理在这里生成）→ 使用 → @PreDestroy → DisposableBean.destroy → destroy-method。

Q94 ★ 循环依赖怎么解决？三级缓存分别存什么？

🗣 人话：A 要 B、B 要 A，谁先来都卡住。Spring 的办法是「半成品先摆出来」：A 刚 new 出来还没填属性，就先把这个引用登记到二级缓存，B 需要时先拿去用。三级缓存是个工厂，专门决定「要不要提前给 A 生成代理」。构造器注入没法这么玩，所以解决不了。

要点：只解决单例 + setter/字段注入的循环依赖，构造器注入和 prototype 解决不了（直接报错）。

  • 一级 singletonObjects：成品 Bean。
  • 二级 earlySingletonObjects：提前暴露的早期引用（可能是代理）。
  • 三级 singletonFactories：ObjectFactory，调用 getEarlyBeanReference 时决定是否提前生成 AOP 代理。 为什么需要三级而不是两级：为了让代理对象在需要时才创建——如果 A 被 AOP 代理，B 依赖的必须是代理对象，用工厂延迟到"真的被循环依赖"时才生成，避免所有 Bean 都提前代理。 ⚠ 2.6+ 默认禁止循环依赖（spring.main.allow-circular-references=false），正确做法是重构（抽第三方的 Service 或用 @Lazy）。

Q95 ★ @Autowired 与 @Resource 的区别

🗣 人话：@Autowired 是「先看类型，撞车了再看名字」；@Resource 是「先看名字，找不到再看类型」。官方更推荐构造器注入：依赖跑不掉、好测试，还能一眼看出循环依赖。

要点：@Autowired 是 Spring 的，按类型注入（多个候选时按名称/@Primary/@Qualifier），required=false 可为空；@Resource 是 JSR-250，默认按名称，找不到再按类型。构造器注入是官方推荐（不可变、易测试、能暴露循环依赖）。

Q96 ★ AOP 的实现与失效场景

🗣 人话：AOP 靠的是「替身」，你在类里 this.方法() 就是绕过替身直接找本人，加料全没了。所以自调用、private 方法、new 出来的对象、异常被自己吞了——这几种注解都白写。

要点：有接口默认 JDK 动态代理，无接口用 CGLIB（Boot 2.x 默认 proxyTargetClass=true 强制 CGLIB）。 失效场景：① 同类内部方法自调用（this.method() 不走代理）；② private/final/static 方法；③ 非 Spring 管理的对象（new 出来的）；④ 异常被自己 catch 了；⑤ 多线程调用（事务上下文不传递）。 解决自调用：注入自身代理（AopContext.currentProxy() 需 exposeProxy=true）、拆到另一个 Bean、用 TransactionTemplate。

Q97 ★ @Transactional 失效的 8 种情况

🗣 人话：记住最常见的三个：自己调自己、异常被 catch 了、抛的是受检异常（默认只认 RuntimeException）。所以 @Transactional(rollbackFor = Exception.class) 必须写，别省。

要点：① 自调用；② 方法非 public（CGLIB 也拦不到 private/protected）；③ 异常被 catch；④ 抛的是受检异常（默认只回滚 RuntimeException/Error，要 rollbackFor = Exception.class）；⑤ 类没被 Spring 管理；⑥ 数据库引擎不支持事务（MyISAM）；⑦ 多线程；⑧ 传播行为设成 NOT_SUPPORTED/REQUIRES_NEW 用错；⑨ try-catch 后没重新抛。 最佳实践：@Transactional(rollbackFor = Exception.class) 必写。

Q98 ★ 事务传播行为 7 种

🗣 人话：REQUIRED 是「有事务就跟着，没有就开一个」（默认）；REQUIRES_NEW 是「你们先停，我单开一个，我挂了不影响你们」；NESTED 是「在我这里面打个存档点，我这儿出错回存档点，你整个挂了我跟着完」。REQUIRES_NEW 会多占一条连接，嵌套深了能把连接池抽干。

要点：REQUIRED（默认，有则加入无则新建）、REQUIRES_NEW（挂起当前，新建独立事务，内层回滚不影响外层）、NESTED（保存点，内层回滚到 savepoint，外层回滚会带着内层）、SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER。 坑：REQUIRES_NEW 会占用新连接，嵌套多层容易把连接池打满；同类内调用传播行为不生效（见 Q96）。

Q99 ★ Spring MVC 请求处理流程

🗣 人话：请求先到 DispatcherServlet（总调度），它查表找到该谁处理，再让适配器去调你的方法，中间把参数解析好，返回值该转 JSON 转 JSON，该渲染页面渲染页面。拦截器像安检：进门前按顺序过，出门反着过，出了事 afterCompletion 也会走。

要点：DispatcherServlet → HandlerMapping 找 Handler（含拦截器链）→ HandlerAdapter 执行（参数解析 HandlerMethodArgumentResolver、返回值处理 ReturnValueHandler）→ 返回 ModelAndView → ViewResolver 渲染（@ResponseBody 走 HttpMessageConverter）。 拦截器 preHandle（正序）→ Controller → postHandle（逆序）→ afterCompletion（逆序，异常也会走）。

Q100 ★ Spring Boot 自动配置原理

🗣 人话：Spring Boot 就是「提前写好一张清单，写着哪些情况该配什么」。启动时把清单读出来，再用一堆条件注解筛一遍：类在不在、你有没有自己定义、配置开没开。符合条件才生效。所以你能覆盖它——你自己定义了 Bean，它就不配了。

要点：@SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan。 @EnableAutoConfiguration 通过 AutoConfigurationImportSelector 读 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（2.7+，之前是 spring.factories）拿到候选配置类 → 用 @ConditionalOnClass/OnMissingBean/OnProperty 等条件装配过滤 → 注册 Bean。 自定义 starter：写 @AutoConfiguration + 条件注解 + spring-configuration-metadata.json 提供 IDE 提示。

Q101 ★ @Configuration 与 @Component 的区别（CGLIB 增强）

🗣 人话：@Configuration 的类会被 CGLIB 偷偷改成子类，你在里面调另一个 @Bean 方法，它先看容器里有没有，有就直接给你，所以拿到同一个对象。@Component 没这待遇，调一次 new 一个。Boot 2.2 之后建议关掉这个增强，启动更快，但别在类里互相调。

要点：@Configuration(proxyBeanMethods=true) 会被 CGLIB 增强，类内 @Bean 方法互相调用返回同一个单例；@Component 不增强，方法调用是普通 new。 Boot 2.2+ 建议 proxyBeanMethods=false（Lite 模式，启动更快，但要求 Bean 之间不要方法调用）。

Q102 Spring 的扩展点有哪些？

🗣 人话：想改 Bean 本身用 BeanPostProcessor；想改 Bean 的定义（还没造出来）用 BeanFactoryPostProcessor；想动态注册 Bean 用 ImportSelector；想监听事件用 ApplicationListener。Spring Boot 各种「魔法」都是从这几个口子来的。

要点：BeanPostProcessor（改 Bean 实例）、BeanFactoryPostProcessor（改 BeanDefinition，如 PropertySourcesPlaceholderConfigurer）、ImportSelector/ImportBeanDefinitionRegistrar（动态注册）、ApplicationListener（事件）、InitializingBean/DisposableBean、HandlerInterceptor、@Aspect。 注意 BeanPostProcessor 里的 Bean 不会触发其他 BPP（会提前实例化，容易踩循环依赖）。

Q103 ApplicationContext 与 BeanFactory 的区别

🗣 人话：BeanFactory 是最底层的容器，你要才给你（懒加载）；ApplicationContext 是加强版，启动时就把单例都造好，还带事件、国际化、资源加载。FactoryBean 是「造 Bean 的工厂 Bean」，别和 BeanFactory 搞混。

要点：BeanFactory 是基础容器，懒加载；ApplicationContext 是其子接口，启动时预实例化单例，多了国际化、事件发布、资源加载、AOP 集成。FactoryBean 是"生产 Bean 的 Bean"（getObject()），BeanFactory 是容器本身。

Q104 Spring 事件机制与事务事件

🗣 人话：发事件默认是同步的，发完等听众都听完才往下走，想异步加 @Async。最有用的是 @TransactionalEventListener(AFTER_COMMIT)：等事务真提交了再发通知，避免「消息发出去了但事务回滚了」。

要点：ApplicationEventPublisher.publishEvent 默认同步执行，可 @Async 异步（需线程池），@TransactionalEventListener(phase = AFTER_COMMIT) 可以事务提交后再发通知（解决"消息发了但事务回滚"的经典问题）。

Q105 Spring Cloud 核心组件（2024 后的现状）

🗣 人话：现在的主流组合是 Nacos + Gateway + OpenFeign + Sentinel。Eureka、Hystrix、Zuul、Ribbon 都停更了，面试还提这几个会显得资料老。

要点：

  • 注册中心：Nacos（AP/CP 可切，主流）/ Eureka（停更）/ Consul。
  • 配置中心：Nacos / Apollo。
  • 网关：Spring Cloud Gateway（WebFlux，非阻塞）/ Zuul（淘汰）。
  • 负载均衡：LoadBalancer（替代 Ribbon）。
  • 熔断限流：Sentinel（阿里，控制台强）/ Resilience4j（Hystrix 停更）。
  • 调用：OpenFeign（声明式，底层还是 HTTP）。
  • 链路：Sleuth/Micrometer Tracing + Zipkin/SkyWalking。

Q106 ★ Feign 的调用原理与常见坑

🗣 人话：Feign 就是「给远程接口套个本地接口的壳」，你调方法，它背地里拼 HTTP 请求。最大的坑是默认没设超时，下游一卡你的线程就一直挂着，最后把自己拖死。所以 connectTimeout/readTimeout 必须配。

要点：@FeignClient 启动时被扫描 → 生成 JDK 动态代理 → 方法调用被 FeignInvocationHandler 拦截 → 编码成 HTTP 请求 → 走 LoadBalancer 选实例 → 发请求 → 解码返回。 坑：默认没有连接超时/读超时配置（要显式配 connectTimeout/readTimeout，否则线程被拖死）；GET 传对象要 @SpringQueryMap；文件上传要单独配 Encoder；feign.hystrix.enabled 已改名 spring.cloud.openfeign.circuitbreaker.enabled。

Q107 ★ Gateway 的三大核心概念与过滤器顺序

🗣 人话：Route 是「什么请求转给谁」，Predicate 是「凭什么判断」，Filter 是「路上顺手干点啥」。多个 Filter 像洋葱：进去按顺序一层层进，出来反着出。网关是整个系统的门，里面千万别写阻塞代码，一堵全堵。

要点：Route（id + uri + predicates + filters）、Predicate（断言，匹配请求）、Filter（GatewayFilter 单路由 / GlobalFilter 全局）。 执行顺序：order 小的先执行 pre，后执行 post（洋葱模型）。自定义全局鉴权常用 GlobalFilter + Ordered，注意不要在 Gateway 里做阻塞调用（WebFlux 线程模型，阻塞会拖垮整个网关）。

Q108 Spring Boot 启动慢怎么优化？

🗣 人话：先看自动配置报告，把用不上的 starter 删了；再查有没有 @PostConstruct 里发远程请求；还慢就上 CDS 或者原生镜像。lazy-initialization 能快，但会把错误推迟到第一次调用，生产慎用。

要点：--debug 看自动配置报告；关掉不用 starter；spring.main.lazy-initialization=true（慎用，把错误推迟到首次调用）；减少 @ComponentScan 范围；proxyBeanMethods=false；CDS/AOT（Boot 3 + GraalVM 原生镜像，启动到毫秒级）；排查 BeanPostProcessor 过多、@PostConstruct 里有远程调用。

八、消息队列（8 题）

🗣 人话版：消息队列就是饭店的传菜口：厨师做好放上去，服务员自己来取，两边不用互相等。它的毛病也都是传菜口的通病——菜会不会掉（丢消息）、会不会上两遍（重复消费）、会不会排错队（顺序）、堆太多怎么办（堆积）。

Q109 ★ Kafka、RocketMQ、RabbitMQ 怎么选？

🗣 人话：要吞吐、日志埋点选 Kafka；要事务消息、延迟消息、重试死信齐全选 RocketMQ（电商交易首选）；要路由灵活、量不大选 RabbitMQ。选型就看四件事：量、可靠性、有没有延迟/事务需求、团队能不能运维。

要点：

  • Kafka：吞吐最高（百万级），顺序写 + 零拷贝 + 批量，适合日志/埋点/流计算；但延迟消息、事务消息、消息重试、死信支持弱，topic 多了性能下降。
  • RocketMQ：阿里开源，事务消息、延迟消息（18 个等级）、消息重试 + 死信、消息轨迹齐全，适合电商交易类业务；Java 技术栈友好。
  • RabbitMQ：Erlang，路由灵活（Exchange 四种），低延迟，但堆积能力弱（百万级就吃力），适合业务解耦、中小规模。 选型看：吞吐、可靠性、是否有延迟/事务需求、团队运维能力。

Q110 ★ 如何保证消息不丢？

🗣 人话：三关都要守住：发的确认发出去了、Broker 确认落盘了、消费端确认处理完了才 ACK。最后一层兜底永远是「本地消息表 + 定时对账」，因为再可靠的 MQ 极端情况下也会丢。

要点：三段都要保证。

  • 生产端：同步发送 + 重试，RocketMQ 用 sendStatus=SEND_OK 判断；Kafka acks=all + retries。
  • Broker：刷盘策略（RocketMQ 同步刷盘 SYNC_FLUSH；Kafka min.insync.replicas>=2 + replication.factor>=3）。
  • 消费端：手动 ACK，业务处理成功后再提交 offset，失败进重试队列。 最终兜底：本地消息表 + 定时对账（不丢的最后一层）。

Q111 ★ 如何保证不重复消费？幂等怎么做？

🗣 人话：MQ 只能保证「至少一次」，重复一定会发生，所以只能在消费端做幂等：唯一索引、状态机、Redis 记 messageId。注意别「先占位后处理」——处理失败消息就被吞了，得处理成功再记。

要点：MQ 只能保证 at least once，重复不可避免，只能消费端幂等。 方案：① 唯一索引（DB 兜底，最可靠）；② Redis SETNX 记录 messageId（注意设置过期，且要在业务成功后写）；③ 状态机（只允许 待支付 → 已支付，重复消息直接被状态拒绝）；④ 版本号/乐观锁。 ⚠ SETNX 先占位 有风险：业务失败但占位成功 → 消息被吞。正确顺序是业务成功后记录，或用"消费中/已消费"两阶段状态。

Q112 ★ 如何保证消息顺序？

🗣 人话：全局有序等于单队列单消费者，吞吐直接没了，一般没人这么干。实际只要「同一个订单/同一个用户」有序：按业务 key 发到同一个分区或队列，消费端同一个 key 串行处理。

要点：全局顺序 = 单队列单消费者（吞吐极低），一般只要局部顺序（同一订单/同一用户）。 Kafka：同一 partition（key 相同 hash 到同一分区）+ 单消费者单线程消费；RocketMQ：顺序消息（MessageQueueSelector 按业务 key 选队列）+ MessageListenerOrderly。 消费端并行会破坏顺序 → 用内存队列按 key 分发给不同 worker，同 key 串行。

Q113 ★ 消息堆积怎么处理？

🗣 人话：先搞清楚为什么堆——消费者挂了、变慢了、还是有死循环一直重试。然后临时加消费者（Kafka 消费者不能超过分区数）、提高批量、把非核心消息先转存走，实在不行丢掉日志类消息。平时就要盯 lag 和消费耗时。

要点：先定位原因（消费者挂了/变慢/流量突增/死循环重试）。 处理：① 临时扩容消费者（注意分区数上限，Kafka 消费者数 ≤ 分区数）；② 提升消费能力（批量拉取、异步化、SQL 批量写）；③ 降级：把消息转存到临时 topic/DB，先让队列恢复；④ 丢弃非核心消息（日志类）；⑤ 事后补偿。 预防：监控 lag、消费耗时打点、消费者要有超时和熔断（下游挂了一个消费者能拖死整个 topic）。

Q114 RocketMQ 事务消息原理

🗣 人话：先发一条「半消息」（消费者看不见），然后执行本地事务，成功了才让它变成真消息；要是中途进程挂了，Broker 会回来问「你那事儿到底成没成」。就是为了让「改库」和「发消息」要么都成、要么都不成。

要点：发 半消息（half message，对消费者不可见） → 执行本地事务 → 返回 COMMIT/ROLLBACK → 若没回（进程挂了），Broker 回查生产者的 checkLocalTransaction → 决定提交或回滚。 作用：解决"本地事务与发消息"的原子性。不足：回查最多 15 次，仍可能不一致，需要对账兜底。

Q115 延迟消息怎么实现？

🗣 人话：RocketMQ 4.x 只有 18 个固定档位，5.0 才支持任意时间；RabbitMQ 用「消息过期 + 死信队列」凑，但会队头阻塞；Kafka 原生没有，得自己搭。订单 30 分钟关单就是它的经典用法。

要点：RocketMQ 4.x 固定 18 个等级（1s~2h）；5.0 支持任意时间（定时消息，时间轮）。RabbitMQ 用 TTL + 死信队列（注意队头阻塞问题）或延迟插件。Kafka 原生不支持，要自建时间轮/多级 topic。 业务场景：订单 30 分钟未支付关闭。

Q116 消息队列的作用与引入成本

🗣 人话：好处是解耦、异步、削峰；坏处是「本来一个函数调用的事，现在要考虑丢、重、乱序、堆积、事务一致」。所以只把非核心、能补偿的环节异步，下单扣库存这种核心链路别乱异步。

要点：解耦、异步、削峰填谷。 成本：系统复杂度上升（重复、丢失、顺序、堆积）、一致性问题（本地事务与消息）、运维成本、链路变长排查难。 原则：核心链路（下单扣库存）不要为了"看起来高级"异步化；只把非核心、可补偿的环节异步。

九、分布式与微服务（14 题）

🗣 人话版：一个系统扛不住了就拆成好几个，拆完就多了新麻烦：它们在哪儿（注册中心）、怎么找到彼此（RPC）、一个挂了怎么不连累别人（熔断限流）、数据怎么对得上（分布式事务）。答这章先讲「拆开之后多了什么麻烦」，再讲方案。

Q117 ★ CAP 与 BASE

🗣 人话：网络一定会断，所以 P 必须保；剩下就在「要一致」和「要可用」之间选。BASE 就是「先能用，晚点对上账也行」，大部分业务都这么干。Eureka 选可用（可能读到旧实例），ZK 选一致（选举时不可用），Nacos 可以切。

要点：CAP 三者不可同时满足（P 必须保，所以在 C 和 A 之间取舍）；BASE（基本可用、软状态、最终一致）是工程解法。 实践：注册中心 Eureka 是 AP（可用性优先，可能读到旧实例）、ZooKeeper 是 CP（选举期间不可用）、Nacos 可切换。业务系统多数选 AP + 最终一致。

Q118 ★ 分布式事务方案怎么选？

🗣 人话：能用「最终一致 + 对账」就别上强一致。方案从重到轻：2PC（强一致但慢、会阻塞）、TCC（性能好但要写三套接口，还得防悬挂防空回滚）、Saga（长流程每步带补偿，但没有隔离性）、本地消息表/事务消息（最常用）、Seata AT（自动生成反向 SQL，但有全局锁）。跨行转账最好放同一个库用本地事务。

要点：

  • 2PC/XA：强一致，性能差、阻塞、协调者单点，适合内部短事务、低并发。
  • TCC：业务补偿，性能好，但要写 Try/Confirm/Cancel 三套，防悬挂、空回滚、幂等三大坑。
  • Saga：长事务、每步有补偿，适合跨服务长流程，无隔离性。
  • 本地消息表 / 事务消息：最终一致，最常用（下单成功后发消息扣积分）。
  • Seata AT：自动生成 undo log 反向补偿，全局锁会降低并发，适合不想改业务代码的场景。 结论：能用最终一致就别用强一致；跨行转账这类必须强的，就在同一个库用本地事务。

Q119 ★ 分布式锁的三种实现对比

🗣 人话：Redis 快，但主从切换那一瞬间可能两把锁；ZK 强一致，但慢；DB 最简单也最慢。资金这种宁可慢也不能错的，用 ZK 或 DB 唯一索引。

要点：Redis（性能最好，SETNX + Lua + 看门狗，主从切换可能丢锁）；ZooKeeper（临时顺序节点，强一致，Watch 监听前一个节点，性能低于 Redis）；DB（唯一索引/for update，简单但性能差）。 选型：互斥但可容忍极小概率失效 → Redis；绝对互斥（如资金） → ZK/DB。

Q120 ★ 限流算法有哪几种？

🗣 人话：固定窗口简单，但临界点会放过双倍流量；滑动窗口平滑，但要用 Redis 存一堆时间戳；漏桶是「匀速滴水」，挡不住突发；令牌桶是「平时攒着，忙时能花」，最常用。

要点：固定窗口（临界点双倍流量）、滑动窗口（Redis ZSet 或分桶计数，平滑但有内存成本）、漏桶（恒定速率，抗突发差）、令牌桶（允许一定突发，最常用，Guava RateLimiter、Sentinel 的 Warm Up/匀速排队）。 分布式限流用 Redis + Lua（原子）或 Sentinel 集群流控；单机用 Guava。限流要配合降级，否则只是把请求拒掉。

Q121 ★ 熔断、降级、隔离的区别

🗣 人话：熔断是「你老出错，我先不找你了」，保护的是调用方；降级是「你不干了我给个兜底答案」；隔离是「每个下游一个独立池子」，一个淹了不连累别人。

要点：熔断（失败率/慢调用比例超阈值 → 打开 → 半开试探 → 关闭，保护调用方）；降级（返回兜底数据/缓存/默认值）；隔离（线程池隔离/信号量隔离，防止一个依赖拖垮全部）。 Sentinel 核心：QPS/线程数 限流、慢调用比例/异常比例/异常数 熔断、热点参数限流、系统自适应保护。

Q122 ★ 服务雪崩是怎么发生的？怎么防？

🗣 人话：一个下游变慢 → 调它的线程全卡住 → 线程池满 → 我也变慢 → 上面也被拖死，一层层往上炸。防线是：超时必须设（而且要比上游短）、重试要克制、熔断、每个依赖独立线程池、限流、兜底。

要点：某个下游变慢 → 调用方线程池被占满 → 调用方也不可用 → 逐级向上扩散。 防御：超时（必须设，且要小于上游超时）、重试要克制（重试放大流量，只对幂等且非超时错误重试）、熔断、舱壁隔离（每个依赖独立线程池）、限流、降级兜底、链路压测。

Q123 ★ 接口幂等怎么做？

🗣 人话：最可靠的永远是数据库唯一索引——并发再高，也只有一个能插进去。其他（token、SETNX、状态机）都是辅助。支付回调、退款、下单、MQ 消费，这几个场景必须做。

要点：唯一索引（最可靠）、Token 机制（先取 token，提交时校验并删除）、Redis SETNX 业务唯一键、状态机（只允许特定状态流转）、数据库乐观锁版本号、防重表。 注意：select 再 insert 有并发窗口，必须靠唯一索引兜底。MQ 消费、支付回调、退款、下单是幂等必做场景。

Q124 ★ 分布式 ID 与号段模式

🗣 人话：一次从数据库领 1000 个号放内存慢慢发，用完再领，数据库压力直接除以一千。双 buffer 是「快用完时提前去领下一段」，免得用户等着。雪花最怕服务器时钟往回跳。

要点：见 Q69。号段模式（Leaf-segment）：一次从 DB 取 1000 个 ID 放内存，用完再取，DB 压力降低 1000 倍；双 buffer 避免取号段时阻塞。雪花算法要处理时钟回拨（拒绝/等待/用历史最大 ID + 序列）。

Q125 ★ 服务注册与发现原理

🗣 人话：服务起来就报到，消费者拉一份名单存本地，之后靠推送或定时更新，心跳停了就摘掉。上线要注意：先摘流量再停服务，不然总有请求打到已经停的机器上。

要点：服务启动注册（临时节点/心跳），消费者拉取实例列表并本地缓存，定时/推送更新。健康检查：心跳续约（Nacos 5s 一次，15s 不健康，30s 剔除）、ZK 临时节点会话。 注意：下线要先摘流量再停服务（优雅停机 server.shutdown=graceful + 主动注销），否则有请求打到已停实例。

Q126 ★ 链路追踪怎么实现？

🗣 人话：一个请求从头到尾给个 TraceId，每过一个服务再给个 SpanId，父子串起来就是一棵调用树。难点在传递——HTTP header 能带、MQ 能带，线程池得自己包一层，不然异步一断就断了。

要点：TraceId（全局唯一）+ SpanId（调用片段）+ ParentSpanId 串成树。传递：HTTP header（traceparent）、MQ 消息属性、线程池（要包装 Runnable 传递上下文，否则异步断链）。 落地：SkyWalking（字节码增强，无侵入）/ Zipkin + Sleuth（需埋点）/ OpenTelemetry（标准）。日志里打 TraceId 是最低成本的排查手段。

Q127 ★ 配置中心要解决什么问题？

🗣 人话：配置集中放、改完能实时推、能灰度能回滚。坑是：线程池、连接池这种已经初始化好的东西，改配置不会自动生效，得自己重建。配置推错比代码 bug 更致命，所以必须灰度。

要点：集中管理、动态刷新（@RefreshScope / Nacos @NacosValue）、灰度发布、版本回滚、权限审计、敏感配置加密。 坑：动态刷新对连接池/线程池这类已初始化对象无效（要手动重建）；配置推错比代码 bug 更致命，必须灰度 + 快速回滚。

Q128 ★ 灰度发布 / 蓝绿部署怎么做？

🗣 人话：新版本先放一台，按用户 ID 或请求头把一小部分流量导过去，盯着错误率和耗时，没问题再加。前提是新老版本能共存：数据库只加字段不删字段、接口向后兼容。

要点：按请求头/用户 ID/比例路由（Gateway + 注册中心元数据 version）；新版本先放 1 台，观察错误率和 RT，逐步放量。 能力要求：数据库兼容（新旧版本共存，加字段不删字段）、接口向后兼容、可快速回滚。

Q129 ★ 微服务拆分的边界怎么定？

🗣 人话：按业务拆，别按技术拆（不要一个 service 层一个服务）。标准是：高内聚、团队自己管自己、数据不共享、改一个需求只动一个服务。拆完还天天五个服务一起发版，那就是「分布式单体」。

要点：按业务能力/领域（DDD 限界上下文）拆，不是按技术分层拆。原则：高内聚低耦合、团队边界（康威定律）、数据独立（不共享库）、变更频率一致。 反模式：分布式单体（服务拆了但强耦合、共享数据库、每次改需求要同时发 5 个服务）。

Q130 为什么微服务不建议共享数据库？

🗣 人话：共享库等于「偷偷耦合」——你想改表结构得问一圈人，想扩容也扩不了。正确做法是每家有自己库，要数据走接口或者冗余一份。

要点：共享库 = 隐式耦合，无法独立演进/扩容/降级，事务边界混乱。正确做法：每服务独立库，跨服务通过 API/消息，查询场景用数据冗余 + 宽表 + ES。

十、系统设计场景题（10 题）

🗣 人话版：场景题没有标准答案，面试官看的是你会不会一层层削流量：前端挡一批、网关限一批、缓存扛一批、队列缓一批，最后才轮到数据库。答题顺序永远是：先算量级，再画漏斗。

Q131 ★ 设计一个秒杀系统

🗣 人话：核心是「一层层削流量」：前端按钮置灰、网关限流、Redis 先扣库存（扣到负数就说明没了）、扣成功发 MQ 慢慢下单、数据库再用 where count>0 兜底。绝不能超卖，也不能少卖（少卖靠对账回补）。

要点（按流量漏斗讲）：

  1. 前端：按钮置灰、答题/验证码防刷、静态资源 CDN。
  2. 网关层：限流（按用户/IP/商品）、黑名单、库存预热。
  3. 应用层：Redis 预扣库存（DECR 原子，返回 <0 则失败并回补）或 Lua 脚本（判断+扣减原子），扣成功发 MQ 异步下单。
  4. DB 层：update stock set count=count-1 where id=? and count>0（乐观锁兜底，绝不能超卖），订单表分库分表。
  5. 防超卖：Redis 扣减 + DB 条件更新双保险；防少卖：MQ 消费失败重试 + 定时对账回补。
  6. 其他：一人一单（Redis Set 去重 + DB 唯一索引）、接口幂等、热点隔离（单独集群）。

Q132 ★ 订单 30 分钟未支付自动关闭，怎么做？

🗣 人话：主力用延迟消息，30 分钟后投递过来关单；但消息可能丢，所以再加一个定时扫表兜底；关单前一定再查一次支付状态，避免「刚付完就被关」。

要点：

  • 延迟消息（RocketMQ 定时消息）：简单可靠，但要处理消息丢失 → 配合定时扫表兜底（每分钟扫"待支付且创建时间 < now-30min"的订单，走游标 + 索引避免慢查询）。
  • Redis 过期监听：不可靠（过期事件不保证、可能延迟），不要单独用。
  • 时间轮（Netty/Redisson RDelayedQueue）：单机场景。
  • 定时任务分片（XXL-JOB 分片广播）：数据量大时。 标准答案：延迟消息为主 + 定时扫表兜底 + 关闭前查一次支付状态（防并发）。

Q133 ★ 设计一个短链接系统

🗣 人话：发一个号 → 转成 62 进制（大小写字母加数字）→ 存映射 → 访问时查出来 302 跳过去。用 302 不用 301，是因为 301 会被浏览器记住，你就统计不到点击了。

要点：发号（雪花/号段/Redis INCR）→ Base62 编码（6 位约 568 亿）→ 存 short → long 映射（MySQL + Redis 缓存）→ 跳转用 301/302（301 浏览器缓存减少服务压力但无法统计；302 可统计，一般用 302）。 优化：布隆过滤器防穿透、热点短链本地缓存、预生成号段减少 DB 交互。

Q134 ★ 设计一个排行榜

🗣 人话：ZSet 天生就是排行榜：加分 ZINCRBY、取前 N ZREVRANGE、查排名 ZREVRANK。同分要按「谁先到」排，就把时间戳编进分数里。榜特别大就分桶，每桶取前 N 再合并。

要点：Redis ZSet（ZINCRBY 加分、ZREVRANGE 取 TOP N、ZREVRANK 查排名），O(logN)。 大规模：按周期分 key（日榜/周榜/总榜），榜单分段缓存（TOP 100 直接缓存，101~1000 懒加载），超大数据用分桶 + 归并（每桶 TOP N 再合并）。 注意：同分排序（score 拼时间戳，score * 1e10 + (MAX_TS - ts)）。

Q135 ★ 设计一个分布式计数器（点赞/阅读量）

🗣 人话：Redis INCR 最快，但一个热点 key 会被打爆，所以拆成十个 key 各加各的，读的时候加起来。再定时批量落库，别每次都写 DB。UV 去重用 HyperLogLog，12KB 能估上亿。

要点：Redis INCR（热点 key 用分片计数 key:{0..9}，读时求和）→ 定时批量落库（每 5s 聚合一次，减少 DB 压力）→ 用户维度去重用 Set/Bitmap/HyperLogLog（UV 用 HLL，精确去重用 Bitmap 按用户 ID 偏移）。 一致性：允许最终一致，Redis 挂了会丢增量，重要数据要 WAL 或本地缓冲。

Q136 ★ 大文件上传 / 断点续传

🗣 人话：切成 5MB 一块，先算文件 MD5 问服务端「传过没」（秒传），传过的块跳过（断点续传），传完按序号合并再校验一次。合并很吃 IO，放异步做。

要点：分片（固定 5MB，前端切片）→ 秒传（文件 MD5 查是否已存在）→ 断点续传（服务端记录已上传分片，前端跳过）→ 分片并行上传 → 合并（按序号合并，校验整体 MD5）→ 存对象存储（OSS/MinIO）。 坑：合并时 IO 大要异步；分片临时文件要清理；并发上传同一文件要加锁。

Q137 ★ 接口 RT 从 200ms 涨到 2s，怎么排查？

🗣 人话：先分清是「所有人都慢」还是「只有一部分慢」：平均慢多半是自己资源问题，P99 慢多半是某个下游或个别数据。然后按链路一段段量：应用、DB、下游、GC、连接池、网络。

要点：按链路分段：① 看监控（应用 RT、下游 RT、DB 慢查询、GC）→ ② 有没有发版/配置变更/流量突增 → ③ 线程栈（jstack 看是不是都卡在某个下游）→ ④ 慢 SQL / 索引失效 / 数据量增长 → ⑤ 连接池打满（hikari 指标）→ ⑥ GC 停顿（jstat）→ ⑦ 网络/ DNS。 先定位是"整体变慢"还是"部分请求慢"（P99 还是均值），这决定了方向。

Q138 百万数据导出 Excel 怎么做？

🗣 人话：别同步导，先提交任务再让用户回来下载；写文件要流式写，别把百万行全堆内存；查数据用游标 where id > 上次的 limit 5000，别用 limit 翻页。

要点：异步导出（提交任务 → 返回 taskId → 轮询/站内信下载），流式写（EasyExcel SXSSF/EasyExcel 的 WriteHandler，不要 XSSFWorkbook 全内存），分页/游标查（where id > lastId limit 5000，避免深分页和全量加载），临时文件存 OSS + 过期清理。 坑：一次 select 百万行会 OOM；ResultSet 必须流式（MyBatis fetchSize + ResultSetType.FORWARD_ONLY）。

Q139 多级缓存怎么设计？

🗣 人话：越靠近用户的越快也越小：浏览器/CDN → Nginx → 应用本地缓存（Caffeine）→ Redis → DB。本地缓存最麻烦的是「别的机器改了，我这台不知道」，所以要用 MQ 广播失效或者设很短的过期时间。

要点：浏览器/CDN → Nginx 本地缓存 → 应用本地缓存（Caffeine，纳秒级，容量有限） → Redis → DB。 关键问题：一致性（本地缓存用 MQ 广播失效，或短 TTL 容忍）、容量与淘汰（W-TinyLFU）、热点探测（访问计数超阈值才提升到本地）。 适合极热且读多写少的数据（商品详情、配置、字典）。

Q140 怎么设计一个高可用的支付回调？

🗣 人话：验签 → 幂等 → 记流水 → 立刻回 success（别在人家的回调里做重活，不然他超时重试更乱）→ 异步处理业务 → 失败重试 → 再加个定时查单兜底。核心认知：回调会重复、会乱序、也会丢。

要点：验签 → 幂等（唯一索引 + 状态机）→ 落库（回调流水表）→ 立即返回 success（不要在校验里做重业务，避免对方超时重试）→ 异步处理业务 → 失败进重试队列 → 主动查单兜底（定时查"处理中"的订单）。 关键：回调可能重复、可能乱序、可能丢失，三者都要处理。

十一、线上问题排查（8 题）

🗣 人话版：排查就一个套路：先看范围（全挂还是部分）、再看改动（刚发版没）、再看资源（CPU/内存/IO/连接数）、最后才看线程栈和日志。记住先止血再治病——回滚、限流、扩容，别一边着火一边找起火点。

Q141 ★ 接口超时但日志没报错，怎么查？

🗣 人话：日志没报错，说明请求还没走到报错那步，或者卡在等资源。先 jstack 看线程卡哪儿：等锁、等连接池、还是等下游。还有个常被忽略的：客户端超时比服务端短，服务端还在慢慢算，日志当然正常。

要点：① jstack 看线程卡在哪（BLOCKED 找锁、WAITING 找 park）；② arthas trace 看方法耗时分布、watch 看入参出参；③ 连接池指标（HikariCP activeConnections/pendingThreads）；④ 下游依赖 RT（Feign/Sentinel 面板）；⑤ GC 日志；⑥ 是不是客户端超时时间 < 服务端处理时间（日志正常但调用方已断开）。

Q142 ★ 服务突然不可用（大量 502/超时）的排查顺序

🗣 人话：先看有没有刚发版/改配置，再看流量是不是突增，再看资源（CPU、内存、连接数、句柄），再看依赖（DB/Redis/MQ），最后看注册中心是不是把实例全摘了。顺序很重要：先止血（回滚、限流、扩容），再找根因。

要点：① 看变更（发版、配置、扩容）；② 看入口 QPS（突增？被刷？）；③ 看资源（CPU/内存/连接数/磁盘/句柄 ulimit）；④ 看依赖（DB/Redis/MQ/第三方）；⑤ 看注册中心（实例是否被全部摘除，心跳是否正常）；⑥ jstack 看线程数（是否爆线程）。 先止血（回滚/限流/扩容/切流），再定位根因。

Q143 Connection is not available, request timed out 怎么解决？

🗣 人话：报这个错就是「连接都借出去了，还有人排队等」。常见原因：慢 SQL 占着不还、事务里包了 RPC（等下游时还攥着连接）、代码借了没还。先查慢 SQL 和事务范围，别一上来就调大连接池——数据库那头才是真上限。

要点：HikariCP 连接池耗尽。原因：慢 SQL 占用连接、事务范围过大（把 RPC 包进事务）、连接泄漏（手动 getConnection 未 close）、并发超过池大小。 排查：show processlist 看 DB 侧连接、Hikari 的 metricRegistry 指标、leakDetectionThreshold 开泄漏检测。 解决：缩短事务、加索引、池大小 = (CPU核数*2 + 磁盘数) 经验值 + 压测、绝不无限加大连接池（DB 连接数才是瓶颈）。

Q144 数据库 CPU 100% 怎么办？

🗣 人话：先 show processlist 找跑最久的那条 SQL，能杀就杀（止血），再看是不是全表扫、统计信息过期、还是突然来了波流量。加索引、改 SQL、限流，最后才考虑升配。

要点：① show processlist 找长时间运行的 SQL；② show engine innodb status 看锁等待；③ 慢日志 TOP；④ 杀掉非核心慢查询止血；⑤ 加索引/改写/限流；⑥ 检查是否全表扫描或统计信息过期（analyze table）；⑦ 主从分离把读流量挪走。

Q145 主从延迟导致"数据刚写就读不到"，怎么解？

🗣 人话：写完立刻读，就读主库——最简单也最有效。可以在拦截器里打个标记，写完后 1 秒内强制走主库。别为了这点一致性搞一堆复杂路由。

要点：见 Q72。补充应用层方案：写后一段时间内强制走主库（拦截器标记 forceMaster，如 1s 内）、从库延迟监控动态路由、关键业务读主库。

Q146 线程数暴涨 / unable to create native thread

🗣 人话：先数一下到底多少线程、都是什么状态（jstack 里统计）。常见原因：用了 newCachedThreadPool 或每个请求 new 一个线程、连接没复用、-Xss 太大导致栈内存不够。治本是统一线程池 + 有界队列 + 复用连接。

要点：jstack | grep java.lang.Thread.State | sort | uniq -c 统计线程数与状态；ls /proc/<pid>/task | wc -l 看真实线程数。 原因：线程池被无界创建（newCachedThreadPool、每次请求 new Thread）、连接未复用、ulimit -u 限制、-Xss 太大导致栈内存不够。 解决：统一线程池 + 有界队列 + 复用连接 + 调 ulimit/-Xss 256k。

Q147 缓存与 DB 数据不一致怎么排查？

🗣 人话：先分清是「并发写导致的」还是「删缓存失败导致的」，加个日志就知道。然后检查有没有写成「先删缓存再改库」（错的），有没有主从延迟把旧值又读回缓存。修法：延迟双删、订阅 binlog、缓存带版本号。

要点：① 确认是并发写导致还是删缓存失败（加日志）；② 检查是否有先删后写的错误顺序；③ 检查双写并发（同一 key 两个线程，一个旧值后写回）；④ 检查主从延迟（读从库的旧值回填缓存）；⑤ 修复：延迟双删、binlog 订阅、加锁、缓存加版本号。

Q148 线上 Full GC 频繁但内存不高，为什么？

🗣 人话：内存不高还频繁 Full GC，八成不是堆的事：元空间不够（动态生成类太多）、有人显式调 System.gc()、大对象直接进老年代、或者年轻代太小导致对象很快晋升。先看 gc.log 里 Full GC 的触发原因，一眼就能定方向。

要点：① 元空间不足（动态类/CGLIB/Groovy 脚本）；② 显式 System.gc()（RMI、DirectByteBuffer 回收触发）；③ 大对象直接进老年代导致老年代快速填满；④ Humongous 分配（G1 下大对象占 Region）；⑤ 年轻代太小导致对象快速晋升。 看 gc.log 里 Full GC 的触发原因（Allocation Failure / Metadata GC Threshold / System.gc()）——这一步就能定方向。

十三、MyBatis（6 题）

🗣 人话版：MyBatis 就是个SQL 翻译机：你只写接口，它偷偷生成实现类，把你的「方法名」翻译成一条 SQL。这章重点是两件事：缓存什么时候会骗你（二级缓存跨表会读到脏数据）、${} 为什么危险（直接拼字符串，等于把大门钥匙递给用户）。

这一章是看你旧资料时发现的口子——你原来的笔记里 MyBatis 只有"#{}/${}"一句，但 6 年面试问的是代理机制和缓存边界。

Q157 ★ #{} 与 ${} 的区别，什么时候必须用 ${}

🗣 人话：#{} 是「占位符」，SQL 先定好型再填值，天然防注入；${} 是「直接拿字符串拼进去」，等于把 SQL 交给用户写。表名、列名、排序字段这种没法用占位符的地方才用它，而且必须白名单校验。like 也别用 ${}，用 concat。

要点：#{} 走 PreparedStatement 占位符，预编译、防注入、能复用执行计划；${} 是字符串拼接，直接进 SQL。 必须用 ${} 的场景：表名、列名、排序字段（预编译不支持标识符占位）、order by ${sort}。这时候必须自己做白名单校验，否则就是注入口子。 ⚠ 追问："为什么 like 要用 #{}"——like concat('%', #{kw}, '%')，别写成 '%${kw}%'。

Q158 ★ 一级缓存与二级缓存

🗣 人话：一级缓存是「同一个 SqlSession 内」的，Spring 下每次请求一个 session，基本等于没有。二级缓存是 namespace 级的，问题大：跨表更新它不知道、多台机器各存各的、存的是对象引用还可能被改脏。生产建议直接关掉，要缓存上 Redis。

要点：

  • 一级：SqlSession 级，默认开启，Executor 里一个 PerpetualCache 的 HashMap。同一个 SqlSession 内两次相同查询只打一次库。commit/rollback/close、执行 update、flushCache 都会清空。Spring 下每次请求一个 SqlSession，基本等于没用。
  • 二级：namespace 级，需 <cache/> 或 @CacheNamespace 开启，要 commit 才写入，多个 SqlSession 共享。
  • 二级缓存的坑：跨 namespace 更新不会清对方的缓存（多表关联必脏）、分布式下各节点缓存不一致、缓存的是对象引用（可能被业务改脏）。生产建议：默认关掉二级缓存，要缓存用 Redis（细粒度可控）。

Q159 Mapper 接口没有实现类，为什么能注入？

🗣 人话：启动时扫描接口，给每个接口生成一个 JDK 动态代理；调用时用「接口全名 + 方法名」拼一个 statementId，再到 XML 里找对应的 SQL。所以接口名必须等于 namespace，方法名必须等于 id，差一个字就报 BindingException。

要点：MapperScannerConfigurer/@MapperScan 扫描接口 → 生成 BeanDefinition（MapperFactoryBean）→ 注册时用 JDK 动态代理生成 MapperProxy。 调用时 MapperProxy.invoke 用接口全限定名 + 方法名拼出 statementId，去 Configuration.mappedStatements 找 MappedStatement，再交给 Executor 执行。所以接口名必须和 XML 的 namespace 一致，方法名必须和 id 一致，改一个就报 BindingException。

Q160 ★ 插件（拦截器）原理，PageHelper 怎么实现的？

🗣 人话：MyBatis 在四个关键位置留了口子：执行器、SQL 构造器、参数处理器、结果集处理器。插件就是在这四个地方套一层代理。PageHelper 拦的是执行器：先查一次总数，再把你的 SQL 改成带 limit 的。它用 ThreadLocal 传分页参数，所以忘了 clear 就会「下一次查询莫名其妙也分页」。

要点：MyBatis 允许拦截 4 大对象：Executor（执行器）、StatementHandler（SQL 构建）、ParameterHandler（参数）、ResultSetHandler（结果集）。 启动时把 Interceptor 组成责任链，用 JDK 动态代理包一层，Plugin.wrap() 按 @Intercepts 的签名决定是否代理。 PageHelper 就是拦截 Executor.query：先查 count，再把原 SQL 改写成 limit ?,?（用 ThreadLocal 传分页参数），最后在 finally 里 clearPage()。这就是"分页参数没清导致下一次查询莫名分页"的根因。

Q161 延迟加载与 N+1 问题

🗣 人话：延迟加载是「先给你个空壳，你真用到里面的数据才去查」。N+1 是「查 100 个订单，又挨个查了 100 次用户」，一共 101 次。解法是一次 join 查完，或者先把 100 个用户 id 收集起来一次 in 查回来。别在 for 循环里调 Mapper。

要点：lazyLoadingEnabled=true + aggressiveLazyLoading=false（3.4.1 后默认 false，按需加载）。原理是给关联对象生成代理（Javassist/CGLIB），触发 getter 时才发 SQL。 N+1：查 100 个订单 → 每个订单再查一次用户 = 101 次。解决：fetchType="eager" 用 join 一次查完、<collection> 嵌套结果映射、或业务层批量查（in）后内存拼装。别在循环里调 Mapper。

Q162 批量插入 1 万条怎么做最快？

🗣 人话：最快是一条 SQL 拼多个 values，但别拼太长（受 max_allowed_packet 限制），500~1000 条一批。JDBC batch 也行，但连接串必须开 rewriteBatchedStatements，不然它还是逐条发。循环单条最慢，别用。

要点：三种方式差距很大：

  1. foreach 拼 insert into t values (...),(...)：一条 SQL，最快，但SQL 长度受 max_allowed_packet 限制，建议 500~1000 条一批。
  2. ExecutorType.BATCH：JDBC 批量，需 rewriteBatchedStatements=true 才真正合并（否则还是逐条）。
  3. 循环单条 insert：最慢，别用。 实测经验：1w 条从 30s 降到 1s 以内很常见。注意事务别开太大（锁 + undo 膨胀）。

十四、Dubbo 与 Zookeeper（7 题）

🗣 人话版：Dubbo 是打电话：先查电话簿（注册中心）拿到号码，再拨号（长连接），对面总机（线程池）派个人接。ZK 是居委会：谁家有事大家投票，超过一半才算数——所以它慢但可靠，适合当裁判，不适合当仓库。

Q163 ★ Dubbo 的一次调用经过了哪些组件？

🗣 人话：你调的那个接口其实是个代理 → 它从注册中心给的名单里挑一台（先按规则过滤，再按负载均衡选）→ 过一串过滤器 → 用 Netty 长连接发出去 → 服务端线程池接住 → 反射调用真正的实现。链路上任何一环都能做文章。

要点：消费端持有代理（Proxy） → Cluster（容错，选一个 Invoker）→ Directory（服务列表，注册中心推送）→ Router（路由过滤，标签/灰度）→ LoadBalance（选一台）→ Filter 链（超时、限流、监控）→ Client（Netty 长连接）→ 服务端 Dispatcher 分发给线程池 → Invoker 反射调用。 服务暴露：ServiceConfig → Protocol.export → 启动 Netty → 注册到 ZK/Nacos。

Q164 ★ Dubbo SPI 与 JDK SPI 的区别

🗣 人话：JDK 的 SPI 是「一锅全端上来」，你想要哪个还拿不到；Dubbo 的是「报菜名，点哪个上哪个」，还支持按配置动态选（@Adaptive）、按分组自动激活（@Activate），还能注入别的扩展。Dubbo 的扩展性全靠它。

要点：JDK SPI 一次性加载所有实现（浪费）、不能按名取、无 IoC/AOP。 Dubbo SPI：按 key 加载（ExtensionLoader.getExtension("dubbo")）、懒加载 + 缓存、支持 @Adaptive 自适应扩展（运行时按 URL 参数选实现，如 protocol、loadbalance）、支持 @Activate 自动激活（Filter 分组）、支持 IoC（注入其他扩展）和 AOP（Wrapper 包装）。 配置：META-INF/dubbo/接口全限定名，内容是 key=实现类。

Q165 Dubbo 的负载均衡策略

🗣 人话：Random 是默认的，按权重随机（机器越强权重越大）；RoundRobin 是平滑轮询；LeastActive 是「谁手上活少给谁」；ConsistentHash 是「同一个参数永远打到同一台」，适合有本地缓存的场景。

要点：Random（默认，带权重，权重来自性能预热）、RoundRobin（平滑加权轮询，不是简单取模）、LeastActive（最少活跃调用，慢机器少接活）、ShortestResponse（最短响应，2.7+）、ConsistentHash（同一参数打到同一台，用于有状态/本地缓存）。 坑：ConsistentHash 默认只对第一个参数取 hash，要自定义 hash.arguments。

Q166 集群容错策略怎么选？

🗣 人话：读接口用 Failover（失败了换一台重试），写接口必须 Failfast 或 retries=0——超时重试十有八九会重复下单。这是 Dubbo 最容易踩的坑。

要点：Failover（默认，失败重试其他机器，适合幂等读）、Failfast（失败立刻报错，适合非幂等写）、Failsafe（忽略异常，用于日志）、Failback（失败后台重试，用于消息通知）、Forking（并行调 N 个取最快，浪费资源）、Broadcast（全部调用，用于缓存刷新）。 写操作必须关重试：retries=0，否则超时重试会导致重复下单。

Q167 ★ Dubbo 超时和重试的坑

🗣 人话：默认 1 秒超时、重试 2 次，也就是最多打三次。最坑的是「超时不等于没执行」：服务端还在扣钱，客户端已经重试了。所以写接口关重试，服务端超时设得比客户端长，再加幂等兜底。

要点：默认 timeout=1000ms、retries=2（总共 3 次）。超时不代表服务端没执行——服务端还在跑，消费端已超时重试 → 重复扣款。 原则：服务端超时时间 > 消费端超时时间（否则消费端先断，服务端白算）；写接口 retries=0；用幂等 + 唯一索引兜底；cluster=failfast。

Q168 ★ ZAB 协议与脑裂

🗣 人话：ZAB 就是「一个老大说了算，但必须过半小弟点头才算数」。网络一断可能出现两个老大，但少数派那边凑不够半数，什么也干不成，老大自己就退位了。所以 ZK 必须奇数台、至少 3 台。

要点：ZAB = 崩溃恢复（选主）+ 原子广播。写请求由 Leader 转成 proposal，超过半数 Follower ACK 后 commit。 与 Paxos 区别：ZAB 是主备模型（只有 Leader 处理写），为"顺序一致性"设计；Paxos 是去中心化的共识算法。 脑裂：网络分区导致出现两个 Leader（旧 Leader 以为自己还活着）。ZK 的防护是过半机制——少数派分区选不出 Leader，也提交不了任何写，Leader 会自杀。所以 ZK 集群必须是奇数且 ≥3。

Q169 ZK 分布式锁怎么做？它适合什么、不适合什么？

🗣 人话：每个人在 /lock 下建一个临时顺序节点，谁号码最小谁拿锁，其他人只盯着自己前一个（不是盯所有人，不然一释放全被叫醒）。会话断了节点自动消失，天然不会死锁。它强一致但慢，适合选主、配置这种低频场景，不适合当数据库和队列。

要点：临时顺序节点：/lock/order-0000001，谁序号最小谁持锁，其他节点监听前一个节点（不是监听父节点，避免羊群效应）。会话断开临时节点自动删除 → 天然防死锁。 适合：强一致、低并发的协调场景（选主、配置、分布式锁）。 不适合：高吞吐读写（写要过半同步，比 Redis 慢一个量级）、大数据量存储（不适合当 DB/队列）、频繁创建删除节点（watch 和会话开销大）。

Q170 ★ TCP 三次握手、四次挥手，为什么是 3 和 4？

🗣 人话：三次握手是「我能发你收得到吗 / 我收得到你也能发吗 / 好，开始」，两次不够是因为服务端要确认客户端收到了自己的回复。四次挥手是因为全双工：我说完了不代表你说完了，所以 ACK 和 FIN 得分开。

要点：三次是双方各自确认"我能发、你能收"，两次无法让服务端确认客户端收到了自己的 SYN（防止历史重复连接）。四次是因为 TCP 全双工，FIN 只表示"我没数据要发了"，对方可能还有数据，所以 ACK 和 FIN 要分开（被动方处理完才发 FIN）。 状态：SYN_SENT → ESTABLISHED；断开 FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED。

Q171 TIME_WAIT 过多 / CLOSE_WAIT 过多分别说明什么？

🗣 人话：TIME_WAIT 多，说明你自己在频繁主动断连接（短连接太多），用连接池就好；CLOSE_WAIT 多，说明对方断了你这边没 close，是代码漏关连接，只涨不降肯定是 bug。

要点：TIME_WAIT 在主动关闭方，持续 2MSL（60s），作用是让最后的 ACK 能重传 + 让旧连接的迷路报文消散。过多 → 短连接太多，解决：连接池、keep-alive、调 tcp_tw_reuse（别开 tcp_tw_recycle，NAT 下会丢包）。 CLOSE_WAIT 是被动关闭方没调 close() → 代码没关连接（连接泄漏），数量只涨不降就是 bug，lsof -p <pid> 查。

Q172 HTTP/1.1、HTTP/2、HTTP/3 的核心差别

🗣 人话：1.1 是一条车道串行跑，前面堵住后面全等；2 是拆成小包多路复用，一条连接跑多个请求，但 TCP 那头还是可能堵；3 直接换成 UDP 的 QUIC，把 TCP 的堵也绕开了。

要点：1.1 队头阻塞（一个连接串行处理请求）+ 文本协议 + 需 keep-alive；2 二进制分帧 + 多路复用（一个连接并行多流）、头部压缩（HPACK）、服务端推送，但TCP 层仍有队头阻塞；3 改用 QUIC（UDP），解决 TCP 层阻塞，弱网切换更快（0-RTT）。 实践：内部 RPC 用 HTTP/2 或 Dubbo 协议；对外静态资源上 CDN + HTTP/2。

Q173 HTTPS 握手到底加密了什么？

🗣 人话：非对称加密太慢，所以只用来「商量一把临时钥匙」，之后的数据都用这把对称钥匙加密。证书解决的是「对面是不是真的」，防中间人。ECDHE 还多一个好处：私钥以后泄露了，以前的流量也解不开。

要点：非对称加密只用来协商对称密钥（因为非对称太慢），后续数据用 对称加密（AES）。证书解决身份认证（CA 签名链），防中间人。 ECDHE 支持前向安全（私钥泄露也解不开历史流量），RSA 密钥交换不支持。所以现在都要求 ECDHE 套件。TLS1.3 把握手压到 1-RTT（甚至 0-RTT）。

Q174 ★ 线上排查常用的 Linux 命令（要能说出用哪个看什么）

🗣 人话：记住口诀：CPU 高看 top -Hp，内存涨看 jmap 和 dmesg（有没有被 OOM 杀掉），IO 高看 iostat，连不上看 ss 和 tcpdump，句柄不够看 lsof 和 ulimit。

要点：

  • CPU：top（1 看每核、H 看线程）、pidstat -u 1、vmstat 1（r 运行队列、cs 上下文切换）
  • 内存：free -h、pidstat -r、smem、dmesg | grep -i oom（看有没有被 OOM Killer 杀）
  • 磁盘 IO：iostat -x 1（%util、await）、iotop
  • 网络：ss -s、netstat -anp | grep ESTAB、ss -lnt（端口）、tcpdump -i eth0 port 8080 -w a.pcap
  • 文件/句柄：lsof -p <pid>、lsof -i:8080、ulimit -n、df -h、du -sh *
  • 日志：tail -f、grep -c、awk '{print $7}' access.log | sort | uniq -c | sort -rn | head 记住一句："CPU 高看 top -Hp，内存涨看 jmap/dmesg，IO 高看 iostat，连不上看 ss 和 tcpdump"。

Q175 Tomcat 的架构与关键参数

🗣 人话：Connector 负责收请求，Container 负责处理。三个关键数：maxThreads 是最多几个人干活，acceptCount 是门口能排多长的队（超了直接拒绝），maxConnections 是同时能接多少连接。接口里有阻塞调用时，maxThreads 就是并发上限，加机器比调参数管用。

要点：Server → Service → Connector（NIO，负责 IO）+ Container（Engine→Host→Context→Wrapper，负责业务），一个请求经 Connector 解析后交给 Container 的 Pipeline-Valve 责任链。 关键参数：maxThreads（默认 200，工作线程上限）、acceptCount（等待队列，默认 100，超了直接拒绝）、maxConnections（NIO 默认 8192）、connectionTimeout、minSpareThreads。 Spring Boot 里配：server.tomcat.threads.max / server.tomcat.accept-count / server.tomcat.max-connections。 坑：接口里有阻塞调用时，线程数就是并发上限，加机器比调参数有效；maxThreads 调到几千反而因为上下文切换变慢。

十六、Elasticsearch（4 题）

🗣 人话版：ES 是一本倒着查的书：普通数据库是「翻到第几页看写了啥」，ES 是「先查关键词索引，直接告诉你哪几页有这个词」。所以它搜得快，但写得慢一点，而且不是实时的（默认差 1 秒）。

Q176 倒排索引为什么快？

🗣 人话：普通数据库是「翻到第几页看写了啥」，ES 是先有一本「词 → 出现在哪几页」的目录，查词直接翻到页，所以搜得快。搜不到八成不是 ES 的问题，是分词器或者字段类型（text/keyword）配错了。

要点：正排是"文档 → 词"，倒排是"词 → 文档列表（含位置、词频）"，查词直接定位文档，不用扫全表。 结构：Term Dictionary（FST，有限状态转换器，压在内存里）+ Posting List（倒排表，FST 指向磁盘的 .tim/.doc），Posting List 用跳表支持快速求交集（AND 就是多个 posting list 求交）。 写入时分词（中文用 IK），所以"搜不到"通常是分词器/字段类型（text vs keyword）问题。

Q177 写入流程：为什么 ES 是"近实时"？

🗣 人话：写进去先放缓冲区加记日志，默认每秒刷一次生成新的小段，这时候才能被搜到——所以叫「近」实时。批量导入时把刷新关掉，导完再手动刷，能快好几倍。写完立刻要读，别指望 ES。

要点：写 buffer + translog（保证宕机不丢）→ 每 1s refresh 生成新 segment（此时才可被搜索，所以叫 near real-time）→ flush 落盘并清 translog → 后台 merge 合并小 segment（merge 很吃 IO，要限流）。 关键参数：refresh_interval（批量导入时设 -1 再手动 refresh，能快数倍）、translog.durability。 别用 ES 做实时强一致查询（默认 1s 延迟）；写完立刻要读，用 refresh=true（性能差）或读 MySQL。

Q178 深分页为什么慢？怎么解？

🗣 人话：from+size 是「每个分片都把前 N 条搬出来，协调节点再统一排序」，翻到第 1000 页等于搬了几十万条。用 search_after 拿上一页最后一条当书签，实时又没深度限制；导出用 scroll。

要点：from + size 需要每个分片都取 from+size 条再全局排序，翻到第 1000 页就是 1000×N 条数据在协调节点排序，内存和 CPU 双爆。 方案：scroll（快照，适合导出，占资源要手动清理）、search_after（用上一页最后一条的排序值做游标，推荐，实时且无深度限制）、限制最大页数。默认 index.max_result_window=10000，别乱调大。

Q179 MySQL 与 ES 的数据同步怎么做？

🗣 人话：双写简单但容易不一致；发 MQ 解耦但要处理顺序和重复；最省心的是 Canal 订阅 binlog，业务代码一行不用改，还天然有序。别忘了全量初始化 + 增量追平 + 对账。

要点：同步双写（简单但耦合、可能不一致、失败要补偿）→ MQ 异步（解耦，注意顺序和重复）→ Canal 订阅 binlog（推荐，业务无侵入，天然有序）。 必须考虑：全量初始化 + 增量追平、失败重试 + 对账、延迟（用户写完立刻搜不到 → 前端做乐观更新或读主库）、字段变更要重建索引（reindex）。

十七、设计模式与手撕代码（5 题）

要点：挑 3 个能讲出解决了什么痛点的：

  • 策略 + 工厂：替代大量 if-else 支付/优惠计算，新增渠道只加一个实现类（开闭原则）。
  • 模板方法：抽象类定义导入流程（校验 → 解析 → 落库 → 回调），子类只实现差异步骤。
  • 责任链：风控/审批/参数校验链，每个节点决定是否继续。
  • 建造者：复杂 DTO/查询条件构造（LambdaQueryWrapper 就是）。
  • 观察者/事件：Spring ApplicationEvent，下单后异步发通知。 加分：说"我们也刻意避免过度设计——三个分支以内直接 if-else，可读性优先"。

Q181 单例的 5 种写法，DCL 为什么要 volatile？

🗣 人话：DCL 为什么要 volatile？因为 new 一个对象分三步（分内存、初始化、把地址给变量），二三步可能被重排，别的线程就可能拿到「地址有了但还没初始化」的半成品。加 volatile 就是禁止这个重排。

要点：饿汉（简单但类加载即初始化）、懒汉（线程不安全）、DCL（volatile + 两次判空）、静态内部类（懒加载 + 线程安全，推荐）、枚举（《Effective Java》推荐，天然防反射和反序列化破坏）。 DCL 的 volatile 作用：instance = new Singleton() 分三步（分配内存 → 初始化 → 赋值引用），2 和 3 可能重排，导致别的线程拿到"非 null 但未初始化"的对象。

Q182 手写 LRU（高频手撕题）

🗣 人话：一个哈希表负责 O(1) 找到，一条双向链表负责「谁最久没用」，每次用过就挪到最前面，装满了从最后面踢。LinkedHashMap 开个开关就能白拿一个。

要点：HashMap + 双向链表，get 命中后把节点移到头部，put 满了删尾部。全部 O(1)。 Java 现成方案：LinkedHashMap(16, 0.75f, true) + 重写 removeEldestEntry，5 行搞定——面试时先说思路，再问"可以写简洁版吗"。 陷阱：并发场景要加锁或用 ConcurrentHashMap + 自己维护链表（或直接用 Caffeine）。

Q184 复杂度与 TopK 的取舍

🗣 人话：K 很小就用小顶堆，O(NlogK)；要第 K 大又不想全排序，用快排的 partition，平均 O(N)；数据量太大放不下，先分片各自求 TopK 再合并。

要点：排序 O(NlogN)；堆求 TopK 是 O(NlogK)（K 小优先）；快排 partition 求第 K 大平均 O(N)（会打乱数据）；桶/计数 适合值域小的场景（如年龄、分数）。 10 亿个数找最大 100 个 → 分治 + 小顶堆（内存放不下）；去重 → Bitmap（1 亿用户 ID 约 12MB）。

最左前缀 电话簿按「姓+名」排，你只查名没法用，得从姓开始
索引下推 本该回表后再筛的条件，提前在索引里筛掉，少跑几趟
索引选择性 这个字段能不能把数据分开：性别分不开（没用），手机号能分开（好用）
页分裂 往排好序的页中间硬插一条，塞不下就劈成两页——随机主键的代价
聚簇索引顺序写 主键自增就是「永远往最后加」，不会劈页，所以快
MVCC 给每行留几个历史版本，读的人拿自己那个时间点的版本，互不打扰
ReadView 一张「我这次能看见哪些版本」的名单（快照）
undo log 反悔记录，回滚用；也是 MVCC 历史版本的来源
redo log 记账本，先记账再干活，断电了照账本补——保证不丢
binlog 流水账，主从同步和归档用
两阶段提交 先跟 redo 说「准备好了」，再写 binlog，最后才正式提交——防止两边对不上账
WAL Write-Ahead Log，先写日志再写数据，把「随机写」变成「顺序写」
间隙锁 把两条记录中间的空档也锁上，防止别人插队（防幻读）
Next-Key Lock 记录本身 + 它前面的空档一起锁，左开右闭
幻读 同一次事务里，同样的条件查两次，第二次凭空多出几行——像见了鬼
脏读 读到了别人还没提交的数据（人家可能马上回滚）
不可重复读 同一次事务里，同一行读两次值不一样
深分页 翻到第 100 万页，数据库得先把前面 100 万行数完再扔掉
延迟关联 先在小目录里翻页拿到主键，再回主表取数据——少搬整行
大事务 占着茅坑不拉屎：锁一堆行、undo 一堆、主从延迟一大截
半同步复制 主库等至少一个从库「收到了」才返回成功——少丢一点数据
