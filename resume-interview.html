〇、简历体检：5 个会被打的点（先修）

面试官拿到简历 30 秒内就能看到这些问题，先在简历上修掉，修不掉的准备口径。

1. 时间线有硬伤 ⚠⚠⚠

  • 教育经历写的是「本科 2022-2005」——明显笔误，按你的经历应该是 2019-2022（在职/专升本）。
  • 「TINDA 项目 2019.11-至今」，但北京浙星是 2020.5 入职的——2019.11-2020.5 这段在随行付？要么改成实际入职时间，要么准备好解释。
  • 「ATLATL 2025.12-至今」没问题，但和「帕纳佳世 2022.10-2023.4」之间有近 3 年空档没写项目——面试官会问"22 年底到 25 年底在干什么"（大概率是在做唐库迭代，写上）。
  • 技能第 8 条整段重复了两遍，删掉。

2. 错字和格式 ⚠⚠

  • 使用 EXPLAN 分析慢查询 → EXPLAIN。这个错字最致命——你把 SQL 调优写在技能栏，工具名还拼错，面试官直接掉分。（我是从 PDF 里读出 EXPLAN 的，也可能是提取问题，打开简历自己确认一遍。）
  • 「价钱打印」→ 价格打印；「自主机点餐」→ 自助点餐。
  • 建议全文再过一遍，错字在 6 年简历上是"不细心"信号。

3. 全篇没有数字 ⚠⚠⚠

「十万余商户」是全简历唯一的数字。每段责任描述都要补量级，例：

  • 唐 库：多少门店在用、日均交易多少笔、峰值 QPS 多少；
  • 支付通道：接了几个通道、日均流水规模、掉单率/对账差异率降到多少；
  • 慢 SQL 优化：从多少秒优化到多少毫秒、扫了多少行到多少行。

4. 技术栈停留在 3 年水位 ⚠⚠⚠

简历里是「熟练使用 MySQL/Redis/Spring」+ EXPLAIN 调优 + 缓存穿透雪崩——这是 3 年简历的写法。6 年面试官会预期看到：MQ、微服务/分布式、并发处理、架构设计。两条路：

  • 用了但没写：比如订单超时是不是用了延迟消息？库存扣减有没有用 Redis？写上；
  • 真没用：准备好口径（见八-1），并且把题库里 MQ/分布式的答案吃透，能聊。

5. 所有项目同源 ⚠

沙县、新时代都是"在唐库基础上定制"，TINDA、会生活也是收银 POS 赛道。面试官会怀疑"一个 SaaS 产品卖 N 家客户，你是实施还是研发？"。应对：主动强调你做的是平台层（支付通道、硬件接口、财务模块这种多客户共用的），定制只是数据配置，不是 fork 一份代码。

一、自我介绍 60 秒模板（背下来）

面试官好，我叫我，6 年 Java 后端，一直在做新零售 SaaS 这条线，核心是收银、支付和进销存 ERP。 最近 5 年多在唐库新零售，我主要负责两块：一是支付通道——微信、支付宝、银联商务都接过，包括回调、退款、对账、分账这些全链路；二是硬件接口——收银机、电子秤、扫码盒子、打印机的对接，也用过 MQTT 做过远程控设备的 App。 数据上大概服务过十万级商户，日常主要在做慢 SQL 优化和稳定性，比如把财务报表从几十秒压到秒级。 我的特点是对支付和交易链路的一致性比较熟——掉单、重复支付、对账差异这些坑都趟过。

要点：只说赛道 + 两块专长 + 一个数字。别背技能清单，面试官手里有简历。

二、支付方向（★ 你简历的主战场，14 题）

Q1 ★ 微信、支付宝、银联商务三家的对接差异？

🗣 人话：三家都是「给地址、签名、发请求、等回调」，差别在细节：微信最绕（证书 + 私钥 + 回调还要解密），支付宝最简单（RSA2），银联商务 SDK 老、文档差、进件还得交纸质材料。别逐条背，就说「我做过一层统一网关，把三家差异都关在适配器里」。

要点：从五个维度比——

  • 签名：微信 v3 用平台证书验签 + 商户私钥签名（AES-256-GCM 加密回调解密）；支付宝 RSA2；银联商务类似证书体系但SDK 更老、文档更差。
  • 回调：微信/支付宝都是 POST JSON/表单，要求返回 success 应答，否则重试（微信 15s/15s/30s...衰减重试 8 次）。
  • 退款：都支持原路退回，微信有退款回调，支付宝要轮询或异步通知。
  • 进件：服务商模式下特约商户进件流程各家不同，银联商务经常要线下材料。
  • 坑：微信证书会定期轮换，要定时下载更新，不然某天回调验签全失败；支付宝网关有沙箱但和生产行为有差异。 结合项目：你说"支付通道"，就要能讲出你们怎么抽象统一支付网关——统一下单接口 + 适配器模式，每个通道一个实现。

Q2 ★ 用户付了钱，但回调丢了（掉单），怎么处理？

🗣 人话：用户付了钱，但渠道的通知没到你这儿——钱在人家账上，你系统还显示待支付。三层兜底：定时去问渠道「这单到底付没付」、第二天拿对账单逐笔核、差异报警让人处理。补单也必须幂等，不然一问就补两遍。

要点：三层防线——

  1. 主动查单：定时任务扫"支付中"状态超过 5 分钟的单，调渠道查单接口，查到已支付就补单（补单也要幂等）；
  2. 对账兜底：T+1 下载渠道账单和本地流水比对，差异单人工/自动处理；
  3. 对账差异报警：长款（渠道有本地无）通常是我们掉单，短款（本地有渠道无）通常没真正支付。 结合项目：收银场景还有"扫码后店员以为付了，顾客其实没付"——所以 POS 端要有轮询查单 + 声音提示。

Q3 ★ 支付回调的幂等怎么保证？

🗣 人话：渠道会重复通知你，所以你得「来几次都只算一次」。最硬的靠唯一索引（插第二次直接失败），再配状态机（只允许待支付→已支付，已支付再来直接回 success）。顺序记牢：先验签、再落库、最后应答，别在应答前干重活。

要点：回调会重复（网络超时渠道重发），必须幂等：

  1. 渠道订单号/我方支付流水号唯一索引兜底（并发重复插入直接失败）；
  2. 状态机：只有 待支付 → 已支付 合法，已支付的单再来回调直接返回 success；
  3. 更新前 where status = 'PENDING'，影响行数为 0 说明处理过。 顺序：验签 → 查本地单 → 加唯一锁 → 状态机更新 → 发后续业务（同事务或消息）→ 应答。注意：先落库再发消息，消息丢了还有查单兜底。

Q4 验签失败的常见原因？

🗣 人话：八成是证书过期没更新（微信会定期换），其次是时间戳差太多（服务器时间没同步）、编码不对、参数被网关改过、测试和生产密钥拿混了。别瞎试，先用官方工具把签名原文验一遍。

要点：① 平台证书没更新（微信定期轮换）；② 时间戳超 5 分钟（防重放，注意服务器时间同步 NTP）；③ 编码问题（UTF-8）、参数被网关改写（空值丢失）；④ 拿错密钥（测试/生产混了）。排查思路：先用渠道官方工具验一遍签名原文，别瞎试。

Q5 金额怎么处理？为什么不能用 double？

🗣 人话：钱全程用「分」存整数，或者 BigDecimal，绝不用 double（0.1+0.2 都不等于 0.3）。BigDecimal 比大小用 compareTo，别用 equals（它连小数位数一起比）。还有折扣分摊：几毛钱分不匀时，余数塞最后一行，不然对账永远差一分。

要点：全程用"分"（long）或 BigDecimal，绝不用浮点（0.1+0.2≠0.3）。BigDecimal 要 new BigDecimal(String) 或 BigDecimal.valueOf，比较用 compareTo 不是 equals（equals 会比精度）。收银场景还有整单折扣分摊问题：优惠金额按比例分到商品行，余数放在最后一行，不然对账差一分钱。

Q6 退款怎么做？要注意什么？

🗣 人话：退款单独一张流水表，一笔支付可以退多次；校验「累计退款不能超过支付金额」，用条件更新防并发；退完还要等渠道确认到账；失败要重试加人工兜底。库存和优惠券等确认到账再回补，别提前返。

要点：① 退款单独立流水，和支付单一对多（支持部分退款）；② 退款金额校验：累计退款 ≤ 支付金额，用 where refundable >= ? 条件更新防并发超退；③ 退款也有回调/轮询确认到账状态；④ 退款失败的兜底：重试 + 人工工单；⑤ 业务侧注意库存回补、优惠券返还的时机（回调确认后再返）。

Q7 分账（云直通）是怎么回事？

🗣 人话：平台收钱后按比例分给商户和供应商，钱不经过平台账户（不然算二清，违规）。分账方得先签约进件，T+1 才到账，失败要重试对账。你写了云直通，就得准备一个「分账挂起怎么补偿」的真事。

要点：平台收单后按比例分给商户/供应商，钱不过平台账户（合规要求，二清风险）。要点：分账方要先进件/签约、分账有 T+1 时效、分账失败要重试和对账。你简历写了云直通，至少准备一个分账失败的案例：比如收款方账户异常导致分账挂起，怎么补偿。

Q8 多个支付通道，路由怎么选？

🗣 人话：选通道就看四样：费率便宜、成功率高、限额够不够、这条通道现在活没活着。实现上给每条通道配权重和健康度，按商户/金额筛出可用的，加权挑一个，失败切下一个——但切之前一定先查原单状态，不然容易付两遍。

要点：维度：费率、成功率、限额、通道可用性。实现：配置中心维护通道权重与健康度 → 按商户/行业/金额过滤可用通道 → 加权选择 → 失败自动切下一个（注意防重复支付：切换前先查原单状态）。你接了微信/支付宝/银联，正好答这个。

Q9 ★ 支付状态机画一下

🗣 人话：状态就那么几个：待支付→支付中→已支付→退款中→已退款，外加已关闭。规矩是只能顺着走，跳状态直接拒绝并报警，每次变更留一条流水（谁、什么时候、哪个渠道触发的）。这题必须能画出来。

要点：待支付 → 支付中 → 已支付 →（部分）已退款 → 已关闭；异常分支：已支付→退款中→退款失败→人工处理。 原则：状态只能按图流转，非法流转直接拒绝并报警；每个状态变更都留流水（谁、何时、什么渠道触发）。这题是考你对交易系统基本功的，必须画得出图。

Q10 顾客扫了码但付了两次（重复支付）怎么办？

🗣 人话：同一单开了两个收款码，两边都成功，钱多收了。处理就是多出来的原路退回（一般 T+1 对账发现长款时触发）。预防是同一单同一时刻只允许一个「支付中」的渠道单。

要点：一笔订单同时开了两个收款码/两个通道都成功 → 多收的部分自动原路退款（T+1 对账发现长款时触发）。预防：同一订单同一时刻只允许一个"支付中"的渠道单（Redis 锁 / 状态校验）。

Q11 收银高峰（比如商场周末）支付接口怎么扛？

🗣 人话：核心是「回调别做重活」——验签落库就赶紧回 success，后面的业务丢给队列慢慢做。渠道查单有限频，别把人家惹毛。流水表按时间或商户分表，索引带上商户号。最后一定要说一个真实峰值数字。

要点：① 回调处理异步化（验签落库后快速应答，后续业务走 MQ/线程池）；② 渠道接口有限频，查单任务要限速；③ 数据库层面：支付流水表按时间/商户分表，索引 (商户号,状态,时间)；④ 热点商品库存用 Redis 预扣。答不出数字就说"我们日峰值 X 笔"，回家把真实数字记下来。

Q12 ★ 对账系统怎么设计？

🗣 人话：每天把渠道的对账单下下来，跟自己的流水逐笔核，核出三种差异：渠道有我没有（长款，多半是掉单）、我有渠道没有（短款，多半没真付）、金额对不上。然后自动补单或挂人工。注意跨天的单算哪一天，要跟渠道规则一致。

要点：T+1 三步——

  1. 下载渠道账单（微信/银联都提供 API 或文件）；
  2. 比对：以渠道为准和本地流水双向核对，产出三类差异：长款、短款、金额不符；
  3. 处理：自动冲正（掉单补单）/ 挂人工工单 / 生成日报给财务。 细节：金额单位统一为分、跨天单（23:59 支付 00:01 回调）的切日规则要跟渠道账单对齐。你简历有财务模块，这题答好直接加分。

Q13 支付证书、密钥怎么管理？

🗣 人话：密钥绝不进 Git，放配置中心或 KMS，按环境隔离；平台证书要定时下载更新；还得想好「私钥泄露了怎么办」（换证书、重签）。这题考的是安全意识。

要点：不进 Git（配置中心/KMS/加密配置）、按环境隔离、平台证书定时轮换任务、商户私钥泄露的应急预案（换证书 + 重发请求报文签名）。面试官问这题是在看你的安全意识。

Q14 支付和订单系统之间的事务一致性怎么保证？

🗣 人话：支付成功要改订单、扣库存、加积分，这些不在一个库，没法用一个本地事务罩住。做法是：回调先在自己库里落一笔（这是事实），然后发消息让下游各自处理，失败重试 + 对账兜底。接受「几秒内不一致」，但不接受「永久错」。

要点：支付成功要触发订单状态变更 + 库存扣减 + 会员积分，跨系统不能靠本地事务。方案：支付回调本地事务落库 → 发消息（或本地消息表）→ 下游消费，配合幂等（见 Q3）和定时对账兜底。题库 Q114/Q118 有完整展开。

三、硬件与 IoT（MQTT，6 题）

Q15 ★ MQTT 是什么？为什么设备对接用它不用 HTTP？

🗣 人话：MQTT 是给设备用的「微信」：设备连上 Broker、订阅一个频道，谁发消息谁往频道里发，不用互相认识。比 HTTP 省太多——报文头才 2 个字节，HTTP 光头部就几百字节，而且不用每次握手。设备弱网、性能差，这就是它存在的理由。

要点：发布/订阅模型，长连接、报文头最小 2 字节（HTTP 光头部就几百字节）、支持弱网。设备端性能弱、网络差（4G/WiFi 波动），HTTP 每次握手太重。组件：Publisher → Broker（EMQX/Mosquitto）→ Subscriber，Topic 就是"频道"。

Q16 QoS 0/1/2 的区别？

🗣 人话：QoS0 发了不管（可能丢）；QoS1 至少送到一次（可能重复，所以你得幂等）；QoS2 保证只送一次（多两次握手，慢）。设备控制用 QoS1 + 消息 ID 去重就够。指令要设计成「设成 40 度」而不是「加 1 度」，重复执行也不会错。

要点：0 至多一次（可能丢）；1 至少一次（可能重复，所以要幂等）；2 恰好一次（两次握手，慢）。实践：设备控制指令用 QoS1 + 消息 ID 去重，配 QoS2 不值得。结合你浴缸 App：控温指令丢了要重发，重复执行要无害（幂等指令设计：发"目标温度 40 度"而不是"+1 度"）。

Q17 设备离线了，指令怎么办？

🗣 人话：先看设备在不在线（Broker 的会话状态、遗嘱消息）。不在线就把指令存库排队，等它上线再推；App 那边超时提示「设备不在线」。遗嘱消息是设备掉线时 Broker 替它喊一句「我下线了」，你的服务订阅这个就能同步状态。

要点：① 发送前查在线状态（broker 的会话/遗嘱消息 LWT）；② 离线时：指令落库排队，设备上线后再推（或用 MQTT5 的会话保持 + retained 消息做"最新状态"）；③ App 端超时提示"设备不在线"。遗嘱消息：设备异常断线时 broker 代发"我下线了"，你的服务订阅这个 topic 做状态同步。

Q18 MQTT 怎么保证安全？

🗣 人话：每台设备一个独立账号（clientId + 密码，烧在设备里）、全程 TLS、Topic 做权限隔离——A 设备只能订自己的 topic，不然它能收到 B 家的控制指令，那就是事故。

要点：clientId + 用户名密码（设备唯一凭证烧录）、TLS、topic 权限 ACL（一台设备只能订阅自己的 topic，不能收到别人的指令——不然 A 设备能收到 B 设备的控制指令就是事故）、证书到期管理。

Q19 电子秤、打印机这类不用网络的硬件怎么接？

🗣 人话：这些设备不走网络，收银机本地起个服务，通过串口/USB 或厂家给的 DLL 通信（Java 用 JNA/JNI 调）。小票打印机走 ESC/POS 指令。坑在：多台设备抢一个口、驱动热插拔、SDK 内存泄漏。这是你的亮点，准备一个具体型号踩坑的故事。

要点：收银机本地起服务，通过串口/USB/SDK（厂家提供 DLL/JNI）通信，Java 侧用 JNA/JNI 调 SDK 或走厂商中间件。打印小票用 ESC/POS 指令集。坑：多设备抢占、驱动热插拔、SDK 内存泄漏。你这块是简历亮点，准备一个"对接某型号踩坑"的具体故事。

Q20 配网（帕纳佳世 App）怎么做的？

🗣 人话：就是「怎么把 WiFi 密码告诉一个还没联网的设备」。常见三种：手机广播包里夹带密码（SmartConfig）、设备先自己变热点让手机连上去配（AP 模式）、蓝牙辅助。说清楚你们用的哪种、成功率多少、失败了怎么引导重试。

要点：常见方案：SmartConfig（广播包夹带 WiFi 密码）、AP 热点模式（设备先变热点，App 连上后下发 WiFi 配置）、蓝牙辅助。要点是密钥不落盘、失败重试交互。说清楚你用的哪种、失败率多少。

四、SaaS 多租户与 ERP（8 题）

Q21 ★ 多租户数据隔离怎么做？你们用的哪种？

🗣 人话：三档：一个客户一个库（最干净最贵）、一个客户一个 schema（折中）、大家挤一张表靠 tenant_id 区分（最省钱，全靠代码守纪律）。中小商户的收银 SaaS 基本都是第三种。重点讲你怎么防漏：MyBatis 拦截器自动拼 tenant_id、每张表都带租户列、运营后台跨租户查询要白名单。

要点：三档——独立库（最强隔离、贵）、独立 Schema、共享表 + tenant_id（最省、隔离靠纪律）。收银 SaaS 中小商户量大，基本是共享库 + tenant_id，重点讲：① MyBatis 拦截器自动拼 tenant_id 防漏；② 所有表强制带租户列 + 联合索引最左列；③ 跨租户查询（平台运营后台）的白名单机制。没做过也要说得出为什么这么做。

Q22 商户要定制功能（沙县、新时代），怎么不改崩标准版？

🗣 人话：优先级是「能配置就别改代码，能插件就别开分支」。价格策略、小票模板、字段开关做成配置；真要不同实现就用策略模式按租户注入；开分支是最后一步，开了就得想好怎么合并回去。准备一个「这需求我们用配置解决了」的例子。

要点：配置化 > 插件化 > 分支。优先级：能配置的配置（价格策略、小票模板、字段开关）→ 能插件的插件（策略模式 + Spring 条件装配，按租户注入实现）→ 实在不行开分支（维护噩梦，要说明怎么合并）。你同时服务过标准版和多家定制，准备一个"这个需求我们用配置解决而不是改代码"的例子。

Q23 ★ 库存扣减怎么做？超卖了怎么办？

🗣 人话：数据库那句 update ... where num >= ? 是最后一道锁，影响行数为 0 就是没库存了。量大就在 Redis 里先扣（DECR 或 Lua 保证原子），再异步落库。扣减和回补都要幂等，不然重试一次就多扣一件。

要点：① DB 乐观锁兜底：update stock set num=num-? where sku_id=? and num>=?，影响行数 0 就是库存不足；② 高频场景 Redis 预扣（DECR + Lua 原子），DB 异步落库；③ 扣减和订单要幂等（同一订单重复请求只扣一次）；④ 撤单/退款回补也要幂等。题库 Q131/Q136 有展开。

Q24 进销存的盘点差异怎么处理？

🗣 人话：盘点期间先把出入库锁住（或者单独记差异），盘完生成盘盈盘亏的调整单走审批。库存流水必须一条不落，期末 = 期初 + 进货 - 销售 ± 调整，财务对账就靠这个公式。

要点：盘点单锁定期间禁止出入库（或记录差异流水），盘盈盘亏生成调整单走审批，库存流水（进货/销售/调整/退货）必须可追溯，期末库存 = 期初 + 流水汇总——财务对账靠这个。你做过财务模块，这题应该信手拈来。

Q25 门店断网了还能收银吗？怎么设计？

🗣 人话：门店断网也得能卖货，所以 POS 本地先记账（本地库或文件队列），网恢复再按顺序往上传。防重靠本地单号全局唯一 + 服务端幂等；断网期间价格库存可能变了，恢复后以服务端为准，差异生成异常单让人看。这是收银 SaaS 的灵魂题。

要点：本地优先：POS 本地落库（本地 SQLite/文件队列），网络恢复后按序上传；防重复：本地单号全局唯一，服务端幂等；冲突：断网期间价格/库存变化，恢复后以服务端校验为准，差异生成异常单。这是收银 SaaS 的灵魂问题，必准备。

Q26 商品价格策略（会员价、促销价、整单折扣）怎么设计？

🗣 人话：价格是一层层算下来的：原价 → 会员价 → 活动价 → 整单优惠分摊。关键不是算法，是「能解释」——每笔订单存一份价格快照（当时用了什么规则、怎么算的），不然客户来吵架你查不清。规则多了就用策略 + 责任链。

要点：价格计算要分层：原价 → 会员等级价 → 活动价 → 整单优惠分摊。核心是可解释、可追溯：每笔订单存"价格快照"（当时的规则和计算过程），不然客诉来了查不清。规则多了就用策略模式 + 责任链（题库 Q180 正好能用上）。

Q27 订单流水表越来越大怎么办？

🗣 人话：热数据留三个月在线，老的归档到归档库或 ES；按时间分表；报表别去实时算明细，晚上跑一张日结汇总表，白天直接查汇总。

要点：冷热分离（热数据 3 个月在线，冷数据归档库/ES）+ 按时间分表 + 报表走日结汇总表而不是明细实时算。你做过财务报表，把归档策略讲清楚。

Q28 会员储值/余额怎么保证不出错？

🗣 人话：余额永远不能直接 update 了事。每次变动都插一条流水，同事务里再更新余额，余额随时能用流水重算出来。并发扣减用 where balance >= ? 卡住。任何「直接改余额」的方案，面试官都会追着打。

要点：余额变更只通过流水表（每次变更插入一条流水 + 更新余额，同事务），余额 = 流水累计可重算；并发扣减用 where balance >= ? 条件更新；充值有支付回调驱动。任何"直接 update 余额"的方案都会被打。

五、第三方对接通用题（6 题）

Q29 ★ 对接第三方接口的通用套路是什么？（一定会问）

🗣 人话：背这六条就够：超时和重试要设（只对幂等接口重试）、我这边的接口要幂等（对方可能重复调）、注意人家的调用配额（按次收费的更要命）、对方挂了我得有降级、状态不明的单要定时查、成功率/耗时/错误码要单独监控。

要点：背下来这个清单——

  1. 超时 + 重试：连接/读超时必须设，重试只对幂等接口（题库 Q122 服务雪崩）；
  2. 幂等：回调、重发都按"对方可能重复调你"设计；
  3. 限流配额：企查查按次计费，本地缓存 + 配额监控，超了报警；
  4. 降级：第三方挂了不能拖死主流程（审核失败先标记"待审"，不让用户卡死）；
  5. 对账/补偿：状态不明的单定时查证；
  6. 监控：成功率、RT、错误码分布单独打点。

Q30 阿里云绿网（内容审核）是同步还是异步？怎么设计？

🗣 人话：文本是同步返回的，图片视频是异步回调。设计上：提交完先落库标「审核中」，回调回来再改状态；回调可能丢，所以要有定时反查；审核没过也别把用户卡死，先标记待人工。

要点：文本同步返回结果，图片/视频异步回调。设计：提交任务落库（状态：审核中）→ 回调更新结果 → 回调丢了定时反查 → 审核失败不阻塞主流程（先标记待人工）。要答出"回调不可靠"这个意识。

Q31 飞书开放平台的 token 怎么管理？

🗣 人话：tenant_access_token 两小时过期，不能每台机器各自去刷（会互相顶掉），要集中管理 + 提前刷新 + 放 Redis。发消息失败要重试。这题就是看你有没有真接过。

要点：tenant_access_token 有效期约 2 小时，集中管理 + 提前刷新 + 分布式缓存（别每台机器各自刷，会互相顶掉），限频注意。消息用模板卡片，发送失败重试。这题考"有没有真接过"。

Q32 企查查这类按次收费的接口，怎么省钱？

🗣 人话：工商信息一年也不变几次，先查缓存（T+1，命中率能到九成），能批量就批量，调用量要打点（谁把额度刷没了得查得出来），预付费余额要监控报警。

要点：缓存优先（工商信息变更频率低，T+1 缓存命中率 90%+）、批量查、调用配额打点（谁把额度刷没了要能查到）、预付费余额监控告警。答出"成本意识"是加分项。

Q33 门禁闸机、捷顺停车这种硬件云对接要注意什么？

🗣 人话：这类硬件大多是「云端下指令 + 本地网关盒子执行」，走 WebSocket 或长轮询。三个重点：开门指令重复发要无害（幂等）、断网时本地白名单得能放行、事件上报丢了要重传。准备一个捷顺对接的具体坑。

要点：大多** WebSocket/HTTP 长轮询 + 本地网关盒子模式；重点：指令幂等（开门指令重复发要无害）、离线兜底**（断网时本地白名单放行）、事件上报丢失重传。准备好"捷顺对接踩过什么坑"的实例。

Q34 第三方接口变版本/下线怎么办？

🗣 人话：业务别直接依赖人家的 SDK，中间加一层适配器；新旧版本可以同时跑一段对比结果；提前订阅对方公告；旧版本留兼容期。核心认知：第三方就是你的一个不稳定依赖，得当依赖来管。

要点：适配器隔离（业务不直接依赖 SDK）、双跑灰度（新旧版本同时跑对比结果）、提前订阅对方的公告、保留旧版本兼容期。答出"依赖第三方是风险源，要当依赖管理"。

六、TINDA 海外项目（4 题）

Q35 十万商户的量级，架构上怎么撑的？

🗣 人话：十万商户不等于十万并发，得先拆成「日均多少笔、峰值多少 TPS」。然后按漏斗讲：Nginx 分流 → 应用无状态随便加机器 → 数据库读写分离、按商户分片 → Redis 挡热点。这题面试官一定追数字，回家先算出来。

要点：先说量级拆解：十万商户 ≠ 十万并发，日均交易量、峰值 TPS 才是关键数字（回家算出来）。然后按漏斗讲：Nginx 负载均衡 → 应用无状态水平扩 → MySQL 读写分离/按商户分片 → Redis 缓存热点（商品、价格）。这题你简历写了"维持日益增长的十万余商户"，面试官必问，必须有数字。

Q36 海外项目跟国内比有什么特殊问题？

🗣 人话：四个坑：时区（库里存 UTC，展示按当地，财务日切按当地时间）、货币（金额存最小单位 + 币种，汇率要留快照）、多语言（报表模板也得翻译）、网络差（弱网重试 + 幂等）。再加一条合规（数据出境、当地报税）。挑两条你真踩过的深讲。

要点：① 时区：库里存 UTC 或带时区的时间戳，展示按商户时区转（财务日切按本地时间）；② 货币：金额存"最小单位 + 币种"，汇率换算留快照；③ 多语言：i18n 资源文件，报表模板也要国际化；④ 网络差：客户端弱网重试 + 幂等；⑤ 合规：数据是否出境、本地报税规则（乌兹别克斯坦税控）。你真做过，挑两条深讲。

Q37 报税对接（TINDA 有报税功能）要注意什么？

🗣 人话：税务接口的特点：慢、限频、格式死板、而且不能重复上报（重复报就是事故）。所以上报前先落库防重，失败进补偿队列，每天拿自己的报税流水和税控回执对一遍。

要点：税务接口通常是政府/指定服务商，特点：慢、限频、格式严格、不可重放（重复上报是事故）→ 上报前落库防重、失败进补偿队列、对账按日报税流水和税控回执核对。

Q38 海外部署怎么运维？

🗣 人话：跨境网络又慢又不稳，所以服务要部署在当地，国内只做管控；发版还是 Jenkins，但镜像要提前在本地打好，别跨境拉；日志采样回传；监控别依赖国内访问不了的通道。

要点：跨境网络慢且不稳 → 服务部署在本地/当地云，国内只做管控；发版走 Jenkins 但要注意跨境拉包慢（镜像预打包）；日志回传做采样；监控用当地可达的通道（别依赖 Google 服务）。

七、报表与 SQL 优化（4 题）

Q39 ★ 你简历写了 EXPLAIN 调优，举个例子？（必问，且曾把 EXPLAIN 写错）

🗣 人话：按这个套路讲：财务日报 40 秒 → explain 一看是全表扫 + filesort → 加了 (商户号,状态,时间) 联合索引走 range，扫描行数从 800 万降到 2 万 → 再把 select * 改成只查需要的列 → 最后 800ms。数字换成你自己的。

要点：准备一个真实案例，按这个结构说：

财务日报原来要 40s → EXPLAIN 发现 type=ALL 全表扫 + Using filesort → 加了 (商户号,状态,时间) 联合索引后走 range，扫描行数从 800 万降到 2 万 → 再把 select * 改成只查需要的列（覆盖索引）→ 最终 800ms。 数字换成你真实的。EXPLAIN 重点看什么：type（至少 range）、key、rows、Extra（filesort/temporary 是坏信号）——详见题库 Q59。

Q40 大报表为什么慢？除了加索引还有什么招？

🗣 人话：别实时算明细——晚上跑批生成日结/月结汇总表；导出改成异步任务 + 流式写文件；报表查询走从库；数据再大就丢 ES 或 ClickHouse 去做分析。

要点：① 别实时算明细：日结/月结汇总表，凌晨跑批；② 导出异步化：提交任务 → 后台流式生成（EasyExcel）→ 通知下载（题库 Q138）；③ 读写分离让报表走从库；④ 明细数据量大就丢 ES/ClickHouse 做分析。

Q41 慢接口排查的一般流程？

🗣 人话：按你自己的项目语言讲：先看是不是慢 SQL（你最熟），再看第三方调用有没有设超时（支付渠道、企查查），再 jstack 看线程卡在哪，最后看 GC。结尾一定给一个「优化前多少、优化后多少」。

要点：题库 Q137 的流程背一遍，但要用你的项目语言：先看是不是慢 SQL（占你简历大头）→ 再看第三方调用（支付渠道、企查查，有没有超时配置）→ 线程栈看卡在哪 → GC。结尾给一个"优化前后 RT"的数字。

Q42 数据库连接池怎么配的？

🗣 人话：HikariCP，池子大小从「核数×2」起步，靠压测收敛。最容易犯的错是事务里包了第三方调用——等人家 3 秒，连接就被占 3 秒，量一大就报 connection is not available。

要点：HikariCP，池大小 ≈ 核数*2 起步靠压测收敛，事务里别包第三方调用（连接被占满）。题库 Q143 的"connection is not available"案例就是给你准备的。

Q43 Nginx 在你们架构里干了什么？

Q44 Jenkins 发布流程是什么样的？

🗣 人话：提代码 → Jenkins 拉 → Maven 构建跑单测 → 打镜像 → 测试/预发/生产逐级发 → 出问题一键回滚到上一个包。加分的是：发完自动发飞书通知、发完自动健康检查。

要点：提交代码 → Jenkins 拉取 → Maven 构建 + 单测 → 打镜像/打包 → 按环境发布（测试 → 预发 → 生产）→ 回滚方案（保留上一版本包，一键回滚）。加分点：发布前自动通知（飞书机器人）、发布后健康检查。

Q45 你怎么部署一个新服务？（从零到上线）

要点：按顺序说：服务器初始化（JDK/Nginx/防火墙）→ 数据库建库授权 → 配置中心加配置 → Jenkins 建任务 → 域名/证书 → 监控告警接入 → 灰度验证 → 上线。体现"独立扛过全套"（你简历写了"前期服务搭建、部署上线"）。

Q46 线上出问题你的处理顺序？

十、高风险问题与应答口径

1. "你 6 年了，简历里怎么没有 MQ / 微服务 / 高并发？"

口径（诚实 + 有深度）：

"我们的量级（日均 X 万单、峰值 X）用单体 + 读写分离 + 缓存是够的，我们刻意没有上微服务——拆了之后运维成本和链路复杂度反而上来（题库 Q129 分布式单体）。但我自己研究过 MQ 和分布式事务，比如订单超时关单我知道该用延迟消息 + 扫表兜底（现场讲 Q132）。如果贵司是高并发场景，我的支付对账和幂等经验可以直接迁移。" 态度：不吹，但展示"我知道什么时候该用"。

2. "你所有项目都是一家公司的吧？"

口径：见〇-5——强调平台层角色 + 客户差异化配置，不是 fork 项目。"唐库是产品，沙县、新时代是产品上的租户级定制，我负责的支付通道和财务模块是所有客户共用的。"

3. "为什么从上家公司出来 / 为什么看机会？"

口径：讲成长空间不讲是非："业务进入平稳期，定制化交付为主，技术上新的挑战少了；我希望去交易量更大的场景，把支付和一致性的经验用在更复杂的链路上。"永远不说前公司坏话。

4. "期望薪资？"

口径：先问再答："想先了解下这个岗位的职责范围和级别，再聊数字比较匹配。"被追问答区间不给点："北京 6 年 Java 后端，结合我支付方向的稀缺性，我的预期在市场 75 分位左右，具体可以根据职责谈。"
